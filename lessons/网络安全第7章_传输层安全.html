Chapter 7 · Transport Layer Security

传输层安全

TCP 是一条可靠但完全不设防的管道：它保证字节不丢不乱，却不加密、不认证。序列号是它唯一的「身份证」，而序列号是可以被看到、甚至被猜到的。这一章讲两件事——裸 TCP 会怎么被打，以及在它上面加一层 SSL 之后，那些攻击各自失效在哪一步。

本页按老师 PPT 的顺序和详略组织：PPT 用 44 页讲「传输层安全问题」、49 页讲 SSL、11 页讲 SSL VPN，本页的篇幅也照这个比例分配。每一节先给 PPT 抛出的真实问题，再讲机制，最后说明它留下了什么新问题——那正是下一节的由来。

这一章在解决什么问题

先别急着背 SSL 的四个子协议。这一章之所以能成为一章，是因为它讲的是同一个问题的两半：上半章说明裸 TCP 为什么必然被打，下半章说明SSL 是怎么把每一种打法逐个堵死的。把这条因果关系抓住，后面所有细节都有位置可放。

PPT 第 3 页 · 问题

要保护 Web 数据传输的机密性、完整性和真实性，网络层、传输层、应用层都能做——为什么这一章偏偏讲传输层？

PPT 开篇就把三种方案并排画在一起（课本图 7-1），并没有直接说哪个好。它其实是在提醒你：加密放在哪一层，是个有代价的选择题，不是「越底层越好」。

PPT 给的三个位置（p.3）
  • (a) 网络层：HTTP/FTP/SMTP → TCP → IP/IPSec。对应用完全透明，通用性最好；但它是点对点的，保护的是两个 IP 之间的通道，管不了「哪个用户在用」。
  • (b) 传输层：HTTP/FTP/SMTP → SSL or TLS → TCP → IP。本章的主角。
  • (c) 应用层：S/MIME、Kerberos 各自嵌在具体应用里。能按应用定制，但每个应用都得自己实现一遍。

全章因果链：一根绳从裸 TCP 串到 SSL VPN

这一章看上去是「一堆攻击 + 一堆协议」，实际上是一条链：每一环都在补上一环留下的洞，同时又留下新的洞，逼出下一环。下面这张链，建议在复习任何一节之前都回来扫一眼。

起点
传输层要做两件事：用端口区分服务、用序列号保证有序。这两件事都做成了明文——因为 TCP 设计时只考虑可靠，不考虑对手。
于是
端口暴露了「这台机器跑什么服务」→ 侦察与端口扫描；序列号成了 TCP 判断真实性的唯一凭据，而它看得见、还可能猜得到 → 会话拦截；连接状态要占内存、握手又是半开的 → SYN 洪泛。
补丁不够
改端口、装防火墙、开状态检测、上 IDS/IPS——这些全是外围补丁。根子上的问题一个没解决：TCP 报文本身既不加密也不认证。
承上
既然改不动 TCP，那就在它上面加一层。加在哪？网络层太低（点对点、管不到用户），应用层太散（每个应用重写一遍）→ 选传输层。
本章下半
SSL 要同时给出机密性 + 完整性 + 认证 ⇒ 需要密钥 ⇒ 密钥要协商 ⇒ 握手协议；协商结果是预主密钥 ⇒ 密钥生成；有了密钥要用起来 ⇒ 记录协议；新旧密钥切换要同步 ⇒ 密码变更规格协议；出错和关闭要可认证 ⇒ 告警协议。四个子协议不是并列的，是被一条需求链逼出来的。
留下的坑
① SSL 3.0 自己有毛病（MAC 不是标准 HMAC、CBC 填充不受保护、RSA 密钥交换无前向保密）→ TLS 1.0 ~ 1.3；② SSL 只保护调用了它的那个 TCP 应用，装不上客户端、非 TCP 的应用都管不了 → SSL VPN。

第 1 节 · PPT p.3–13 · 课本 7.1（p.202–206）

传输层：它管什么，又漏了什么

传输层只干两件核心事：用端口把数据交给正确的进程，用序列号把字节排成正确的顺序。这两件事本身都做得很好——问题在于，它们顺手把攻击者需要的两样东西也交出去了：服务清单，和会话身份。

承上
上一章（网络层安全）解决的是「两个 IP 之间的通道」。但通道通了，进程和进程之间还是裸的。
本节
先把传输层这台机器拆开看：端口 / 套接字 / 序列号 / UDP / TCP，每个部件是干什么的。
留下的坑
端口公开可扫、序列号明文可见、连接状态可被耗尽 → 第 2、3、4 节的三类攻击全从这里长出来。

1.1 三个层次都能加密，为什么挑传输层PPT p.3课本 p.202

课本图 7-1 把三种方案并排画出来。开卷考试里，「比较分析在网络层、传输层和应用层实现安全传输的优缺点」正是简答第 11 题，这张对照要能默出来。

位置协议栈优点缺点
(a) 网络层
IPsec		 HTTP/FTP/SMTP → TCP → IP/IPSec 对终端用户和应用完全透明，因而通用性最好；具备过滤功能，只对选中的流量做认证与加密 点对点保护（保的是两个 IP 之间的通道），无法基于用户授权；接入后可能泄露内网拓扑
(b) 传输层
SSL / TLS		 HTTP/FTP/SMTP → SSL or TLS → TCP → IP 端到端（进程到进程）；建在可靠的 TCP 之上，安全协议本身不必再操心丢包重传；应用层直接坐在传输层之上，一次实现，多个应用共享 只能保护基于 TCP 的应用；应用要么调用 SSL 库，要么被改造
(c) 应用层
S/MIME、Kerberos		 S/MIME / Kerberos 嵌在具体应用里 可以针对该应用的特定需求定制安全服务（如邮件的「只签不加密」） 每个应用都要单独实现一遍，无法复用
🔑 SSL 选传输层的三条理由PPT p.50

PPT 第 50 页单独列了这三条，是原话，可以直接抄：

  1. IP 层安全是点对点的，传输层是端对端的——前者保护「两台机器之间」，后者保护「两个进程之间」。
  2. 传输层提高了可靠性，使得高层服务不必关注可靠性问题——SSL 建在 TCP 上，不用自己处理丢包、乱序、重传。（这条正好回答课本简答第 6 题：SSL 收到乱序的记录块能不能自己排序？不能，也不需要——TCP 已经排好了。）
  3. 应用层协议直接构建于传输层之上，在传输层上构架安全协议，可以把高层应用从安全性中解放出来。

1.2 核心功能之一：端口与套接字PPT p.8–12课本 7.1.1 p.203

PPT 第 8 页 · 比喻

一台服务器同时跑着 Web、FTP、SMTP，它们只有一个 IP 地址——数据到了，怎么知道该交给谁？

PPT 用的比喻是：「如果把一个服务器比作一间房子，IP 地址就是出入这间房子的大门，端口是小房间。」一个 IP 的端口有 65536 个（0–65535），靠「IP 地址 + 端口号」区分不同的服务。

PPT 第 9 页给的现实例子

客户端和服务器的端口不是一一对应的：你访问一台 WWW 服务器，服务器用的是 80 端口，而你的浏览器可能用的是 3457 这样的临时端口。这就是为什么「服务端口固定、客户端口随机」——也是后面 OS 指纹识别能拿客户端口范围做文章的原因。

熟知端口速记表课本 p.203

应用程序SSHTELNETSMTPDNSHTTPPOP3SNMPFTP
熟知端口222325538011016121

课本原话：「熟知」就表示这些端口号是 TCP/IP 体系确定并公布的，因而所有用户进程都知道的。当一种新的应用程序出现时，必须为它指派一个熟知端口，否则其他的应用进程就无法和它进行交互。

⚠ PPT 和课本在这里分法不一样，别记混
PPT 第 10 页：分 3 类
课本 p.203：分 2 类

① 公认端口（Well Known）0–1023：紧密绑定于一些服务，通信明确表明了某种服务的协议，如 80 对应 HTTP。

② 注册端口（Registered）1024–49151：松散地绑定于一些服务，也用于许多其它目的。

③ 动态/私有端口（Dynamic/private）49152–65535：理论上不应为服务分配；实际上机器通常从 1024 起分配动态端口。

① 熟知端口（well-known port）0–1023：由 ICANN 分配给常用应用层程序固定使用。

② 一般端口1024–65535：随时分配给请求通信的客户进程。

怎么办：选择题按课本的两分法（ICANN、0–1023），问「端口分几类」若给了 49151 这个数就是按 PPT 的三分法。两者不冲突——PPT 只是把课本的「一般端口」再切成注册和动态两段。另外按协议类型还分 TCP 端口和 UDP 端口，两套端口号相互独立（PPT p.10）。

套接字：这里两边的说法也不同

课本 p.203（更严格）
PPT 第 11 页（偏工程视角）

一个套接字（socket）是一个二元组：(IP 地址, 端口号)。

一对套接字即可标识一条 TCP 连接，它是一个四元组：(本地 IP, 本地端口, 远程 IP, 远程端口)。

加上协议就是五元组：(本地 IP, 本地端口, 协议, 远程 IP, 远程端口)——「协议」主要指 TCP 还是 UDP。

套接字主要有 3 个参数：通信的目的 IP 地址、使用的传输层协议（TCP 或 UDP）、使用的端口号。

把这 3 个参数结合起来与一个 Socket 绑定，应用层就能区分来自不同应用程序进程或网络连接的通信，实现数据传输的并发服务。

📖 为什么光有端口号不够（课本的反例）

主机 A 上的进程 P1 用端口 100 连主机 C 的端口 25（进程 P3）；同时主机 B 上的进程 P2 也用端口 100 连 C 的端口 25。站在 C 的角度，只看端口号 25 根本分不开 P1 和 P2。所以必须把 IP 地址和端口号结合起来用——这就是套接字存在的理由。

📌 PPT 第 12 页的一句话，是整个第 2–4 节的引子

「大部分远程网络攻击针对特定端口的特定服务。但很多 DoS 攻击针对很多端口或套接字，因此传输层攻击目标包括端口、套接字和专门的协议。」
——注意这句话把攻击分成了两类：有目标的（冲着某个服务去，先侦察后攻击 → 第 3 节）和 无差别的（冲着资源去 → 第 4 节）。

1.3 核心功能之二：序列号PPT p.13

PPT 原话：「传输层从高层接收数据块，并将其分成分组，每个分组赋予一个唯一的序列标识，用来跟踪分组。传输层保持一些已经用于端口的序列号表，以防止序列号重复。」

然后紧跟着一句——这是全章第一个真正的安全论断：

序列号用于保持传输层的分组传输有序，序列号顺序增加能被用于传输层拦截攻击 PPT p.13 原文。「顺序增加」是可靠性的需要，同时也是可预测性的来源——这是一个设计上无法两全的取舍。
🔑 为什么序列号成了 TCP 的「身份证」

TCP 没有任何密码学手段。收到一个报文时，它凭什么相信这是对方发的？课本 p.206 的原话是：「TCP 协议确认数据包的真实性的主要根据就是判断序号是否正确。」
也就是说：序列号对了 = 身份就对了。而序列号是明文传输的、还是递增的。第 2 节的全部攻击都建立在这一句上。

⚠ UDP 风暴型 DDoS：为什么它「非常简单易行」

攻击原理（PPT p.5 与课本 p.204 说法一致）：攻击者利用控制的僵尸网络中的大量主机，向攻击目标（主机或网络设备）发送大量 UDP 数据包，使其忙于处理和回应 UDP 报文，导致目标设备不能提供正常服务或者直接死机，严重的会造成全网瘫痪。

为什么特别好用（考点）：由于 UDP 协议不需要与目标建立连接，因此攻击者很容易通过伪造源地址的方式向目标发送攻击报文。
对比一下就懂了：TCP 想伪造源地址，得先猜中服务器的初始序列号才能完成三次握手（见 2.3 盲拦截）；UDP 连这一关都没有。

    📝 课本 7.1.3 对 TCP 的安全性分析：三条课本 p.206

    课本这一段很短，但它是简答第 1 题「简要分析 TCP 协议三次握手过程可能存在的安全问题」的答案骨架，三条都要能展开：

    1. 网络扫描。攻击者可以利用 TCP 连接建立过程来进行端口扫描，从而获得目标主机上的网络服务状态，进一步发起有针对性的攻击。
      课本点名的两种：TCP 全连接扫描（建立完整连接，据成败推断端口状态）和 TCP SYN 扫描（只发 SYN，收到 SYN+ACK 说明监听、收到 RST 说明关闭，然后发 RST 中断）。此外还有 FIN、NULL、Xmas 扫描 → 第 3 节详述。
    2. 拒绝服务（DoS）攻击。由于一台主机或服务器所允许建立的 TCP 连接数是有限的，攻击者常用 TCP 全连接（完成三次握手）或半连接（只完成二次握手）来发起 DoS，如 SYN Flood、TCP 连接耗尽型攻击。
    3. TCP 会话劫持攻击。由于 TCP 对数据包没有采取加密和认证措施，攻击者可以监听到 TCP 报文内容，也可以伪造 TCP 报文。
    ⚠ ISN 预测：会话劫持真正的技术核心课本 p.206–207

    课本这段话把「为什么劫持能成功」讲得最清楚，值得逐句读：

    「TCP 报文段的初始序号（ISN）在 TCP 连接建立时产生，攻击者向目的主机发送连接请求可得到上次的序号，再通过多次测量来回传输路径得到进攻主机到目标主机间数据包传送的来回时间（RTT）。已知上次连接的序号和 RTT，就能预测下次连接的序号。」

    一旦攻击者预测出目标主机选择的起始序号，就可以欺骗该目标主机，使其相信自己正在与一台可信主机进行会话。此外，攻击者还可以伪造发送序号在有效接收窗口内的报文，也可以截获报文并篡改内容后再发送给接收方。
    ——注意最后半句：序号不必精确命中，只要落在接收窗口内就行。这把攻击难度又降了一个数量级。

    本节结论
    TCP 的可靠性建立在序列号上，而它的「安全性」也只有序列号。序列号既是明文，又是递增的。

    看得见序列号的人能接管连接（全会话拦截）；猜得中序列号的人不用看也能接管（盲拦截）。

    2.1 传输层拦截的两个前提PPT p.15

    PPT 第 15 页 · 问题

    一个攻击者想插进别人已经建立好的 TCP 连接里，冒充其中一方继续说话——他至少需要知道些什么？

    答案不是「密码」，因为 TCP 根本没有密码。他需要的东西全都写在报文头里，只是他得拿得到。

    PPT 列出的两个必要条件
    1. 攻击者必须对某种类型的网络层识别（即能伪造 IP 分组、知道双方的网络地址）；
    2. 攻击者必须识别传输序列号。

    PPT 接着说明这两条各自意味着什么：

    • 关于序列号：「攻击者观察 TCP 分组头能识别序列的下一个分组以及任何需要回答响应的分组，拦截传输层连接的能力取决于序列号质量。」
    • 关于伪装：「为完成一次拦截，攻击者必须伪装网络层通信，伪装的分组必须包括源和目的地址、源和目的端口。」
    🔑 「伪装的分组必须包括源和目的地址、源和目的端口」——这就是那个五元组

    回到 1.2：一条 TCP 连接由五元组 (本地 IP, 本地端口, 协议, 远程 IP, 远程端口) 唯一标识。攻击者要冒充其中一方，就得把这五个字段全部填对，再加上一个正确的序列号。
    这六样东西没有一样是加密的——能看到流量的人全都直接读到；看不到流量的人，前五样往往能猜到（IP 和端口都很有规律），只剩序列号这一道关。所以整节的重点全压在序列号上。

    为什么序列号「最好不要依次渐增」PPT p.16

    PPT 第 16 页这一段是全节的枢纽，逐句拆开看：

    1
    「序列号的产生最好不要依次渐增，否则攻击者易于预测下个分组编号」
    这是理想要求。但 TCP 的可靠传输必须靠连续递增的字节编号来做重排和重传确认——所以这个要求在会话内部无法满足。
    2
    「序列号通常起始于随机值，以防止攻击者猜得到第一个分组，但整个会话过程中逐一增加」
    于是折中方案是：只把「起点」随机化（ISN，初始序列号），起点之后照旧递增。
    为什么这个折中有意义：它把攻击者分成了两类——能看到流量的（观察者）和看不到流量的（盲目攻击者）。随机 ISN 对前者毫无用处，对后者却是一道硬门槛。
    3
    「观察者很容易识别序列号并拦截会话，但盲目攻击者不能识别初始序列号，这样盲目攻击者无法决定序列号以及危害传输层连接」
    这就是 2.2 全会话拦截 与 2.3 盲拦截 分成两小节的原因：它们的难度差着一个 ISN。
    4
    「很多传输层协议使用伪随机数发生器，就成为可预测的。这个弱点导致盲目攻击者能危害传输层连接」
    最后一句是打脸的：所谓「随机 ISN」，实现上往往是伪随机的。课本 p.206 补上了具体做法——攻击者先发一次连接请求拿到上次的序号，再测 RTT，就能推算下次的 ISN。
    结论：随机化 ISN 只是提高了门槛，不是根治。根治要等到 SSL 用密钥来担保身份（第 6 节起）。

    2.2 全会话拦截PPT p.17

    PPT 先给了一句总纲：「任何干扰 TCP 连接的攻击都归结为 TCP 拦截，这些攻击常常像 DoS 一样出现，使连接过早结束。」然后分了三种，第一种是全会话拦截。

    攻击者需要什么

    直接的数据链路访问能力——也就是说他得在同一个局域网里，或者在通信路径上。

    在混杂模式下，攻击者观察网络地址、端口以及用于连接的序列号——这三样正好凑齐了 2.1 说的全部条件。

    胜负怎么判

    利用这些信息，攻击者试图比一个 TCP 连接结束更快地响应——本质是一场抢答比赛：谁的伪造报文先到，谁就被对方当成真身。

    成功：攻击者获得一个已连接会话，可直接访问网络服务。
    失败：结果是 DoS（双方序列号错乱、连接被重置），或者干脆被忽略。

    📌 「失败就变 DoS」这句话为什么值得记

    它解释了 PPT 那句总纲：拦截失败的副产品就是拒绝服务。所以现实中看到的很多「莫名其妙断线」，可能是一次失败的劫持，而不是网络故障。这也是为什么 IDS 把「连接异常重置」当作劫持企图的告警信号（→ 第 5 节）。

    2.3 盲拦截：看不见也能接管PPT p.18

    这是 PPT 讲得最细的一种（整整五步都列了出来），也是简答第 2 题「简述 TCP 连接劫持的攻击原理以及应对措施」最好的答题素材。

    PPT 第 18 页 · 前提

    攻击者 C 既不在 A、B 的子网内，也不在通信路径上——他连一个字节的流量都看不到。这样还能劫持吗？

    能。代价是他必须把三件事同时做对：让 A 闭嘴、伪造 A 的身份、猜中 B 的初始序列号。下面这个放映机把五步拆开走一遍，每一步都告诉你此刻各方知道什么、C 又缺什么。

    放映机TCP 盲拦截：五步逐帧PPT p.18
    看两件事：① 「谁知道什么」那一栏里，C 始终看不到 B 发出的 SYN/ACK——他手里的序列号全靠猜；② 「删掉这一步试试」会告诉你，第 ① 步的 DoS 不是可选项：不把 A 打掉，A 收到莫名其妙的 SYN/ACK 会立刻回 RST，连接当场崩掉。
    🔑 盲拦截为什么难，难在哪一步

    五步里只有第 ③ 步是概率事件——猜 B 的 ISN。其余四步都是确定性操作。
    所以「防盲拦截」的全部功夫都花在让 ISN 更难猜上（真随机数发生器而不是伪随机）。而这恰恰印证了 PPT p.16 的最后一句：用伪随机数发生器的实现，等于把这道唯一的门槛拆了。

    2.4 ICMP 重定向与 TCP 拦截PPT p.19

    第三种拦截路子完全绕开了序列号——它不冒充谁，而是把流量整个引到自己这里来，引过来之后自然什么都看得见，就退化成了全会话拦截。

    📖 ICMP 重定向本来是干什么的

    「ICMP 重定向报文是 ICMP 控制报文中的一种。当路由器检测到一台机器使用非优化路由的时候，它会向该主机发送一个 ICMP 重定向报文，请求主机根据这个信息来更新自己的路由表。」
    PPT 还给了触发它的两种情形：① 当路由器从某个接口收到数据、还需要从相同接口转发该数据时；② 当路由器从某个接口收到发往远程网络的数据时，发现源 IP 地址与下一跳属于同一网段时。
    ——两种情形的共同点是：路由器发现「你其实可以走一条更短的路」。

    缺陷在哪

    「由于缺乏必要的合法性检查」——主机收到 ICMP 重定向报文时，不验证它是不是真的来自那台路由器。

    攻击怎么走

    黑客发送 ICMP 重定向信息给被攻击主机，让该主机按黑客的要求修改路由表，进而数据包被转发给恶意主机，实现 TCP 拦截。

    2.5 端口策略：数量、静态与动态PPT p.20–22

    一个端口和多个端口的比较PPT p.20

    减少端口数量能减少攻击因素。 PPT 原话。服务器一般应该将开放的端口数量减少到只有基本服务——如 Web 服务器只打开 HTTP（80/TCP）端口，而远程控制台只打开 SSH（22/TCP）端口。

    这就是安全领域常说的「攻击面最小化」：每多开一个端口，就多一个可能有漏洞的服务、多一条可能被扫到的线索。

    静态端口赋值和动态端口赋值PPT p.21

    远程客户连接到服务器需要两个条件：服务器的网络地址，以及传输协议及端口号。客户端连接时通常连到服务器的众所周知端口，但客户本身可能使用选自动态端口范围内的端口。

    ⚠ 动态端口为什么是安全风险

    某些高层协议不使用固定端口号——PPT 点名的三个：RPC、FTP 的数据连接、NetMeeting。它们的共同模式是：控制服务使用众所周知端口，数据传输则用动态端口。

    「动态端口带来不安全的风险，因为防火墙必须允许大范围的端口可访问网络。」
    拿 FTP 举例最直观：控制连接固定在 21 端口，但每传一个文件就临时协商一个数据端口。防火墙如果不理解 FTP 协议，就只能把一大段端口全放开——那道墙基本等于没有。（现代防火墙的解法是「应用层网关 / 连接跟踪」，读懂 FTP 控制连接里协商的端口号，只临时开那一个。）

    端口扫描PPT p.22

    PPT 第 22 页只有一行：「4. 端口扫描（见后面 TCP 侦察）」——老师把它整个挪到了第 3 节讲。本页也照此处理，见 3.2。

    2.6 信息泄露PPT p.23

    传输层对传输的数据不进行加密，因此传输层协议本身并不对信息保护，监控分组通信的观察者能观察到传输层内容。通常传输层上面的高层提供身份鉴别和加密。 PPT p.23 原话
    🔑 这一句是全章的转折点

    读到「通常传输层上面的高层提供身份鉴别和加密」时要停一下——老师是在这里把上半章和下半章接上的。
    前 20 页讲的所有攻击，根子都是「传输层不加密不认证」；而解法不在传输层内部，在它上面加一层。那一层就是 SSL/TLS，正好是 PPT 下一个大节的主题。

    TCP 侦察

    攻击者不会上来就打。PPT 第 24 页把逻辑说得很直白：「绑定到 TCP 端口的网络服务提供对主机系统的直接访问，通过识别系统的类型和服务的类型，攻击者能选择相应的攻击方向。」——先认清对手是什么系统、开了什么服务，才知道该用哪个漏洞。

    留下的坑
    侦察是有目标的攻击的前奏。还有一类攻击根本不需要侦察——它不在乎你是什么系统，只想耗光你的资源。那是第 4 节的 DoS。

    3.1 操作系统框架：五个特征暴露了你的身份PPT p.24–26

    「操作系统框架」（OS fingerprinting，操作系统指纹）的原理是：RFC 只规定了 TCP 必须怎么做，没规定实现细节该怎么选。各家操作系统在这些没被规定的地方各选各的默认值，于是这些默认值就成了指纹。

    1初始窗口大小

    「不同操作系统采用不同的初始窗口大小，但大部分系统还是使用默认值」，因此根据窗口大小可识别传输数据的操作系统的类型，也可以结合窗口的变化情况判断操作系统类型。

    2TCP 选项

    每个 TCP 分组包含 TCP 报头值的一些选项，不同操作系统支持不同的选项、值和次序。某种情况下，TCP 选项能唯一足够识别操作系统和补丁级别，可识别未打系统补丁的漏洞。

    3序列号

    虽然所有系统用同样的方法增加序列号，但初始序列号是各个操作系统特定的。单个 TCP 连接不能泄露可识别信息，但一系列快速连接能泄露用来建立初始连接的模型——可用来识别操作系统、版本以及补丁版本。

    4客户端口号

    服务器用固定 TCP 端口，客户端可选任何可用端口。不同的系统使用不同的动态端口范围供客户选择，观察动态端口范围可帮助识别操作系统。

    5重试

    当 TCP 分组没有收到回答响应，分组会重新发送。重试次数以及间隔是不同操作系统特定的，可以通过 SYN 重试、SYN-ACK 重试、ACK 重试三种方法来确定。

    ✓怎么防

    PPT 的原话：「可以改变窗口大小、重试超时等默认值，可以阻止多操作系统的识别。」
    ——也就是把默认值改掉，让指纹失真。这正好对应第 5 节「改变系统框架」。

    📌 老师特意加的一句：这项技术是双刃的

    「操作系统框架对诊断技术是有用的，但对攻击者在攻击之前的侦查也是有用的，用来识别操作系统和补丁级别。」
    同一项技术，网管拿去做资产盘点，攻击者拿去做目标筛选。这类「中性技术」在考试里常被拿来出辨析题。

    3.2 端口扫描：对一个 SYN，服务器有四种回答PPT p.27–30

    PPT 第 27 页 · 问题

    攻击者要打一个服务，得先找到它在哪个端口——可他并没有你的服务清单。怎么找？

    PPT 的答案朴素得有点好笑：「端口扫描的任务是企图连接到主机的每一个端口。」挨个敲门，谁应声就是谁。

    「如果端口有回答，则活动服务正在监听端口；如果是众所周知端口，则增加了服务识别的可能性」——敲开 80 端口，基本可以认定是 Web 服务。

    PPT 给的两种扫描方法
    • 目标端口扫描：用以测试特定的端口（我只关心你开没开 22）。
    • 端口扫视（sweep）：用以测试主机上的所有可能的端口（把 65536 个门全敲一遍）。

    四种类型的回答PPT p.28

    这是本小节最该背下来的一段。注意每一种回答后面 PPT 都跟了一句「防火墙可以怎么骗你」——这四句才是重点。

    1
    SYN-ACK → 端口有服务
    假如一个服务在端口运行，那么 SYN-ACK 返回给客户，这是正常的识别。
    防火墙的对策：「为了阻止扫描，一些防火墙无论该端口有没有服务总是返回一个 SYN-ACK，使扫描器不能识别。」→ 这就是下面的「总是回答防御」。
    2
    RST → 端口没有服务
    假如没有服务在运行，很多系统返回一个 RST，这提供一个快速确认：该端口没有服务。
    为什么是 RST：回到 1.5 里 RST 的定义——「用来拒绝一个非法的报文段或拒绝打开一个连接」。往没人监听的端口发 SYN，正是「拒绝打开一个连接」的标准场景。
    3
    ICMP 不可达 → 主机不可达，端口未知
    假如主机不可达，那么 ICMP 分组返回以指示失败，这使端口未知。
    防火墙的对策：「很多防火墙用这种方法迷惑扫描器」——明明主机活着，却回一个 ICMP 不可达，让扫描器以为找错了地方。
    4
    不应答 → 超时，最含糊的一种
    假如分组没有到主机，就没有回答，SYN 请求得不到 SYN-ACK 并超时。虽然这通常意味着主机不可达或不在线……
    防火墙的对策：「……但一些防火墙有意忽略发送的分组并关掉端口。」→ 这就是下面的「无回答防御」。它最耗扫描器的时间，因为对方只能干等到超时。
    🔑 把四种回答串起来看，会发现一件事

    「有服务 → SYN-ACK」「没服务 → RST」这两条是协议规定的诚实行为；而防火墙的三种对策（总是回 SYN-ACK、假装 ICMP 不可达、干脆不回）全都是故意撒谎。
    端口扫描的攻防，本质是一场「目标端还愿不愿意诚实应答」的博弈。这也解释了为什么下面六种防御里有三种都在「怎么回答」上做文章。

    3.3 防御端口扫描的六种方法PPT p.31

    PPT 一口气列了六条。前三条在「怎么回答」上做文章，后三条各走各的路。

    1非标准端口

    将众所周知端口的服务移到非标准端口，以模糊服务类型。
    如把 SSH 从 22 挪到 2222。挡不住全端口扫视，但能滤掉大量只扫常见端口的自动化工具。

    2无回答防御

    因为端口扫描等待分组回答，所以对不活动的端口请求不予回答，使扫描系统等待回答直至超时；但是对活动的端口还是要回答。
    代价：扫描器只是变慢，多花时间照样扫得出来。

    3总是回答防御

    活动与非活动端口总是回答，攻击者无法区别活动和非活动端口。
    比第 2 条彻底：扫描结果里 65536 个端口全是「开放」，等于没扫。

    4敲打协议（knock-knock）

    敲打服务器不打开端口，而是监控其他端口或网络协议，观察到期望的分组序列，服务才启动。
    PPT 给的例子：SSH 服务器先不和端口绑定，直到观察到具有 700 字节不规则数据字长的 ICMP 分组才和端口绑定。

    5主动扫描检测

    入侵检测系统观察扫描主机的一系列连接并阻断访问。
    前四条是「让你扫不出来」，这一条是「你一扫我就把你拉黑」。→ 对应第 5 节的 IDS/IPS。

    6故意延迟

    PPT 只有这四个字。
    思路和第 2 条一致：不阻断，只拖慢。扫 65536 个端口，每个多等 2 秒，全部扫完要 36 小时——在这期间足够被第 5 条发现了。

    骗（1 非标准端口 · 3 总是回答）· 拖（2 无回答 · 6 故意延迟）· 藏（4 敲打协议）· 抓（5 主动扫描检测）
    注意「藏」这一条最特别：其余五条都是「端口开着但让你看不清」，只有敲打协议是「端口真的没开」——扫描器扫到的是事实，只是那个事实要等到正确的「暗号」之后才会改变。

    3.4 日志：为什么它常常抓不到扫描PPT p.32–33

    PPT 原话：「日志对于检测系统扫描和网络攻击很重要。很多网络服务有连接日志，包括时间戳、客户网络地址以及相关的连接信息。」然后紧接着一句转折——这才是重点：

    ⚠ 半连接扫描为什么在服务日志里查不到

    「在握手完成以前，高层并不支持 TCP 连接，结果使部分端口扫描（在握手完成以前）常常没有日志。」
    把 1.5 的三次握手接上就懂了：应用程序（Web 服务器、SSH 服务器）是在三次握手全部完成之后才被 accept() 唤醒的。SYN 扫描只走到第二步就发 RST 掐断，应用程序从头到尾没被叫醒过——它当然写不出日志。
    这正是 SYN 扫描被称为「半开扫描 / 隐蔽扫描」的原因。

    ✓ 那靠什么抓？——把观察点下移到网络层

    PPT 的答案：「网络监控工具如 IDS 和 IPS，一般监控并把 SYN 请求以及任何包括部分建立连接的通信记录日志，SYN 分组被记录，未请求的 ACK 和 RST 也被记录。」
    「基于这些分组的频率、类型和次序，一些工具能识别网络扫描；如果是 IPS，在扫描完成以前能作出反应，阻止更多信息泄露以及限制服务检测。」
    ——IDS 和 IPS 的分工在这句里说清楚了：IDS 记录并告警，IPS 能在扫描完成前就动手拦下。第 5 节会再展开。

    4.1 SYN 攻击：用半连接把内存耗光PPT p.34

    PPT 第 34 页 · 问题

    三次握手是 TCP 的正常流程，攻击者只是「发起连接却不完成」——这怎么就能把服务器打垮？

    因为服务器必须在第二步就开始花钱。PPT 原话：「每个 TCP 实施分配用于管理连接的内存，每个连接包括网络地址、端口、窗口大小、序列号以及用于入出分组的缓存空间。每个服务器收到 SYN 就分配内存。」

    于是攻击变得极其廉价：「SYN 攻击发送大量的 SYN 分组来消耗内存，当连接个数超过限制的时候，新的连接被切断。」

    PPT 对这个过程的完整描述

    「每次 SYN 分组放到一个打开的服务，就产生一个 SYN-ACK 响应，此时客户端不产生 ACK 响应，这时连接被挂起直至超时。足够多的这样挂起将造成 DoS 攻击。」

    🔑 这个攻击的不对称性：为什么它这么难防
    攻击者的成本

    发一个 40 字节的 SYN 包，源地址还是伪造的。发完就不管了——他自己不需要维护任何状态。

    服务器的成本

    分配一整套连接控制块（地址、端口、窗口、序列号、收发缓存），并把它挂在半连接队列里等到超时（默认常常是 63 秒以上，还要重传几次 SYN-ACK）。

    一发一守，代价差着几个数量级——这就是 SYN 攻击的全部秘密。后面所有防护手段，本质都在做同一件事：让服务器推迟花钱，或者干脆不花钱。

    4.2 四种过滤网关防护PPT p.35–40

    PPT 用了整整六页讲这四种。它们的共同思路是：在服务器前面放一个网关/代理，让它替服务器扛住那些不怀好意的 SYN。四种做法从粗到细排下来，正好是一条改进链。

    放映机四种过滤网关防护 · 逐步对照PPT p.35–40
    四种方案在做同一件事的不同程度：「网关超时」只是帮服务器提前打扫（服务器照样分配了内存）；「SYN 网关」把半连接变成全连接（内存占用从「悬着」变成「确定」）；两种「代理」则是让服务器在验证通过之前完全不知情——一个字节的内存都不用花。

    四种方案的取舍对照

    方案网关做什么服务器花不花内存代价 / 副作用
    ① 网关超时设置p.35 防火墙设置 SYN 转发超时参数，该参数远小于服务器的 timeout 时间。计数器到期还没收到客户端 ACK，就往服务器发送 RST 包，使服务器从队列中删去该半连接。 要花，只是提前被回收 治标。攻击速率够高时，队列在超时之前就已经满了。
    ② SYN 网关p.36 收到客户端 SYN 直接转发给服务器；收到服务器的 SYN/ACK 后转发给客户端，同时以客户端的名义给服务器发 ACK 确认包。此时服务器由半连接状态进入连接状态。当客户端确认包到达时，有数据则转发，否则丢弃。 要花，且变成全连接 半连接队列不再溢出，但全连接队列可能被占满——问题被搬了个家。
    ③ SYN 单向代理p.37–38 代理先代替服务器向客户端回应一个序号错误的 SYN ACK。如果收到客户端回应的 RST，就认为该请求通过了验证。一定时间内代理收到客户端重发的 SYN 后，直接向服务器转发，在客户端与服务器之间建立 TCP 连接。连接建立后代理直接转发后续报文，不作处理。 不花——验证通过前服务器毫不知情 依赖「真客户端收到错误序号会回 RST 并重发」这一标准行为；代理只在握手期介入，之后不改报文，开销小。
    ④ SYN 双向代理p.39–40 代理先代替服务器回应正常的 SYN ACK（窗口值为 0）。收到客户端的 ACK 即认为验证通过。代理再向服务器发送同样的 SYN，通过三次握手与服务器建立连接。 不花——同上 建立了两个 TCP 连接（客户端↔代理、代理↔服务器）。由于两个连接使用的序号不同，代理每收到一个报文都要修改报文序号再转发，开销最大。
    📖 单向代理为什么要故意回一个「序号错误」的 SYN ACK

    这是最容易看不懂的一步。它是在做一次「你是不是真的存在」的测试：
    真客户端收到序号对不上的 SYN ACK，按 TCP 规范必然回 RST（拒绝这个非法报文段），然后重发 SYN 重新尝试——两个动作都做了，说明这个 IP 上确实有一个活的 TCP 栈在等回应。
    攻击者用的是伪造源 IP，那个地址上根本没人在等这个响应，既不会回 RST，也不会重发 SYN——测试直接失败，代理连碰都不用碰服务器。
    对比双向代理：它回的是正常的 SYN ACK，验证的是「你会不会回 ACK」。两者都在验证「源地址是不是真的」，只是用了不同的诱饵。

    4.3 加固 TCP/IP 协议栈 · SYN cookiesPPT p.41

    网关那条路是「在外面加东西」，这条路是「改服务器自己」。PPT 列了三条，前两条一句话，第三条是重点。

    1增加最大半连接数

    把队列开大。
    纯粹的军备竞赛：队列开到 10 万，攻击者就发 20 万。而且内存是真花出去的。

    2缩短超时时间

    让半连接更快被回收。
    副作用：网络慢的正常用户会被误杀——他的 ACK 还在路上，连接已经被清了。

    3SYN cookies

    真正的解法：干脆不分配内存。
    应用于 Linux、FreeBSD 等操作系统。

    🔑 SYN cookies：把状态藏进序列号里PPT p.41

    PPT 这一段信息密度很高，拆成四步看：

    1
    队列满时不丢弃、也不分配内存
    「当半连接队列满时，SYN cookies 并不丢弃 SYN 请求，也不分配内存空间，而是通过加密技术来标识半连接状态。」
    2
    把连接信息 hash 成初始序列号
    「服务器的初始序列号是通过对客户端 IP 地址、客户端端口、服务器 IP 地址和服务器端口以及其他一些安全数值等要素进行 hash 运算加密得到的，称之为 cookie。」
    这一步是全部的关键：本来该记在内存里的连接信息，被压缩成一个 32 位的序列号发了出去。服务器不再需要「记住」这个连接——它把记忆寄存在客户端手里了。
    3
    回复 cookie，然后彻底遗忘
    「服务器并不拒绝新的 SYN 请求，而是回复 cookie（回复包的 SYN 序列号）给客户端。」发完这一步，服务器不保留任何状态——攻击者发再多 SYN 也耗不掉内存。
    4
    收到 ACK 时现场验算
    「如果收到客户端的 ACK 包，服务器将客户端的 ACK 序列号减去 1 得到 cookie 比较值，并将上述要素进行一次 hash 运算，看看是否等于此 cookie。如果相等，直接完成三次握手。」
    为什么减 1：回到 1.5 的三次握手——客户端的确认号是 服务器序号 + 1。所以减 1 就还原出了服务器当初发出去的那个 cookie。

    一句话总结：SYN cookies 用「一次 hash 计算」换掉了「一段内存 + 一次超时等待」。攻击者伪造源 IP 的话，cookie 发给了一个不存在的地址，他永远算不出那个 ACK 该填什么——攻击自动失效。

    4.4 RST / FIN 攻击 · ICMP 攻击 · LAND 攻击PPT p.42–43

    SYN 攻击是「不让新连接建立」，这三种是「把已有连接打断」。

    RRST（或 FIN）攻击p.42

    RST = Reset the connection。

    「盲目的 RST 攻击发生在攻击者不能拦截或看到网络连接的时候，用不同的序列和端口值伪造 RST 分组发送，只要其中一个有效就能断开连接。」
    ——注意「只要其中一个有效」：这是撒网式攻击，不需要精确命中，靠量取胜。回想 1.5：落在接收窗口内就算有效，窗口越大越好打。

    IICMP 攻击p.43

    「类似 RST 攻击，ICMP 可用来指定一个断开连接。盲目的 ICMP 攻击也能使 TCP 不能连接。」
    但有一个关键差别：「不像 TCP 重置攻击，防火墙能阻断 ICMP 攻击，而 RST 攻击因为有有效的端口和地址组合，能通过防火墙。」

    LLAND 攻击p.43

    「一个特别打造的 SYN 包中的源地址和目标地址都被设置成某一个服务器地址，导致服务器向它自己的地址发送 SYN-ACK 消息，这个地址又发回 ACK 消息并创建一个空连接，每一个这样的连接都将保留直到超时掉。」
    PPT 给的后果：许多 UNIX 系统将崩溃，而 Windows NT 会变得极其缓慢（大约持续五分钟）。

    📌 「RST 攻击能穿防火墙，ICMP 攻击不能」——这句话是考点

    原因在于两者的合法性长得不一样：
    ICMP 是一类独立的控制报文，防火墙可以整类禁掉（很多企业网就是这么做的），代价只是 ping 和 traceroute 不通。
    RST 则是 TCP 报文的一个标志位，伪造出来的 RST 五元组完全正确——它长得和一个合法连接里的正常复位包一模一样。防火墙无法用「地址/端口」规则区分它，只能靠状态检测（SPI）去比对序列号是否落在合理范围（→ 第 5 节）。

    缓解 TCP 攻击的五条路

    PPT 用三页收束上半章。五条措施要能列出来，但更该注意的是它们的共同特征——那正是下半章存在的理由。

    先分清攻击的两类，因为对策不同PPT p.44

    盲目攻击（blind）
    定向攻击（targeted）

    「没有假定的攻击目标，通过试探发现漏洞，大部分计算机病毒使用这种方法。」
    对它没什么侦察可言——它对谁都一样。防守靠把面收窄（少开端口、防火墙）。

    「针对特定操作系统平台和网络服务。首先通过侦察识别可能的目标，然后攻击可行的目标。」
    对它有效的是破坏侦察——让第 3 节那五个指纹失真，攻击者就选不准弹药。

    1改变系统框架p.44

    「通过改变系统框架可缓解攻击者的识别。」PPT 点名可改的六项：
    SYN 超时 重试计数 重试间隔 初始窗口大小 可用的 TCP 选项 初始序列值

    另加一条：「很多 TCP 端口是标准化的，特定端口用于特定服务。虽然这些端口是标准的，但不是必需的，可以改变端口号以减少攻击的可能性。」
    对照 3.1：这六项正好就是那五个指纹特征。改默认值 = 让指纹失真。

    2阻断攻击指向p.45

    「用防火墙阻断任何外部的 SYN 分组」；对于 DMZ 区内提供的服务，可以设置路由器只开放相应的端口和地址。

    「同时阻断 ICMP 通行能消除来自远程的 ICMP 淹没、拦截和重置攻击的风险。」
    最后半句正好对上 2.4 的 ICMP 重定向和 4.4 的 ICMP 攻击——这是那两处唯一有效的通用对策。

    3状态分组检测（SPI）p.45

    「SPI 跟踪 TCP 连接状态以及具有和已知状态不匹配的分组。」
    PPT 给的例子：一个 RST 分组送到关闭的端口，可以直接丢弃，而不是传递给主机。

    「SPI 能减少拦截攻击、重置攻击、远程系统框架等的影响。」
    这是唯一能对付 RST 攻击的手段——因为伪造的 RST 五元组合法，只有「记得这条连接现在处于什么状态」的设备才看得出它不对劲。

    4入侵检测系统（IDS）p.46

    「IDS 对非标准的或非期望的分组进行监控。IDS 能很快识别远程系统框架、TCP 端口扫描、拦截企图以及 DoS 攻击。」
    四种能力对应本章四节：OS 指纹（3.1）、端口扫描（3.2）、拦截（2.2–2.4）、DoS（第 4 节）。IDS 只报警，不拦截。

    5入侵防御系统（IPS）p.46

    「对于部署在数据转发路径上的 IPS，可以根据预先设定的安全策略，对流经的每个报文进行深度检测（协议分析跟踪、特征匹配、流量统计分析、事件关联分析等）。」

    一旦发现攻击，可立即采取抵御措施：向管理中心告警 · 丢弃该报文 · 切断此次应用会话 · 切断此次 TCP 连接。
    IDS 与 IPS 的分界就在「部署在数据转发路径上」这七个字：IDS 在旁路看，IPS 在路中间站着，所以它能动手。

    ⚠ 把这五条排在一起，会发现一件事

    它们分别在做：改默认值（1）、关门（2）、记状态（3）、看着（4）、动手拦（5）。

    没有任何一条动了 TCP 报文本身。报文照旧是明文的，序列号照旧是唯一的身份凭据。这五条能做的只是让攻击者更难够到那个报文，或者在他够到之后尽快发现。

    换句话说——只要报文本身不加密不认证，防守方就永远处在「猜对手在不在」的位置上。这是补丁的天花板。

    上半章结论
    TCP 的问题不在实现，在设计：它把「真实性」交给了一个明文的、递增的序列号。外围补丁再多也改不了这一点。
    唯一的出路
    既然改不动 TCP（全世界的设备都在跑它），那就在它上面加一层，让这一层用密钥而不是序列号来担保「谁在说话」。

    6.1 Web 安全需求：HTTPS = HTTP + TLS/SSLPPT p.48–49课本 p.207

    PPT 第 48 页 · 问题

    Web 应用是互联网上最广泛的应用，几乎所有商业公司、政府机构都建了网站。可它跑在 TCP 上——而 TCP 不加密也不认证。

    PPT 和课本用的是同一句话：「由于 Web 应用协议主要通过传输层的 TCP 协议来传输其协议报文，而 TCP 协议不支持加密和认证，因此并不能保证 Web 应用传输上的安全。」

    于是有了 SSL（PPT p.48 · 课本 p.207）
    • 网景公司（Netscape）于 1994 年开发了安全套接字（Secure Sockets Layer, SSL）协议，为 Web 浏览器与 Web 服务器之间安全交换信息提供支持。
    • 两个版本：2.0（1995 年）和 3.0（1996 年），最常用的是 3.0 版。IETF 在 2011 年发布的 RFC 6101 中对 SSL 3.0 协议规范进行了详细描述。
    • 后来 IETF 将其标准化，称为「传输层安全（Transport Layer Security, TLS）协议」（→ 第 11 节）。
    • 与 SSL/TLS 有关的国家标准是《GB/T 38636-2020 信息安全技术 传输层密码协议》。

    6.2 为什么把安全放在传输层PPT p.50

    PPT 单独用一页列出三条优点，1.1 已经引过，这里再确认一遍，因为它是简答第 11 题的核心：

  • IP 层安全是点对点的，传输层是端对端的。
  • 传输层提高了可靠性，使得高层服务不必关注可靠性问题。
  • 应用层协议直接构建于传输层之上，在传输层上构架安全协议，可以把高层应用从安全性中解放出来。

    • PPT 同页还给了协议的设计目标，一句话，四件事：

    为两个通讯个体之间提供机密性、完整性、服务器认证以及可选的客户端认证 PPT p.50 原文。注意最后一项——客户端认证是可选的，这条贯穿整个握手协议（阶段 2 的 CertificateRequest、阶段 3 的 Certificate 和 CertificateVerify 全都是可选的）。

    课本补了一个 PPT 没讲的细节，它解释了「透明」到底是什么意思：

    • 模式一：将 SSL（或 TLS）作为传输层之上、应用层之下的一个独立协议子层，对应用程序完全透明。
    • 模式二：将 SSL（或 TLS）嵌入到特定的应用里，比如绝大多数浏览器和 Web 服务器中都实现了 SSL（或 TLS）协议。

    6.4 两个重要概念：连接 vs 会话PPT p.55–58课本 p.208

    PPT 第 55 页 · 为什么要分两个概念

    握手要做公钥运算、要验证书，很贵。你在一个网站上点十个链接，难道要握手十次？

    不用。SSL 把「协商出来的安全参数」和「具体的传输通道」拆成了两个概念——前者叫会话，后者叫连接。一次会话的参数可以被多条连接共享。

    课本把理由写得很直白：「定义会话的目的主要是避免为每次建立连接而进行复杂的密码参数协商过程。」

    连接（connection）
    会话（session）

    「是指一种能够提供合适服务类型（OSI/RM 中定义）的传输通道。对 SSL 来说，这种连接是点对点、暂时的。每条连接都与一个会话关联。」

    对应一条 TCP 连接。参数见表 7-2 连接状态参数（下方）。

    「是指客户与服务器之间的一种关联，由握手协议创建，定义了一组多个连接共享的密码安全参数。」

    对应一次握手的成果。参数见表 7-1 会话状态参数（下方）。

    📖 数量关系与状态机PPT p.56
    • 任何一对通信实体（如客户和服务器上的 HTTP 应用）之间可以有多条安全连接；理论上也允许一对实体之间同时有多个会话，实际上很少出现。

    1. 主密钥（48 字节）在「会话」里，四个工作密钥在「连接」里。这正是「一次握手、多条连接」的实现方式：主密钥算一次，每条连接用各自的随机数从它派生出自己的一套工作密钥（→ 第 8 节）。

    SSL 握手协议 ★ 全章重点

    课本给它的定语是：「客户端和服务器用 SSL 连接通信时使用的第一个子协议」，以及「SSL 中最复杂的协议」。它要在一条完全公开、可被监听、可被篡改的线路上，让两个素不相识的人同时办成三件事：确认对方是谁、商定用什么算法、共同得到一把只有他俩知道的密钥。

    7.3 阶段 1：建立安全能力PPT p.69–70课本 p.213–214

    课本原话：「SSL 握手协议的第一阶段启动逻辑连接，建立这个连接的安全能力（security capabilities）。首先客户端向服务器发出 ClientHello 消息并等待服务器响应，随后服务器向客户端返回 ServerHello 消息，对 ClientHello 消息中的信息进行确认。」

    ClientHello 的五个参数课本 p.214
    ServerHello 怎么答PPT p.70
    版本
    客户端所支持的最高 SSL 版本。
    随机数
    由客户端生成，由 32 位时间戳和一个安全随机数生成器生成的 28 字节随机数组成（合计 32 字节）。主要用于防止密钥交换时的重放攻击。
    会话标志
    变长标志符。非 0 表示客户端想更新现有连接的参数，或为此会话创建一条新的连接；0 值表示客户端想在新会话上创建一条新连接。
    密码套件
    按优先级降序排列的、客户端支持的密码算法列表。每一个元素定义了一个密钥交换方法和一个密码说明。
    压缩方法
    客户端支持的压缩算法列表。
    • 一个 SSL 版本号：取客户端支持的最高版本号和服务端支持的最高版本号中的较低者。
    • 一个用于生成主密钥的 32 字节随机数（客户端一个、服务端一个）。
    • 会话 ID。
    • 从客户端的密码套件列表中选择的一个密码套件。
    • 从客户端的压缩方法列表中选择的压缩方法。
    ⚠ 「取较低者」是降级攻击的入口

    版本和算法都由客户端提议、服务器挑选，而这两条消息此刻还是明文、还没有任何保护。中间人只要把 ClientHello 里的强算法删掉，服务器就只能从剩下的弱算法里挑。
    补救措施在阶段 4 的 Finished 里（见 7.6）。

    📖 密码套件的两部分内容课本 p.214

    第一项内容是密钥交换算法，握手协议支持 5 种：

    RSA
    密钥用接收方的 RSA 公钥加密，必须拥有接收者的公钥证书。
    固定 D-H
    Diffie-Hellman 密钥交换算法，其中包括认证机构签发的 D-H 公钥参数的服务器证书。客户端在证书中提供它自己的 D-H 公钥参数，或需要进行客户端认证时在密钥交换消息中提供证书。
    匿名 D-H
    使用基本的 D-H 算法，在向对方发送 D-H 公钥参数时不进行认证。因此，这种方法容易受到中间人攻击。
    瞬时 D-H
    用于创建瞬时（临时、一次性）的密钥。D-H 公钥在交换时使用发送者的 RSA 或 DSS 私钥签名，接收者用相应公钥验证签名。由于它使用的是临时的认证密钥，因此比前两种 D-H 安全。
    Fortezza
    为 Fortezza 模式定义的密钥交换算法。

    第二项内容是密码规格说明（cipher spec），包含七项：

    密码算法：RC4 / RC2 / DES / 3DES / DES40 / IDEA / Fortezza MAC 算法：MD5 / SHA-1 密码类型：流密码或分组密码 可否出口 散列长度：0 / 16(MD5) / 20(SHA-1) 字节 密钥材料 IV 大小

    7.4 阶段 2：服务器认证与密钥交换PPT p.71课本 p.214–215

    服务器是本阶段所有消息的唯一发送方，客户机是所有消息的唯一接收方。分 4 步：

    1
    证书（Certificate）可选
    「如果需要认证，则第 2 阶段的开始以服务器发送其证书为标志。服务器将 X.509 数字证书和到根 CA 整个证书链发送给客户端，使客户端能用服务器证书中的服务器公钥认证服务器。」
    为什么要发「整个链」而不只是自己那张：客户端信任列表里预装的是根 CA，不是每一张服务器证书。发整条链，客户端才能一层层往上验到某个它预装信任的根。（这条链的验证细节属于第 4 章 PKI 与数字证书的范围，本章只用到结论。）
    2
    服务器密钥交换（ServerKeyExchange）可选
    「这里视密钥交换算法而定。」课本列得很细：
    需要发送：匿名 D-H 交换、瞬时 D-H 交换、RSA 密钥交换但服务器在使用 RSA 时仅用了 RSA 签名密钥、Fortezza 交换。
    不需要发送：其余情况，如使用带有固定 D-H 参数的证书时。
    判断口诀：证书里已经有能用来交换密钥的公钥 → 不用发；没有（证书里的公钥只能签名、或者压根用的是临时密钥）→ 必须补发一条。
    3
    证书请求（CertificateRequest）可选
    「服务端可能会要求客户自身进行验证。」如果服务器使用的是非匿名 D-H 算法，则可向客户端请求证书。消息含两个参数：
    certificate_type 指出公钥算法及其用法　certificate_authorities 指出可接受的认证机构名称列表
    课本给的 certificate_type 取值：RSA（仅限于签名）、DSS（仅限于签名）、固定 D-H 中的 RSA（签名只用于认证，通过发送一个用 RSA 签名的证书来完成）、固定 D-H 中的 DSS（同样仅用于认证）、用于暂态 D-H 中的 RSA、用于暂态 D-H 中的 DSS、Fortezza。
    为什么匿名 D-H 不能请求证书：匿名 D-H 的定义就是「双方都不认证」——服务器自己都没亮明身份，没有立场要求客户端亮身份。PPT 在 IIS 里可以配置强制客户端证书认证，就是把这一步从可选变成必需。
    4
    服务器握手完成（ServerHelloDone）必需
    「服务器向客户端发送服务器响应结束消息，发送完这条消息后服务器需要等待客户端的响应，第 2 阶段结束。」PPT 的说法是「第二阶段的结束，第三阶段开始的信号」。参数为空。
    课本的总结：「上述步骤中，前 3 步是可选的，要根据实际情况来确定是否要发送，只有第 4 步是必需的。」——这句是考点。

    7.5 阶段 3：客户端认证与密钥交换PPT p.72课本 p.215–216

    客户机是本阶段所有消息的唯一发送方，服务器是所有消息的唯一接收方。课本先交代了一个前置动作，别漏掉：

    🔑 发消息之前，客户端要先做两件检查课本 p.215

    「接收到服务器发送的服务器响应结束消息后，如果需要，客户端应该验证服务器提供的证书是否有效，同时还要检查 ServerHello 消息中的参数是否是可接受的。如果所有条件均满足，则客户端将返回一条或多条消息给服务器。」
    ——整个握手里「认证服务器」这件事，就发生在这里，而且是客户端本地完成的，没有任何消息往返。这也是为什么放映机里第 5 步标的是「客户端本地计算」。

    1
    证书（Certificate）可选
    「如果服务器已请求证书，则客户端发送一条 Certificate 消息给服务器。如果没有合适的证书可用，则客户端发送一个 no_certificate 告警。」
    注意这里用到了告警协议（第 9.2 节表 7-4 里的 no_certificate）——四个子协议在握手期间就已经交织在一起了。
    2
    客户端密钥交换（ClientKeyExchange）必需 · 全场最关键的一条
    消息内容与使用的密钥交换类型有关：
    RSA：客户端产生一个 48 字节的预备主密钥（pre_master_secret），并使用服务器证书中的公钥或 ServerKeyExchange 中的临时 RSA 密钥加密。这个预备主密钥将被用于计算后面的主密钥。
    瞬时或匿名 D-H：发送客户端 D-H 公钥参数。
    固定 D-H：由于证书消息已包括 D-H 公钥参数，因此此时消息内容为空。
    Fortezza：发送客户端的 Fortezza 参数。
    这一条是整个握手的胜负手。在此之前双方交换的全是公开信息；从这一条开始，线路上出现了第一个只有服务器能解开的东西。（PPT 第 72 页的原话：「注意这里会使用服务端的公钥进行加密」。）
    3
    证书验证（CertificateVerify）可选
    「客户端给服务器发送一个证书验证消息，以便对客户端证书进行显式验证。此消息只有在客户端证书具有签名能力时才发送（如除带有固定 D-H 参数外的所有证书）。此消息是对一个散列码的签名，该散列码基于前面的消息。」
    CertificateVerify.signature.md5_hash =
    　MD5( master_secret ‖ pad_2 ‖ MD5( handshake_messages ‖ master_secret ‖ pad_1 ) );
    CertificateVerify.signature.sha_hash =
    　SHA( master_secret ‖ pad_2 ‖ SHA( handshake_messages ‖ master_secret ‖ pad_1 ) );
    其中 handshake_message 指所有发送的握手协议消息或接收到的从 ClientHello 消息开始（不包括此消息）的所有消息。如果用户私钥是 DSS，则使用 SHA 散列；如果私钥是 RSA，则它将用来加密 MD5 和 SHA-1 散列值的串接值。
    它到底证明了什么（课本原话）：「这两种情况的主要目的是验证客户端证书的私钥确实为客户端所有，防止他人误用客户端证书。」
    ——光发一张证书不能证明你是证书的主人（证书是公开的，谁都能复制一份）。只有用对应的私钥签个名，才证明你手里有私钥。这正是 PPT 第 72 页写的「对预主密钥和随机数进行签名，证明拥有证书的公钥」。

    课本的总结：「上述步骤中，第 1 步和第 3 步是可选的，只有第 2 步是必需的。」——和阶段 2 的「只有第 4 步必需」放在一起记。

    7.6 阶段 4：完成 · Finished 与降级攻击PPT p.73–74课本 p.216

    课本：「客户端启动 SSL 握手第 4 阶段，完成安全连接的建立。该阶段分为 4 步，前两个消息来自客户端，后两个消息来自服务器。」

  • 客户端 → ChangeCipherSpec。（注意：该消息不是握手协议的一部分，而是属于密码变更规格协议）启用新的密码套件。
  • 客户端 → Finished。用新的密码套件构造并发送，该消息用于验证密钥交换和认证过程是否成功。
  • 服务器 → ChangeCipherSpec。作为对客户端两条消息的响应。
  • 服务器 → Finished。至此握手过程完成，客户端和服务器可以开始交换应用层数据了。
    • 📖 Finished 的计算式课本 p.216

    Finished 消息是两个散列码的串接：

    MD5( master_secret ‖ pad_2 ‖ MD5( handshake_messages ‖ Sender ‖ master_secret ‖ pad_1 ) );
    SHA( master_secret ‖ pad_2 ‖ SHA( handshake_messages ‖ Sender ‖ master_secret ‖ pad_1 ) );

    其中 Sender 是一个识别码，它能够把作为发送者的客户端与 handshake_messages 区分开。handshake_messages 包括从握手消息起到 Sender 码之前的所有数据，但不包括本条消息。
    对比一下 CertificateVerify 的式子会发现：两者结构几乎一样，只多了一个 Sender。加 Sender 的原因是客户端和服务器要各算一个 Finished，必须让两者算出来的值不同，否则一方可以把另一方的 Finished 原样反射回去。

    🔑 PPT 第 74 页：Finished 到底防的是什么PPT p.74

    老师专门用了一页讲这件事，说明它是考点。原文分三句：

  • 「Finished 消息包含了之前所有握手消息的 MAC，这样可防止通过修改握手消息实现的降级攻击。」
  • 「降级攻击：攻击者修改发送的消息，降低使用算法的安全级别。」
  • 「如：攻击者截获发送的 ClientHello 消息，以较弱的算法代替后再发送出去，从而降低了协议的安全性。Finished 消息可发现消息被修改。」

    • 为什么它能发现：Finished 里那个散列的输入是 handshake_messages——从 ClientHello 开始的全部握手报文原文；而它的「盐」是 master_secret——中间人算不出来的东西。

    于是：中间人改了 ClientHello，客户端记得的是原件，服务器记得的是改过的，两边算出的 Finished 对不上 → 握手失败。中间人想同时伪造两边的 Finished？他没有主密钥，算不出来。

    8.1 预主密钥：两种来路PPT p.76

    PPT 第 76 页把两种密钥交换算法下预主密钥的产生方式并排列出来。两者的安全性来源完全不同，这是考点。

    RSA 算法
    D-H 算法

    「客户机随机生成 48 byte 的预主密钥。」

    然后用服务器的公钥加密，放进 ClientKeyExchange 发过去。

    秘密是客户端单方面「造」出来的，靠 RSA 加密保证只有服务器能拿到。
    代价：一旦服务器私钥泄露，历史上录下来的所有会话都能被解密——这就是「不满足前向保密」，也是 TLS 1.3 删掉 RSA 密钥交换的直接原因（见 11.2）。

    「客户机得到随机数 Xc，计算得到 Yc，把 Yc 通过 ClientKeyExchange 消息明文传递给服务器端；根据 a、q、Xc、Ys 计算得到预主密钥。」

    秘密是双方「共同算」出来的，谁也没把它发出去过。
    注意 Yc 是明文传的——D-H 的安全性不依赖于隐藏公开值，而依赖于离散对数难解。窃听者拿到 Yc 和 Ys 也算不出 Xc。
    瞬时 D-H 每次都用新的 Xc，所以天然具备前向保密。

    8.2 主密钥的计算过程PPT p.79课本图 7-10

    课本图 7-10 与 PPT 第 79 页是同一张图。三条并列的支路，每条产出 16 字节，串起来正好 48 字节：

    master_secret =
    　MD5( PM ‖ SHA-1( 'A' ‖ PM ‖ CR ‖ SR ) ) ‖
    　MD5( PM ‖ SHA-1( 'BB' ‖ PM ‖ CR ‖ SR ) ) ‖
    　MD5( PM ‖ SHA-1( 'CCC' ‖ PM ‖ CR ‖ SR ) ) PM = 预备主密钥（48 B）　CR = 客户端随机数（32 B）　SR = 服务器随机数（32 B）
    图中 SR 与 CR 是客户端和服务器在握手协议的「阶段 1」中交换得到的随机数（课本 p.217 原话）。
    每条支路 MD5 输出 16 B，3 × 16 = 48 B，正好是主密钥的长度。
    🔑 三个问题，把这条式子读懂

    ① 为什么要 'A' / 'BB' / 'CCC' 这三个常数？
    三条支路的其它输入完全相同（都是 PM ‖ CR ‖ SR）。不加这三个常数，三条支路会算出一模一样的 16 字节，主密钥就变成同一段重复三遍、有效熵只有 16 字节。常数存在的唯一作用就是把三条支路岔开。
    选 'A'、'BB'、'CCC' 而不是 1、2、3，是因为长度也不同，进一步保证输入不会碰撞。

    ② 为什么套两层散列，MD5 外面包 SHA-1？
    课本 p.219 在讲 TLS 的 PRF 时给了同样思路的解释：「为了提高 PRF 的安全性，同一种情况下可以使用两个不同的散列函数。如果这两个函数中有一个是安全的，则其安全性就可得到保证。」
    也就是「双保险」——MD5 若被攻破还有 SHA-1 顶着，反之亦然。这在 1996 年是很有远见的设计（MD5 确实在 2004 年后被攻破了）。

    ③ 随机数 CR、SR 起什么作用？
    课本 p.218 的原话最到位：「算法的结果类似于一个伪随机数，主密钥可以认为是伪随机函数的种子值。客户端和服务器的随机数可以认为是增加密码分析复杂度的盐值（salt value）。」
    更实际的意义：即使预主密钥重复了，只要 CR/SR 不同，主密钥也不同——这就是 ClientHello 里那句「随机数主要用于防止密钥交换时的重放攻击」的落点。攻击者重放一条旧的 ClientKeyExchange，因为本次的 CR/SR 是新的，算出的主密钥对不上，会话建不起来。

    PPT 第 77 页先说清楚为什么不能直接用主密钥：

    预主密钥不直接用于保护数据，而是生成 4 个用于数据保护的会话密钥。 PPT p.77 原文
    S服务器方向

    服务器写加密密钥 Esc、服务器写 MAC 密钥 Msc：分别用于服务器发出数据的加密和消息验证码计算。

    C客户端方向

    客户端写加密密钥 Ecs、客户端写 MAC 密钥 Mcs：分别用于客户端发出数据的加密和消息验证码计算。

    🔑 为什么要四把，一把不行吗？

    两个维度各拆一次，2 × 2 = 4。

    维度一：加密 vs MAC 必须用不同密钥。同一把密钥既拿去加密又拿去算 MAC，两套算法可能互相泄露信息（密码学上叫「密钥分离原则」）。

    维度二：收发方向必须用不同密钥。如果两个方向共用一把，攻击者就能把服务器发给你的一条合法密文，原样反射回服务器——服务器用同一把密钥解密、验 MAC，全都通过。这类攻击叫「反射攻击」，方向分离是最简单的根治办法。
    同样的道理也解释了 Finished 里那个 Sender 识别码（见 7.6）：凡是双方要各算一份的东西，都必须让两份不一样。

    2. 密钥的派生靠单向散列。预备主密钥 + 双方随机数 → 主密钥（48 B）→ 密钥块 → 六个参数。随机数是明文的没关系，缺了预备主密钥就什么也算不出来。
    3. 结果的确认靠 Finished。双方各自算完密钥后，用新密钥发一条 Finished，内含全部握手消息的散列。对得上，说明两边算出的密钥相同、且握手过程没被篡改。

    加一句会加分：整个过程中会话密钥本身从未在网络上出现过——传的只是「预备主密钥的密文」和两个公开随机数，真正的四把工作密钥是双方各自在本地算出来的。这就是「安全分发」的确切含义。

    这是本章最典型的「开卷也翻不到答案」的题——课本正文里没有解释，只能靠理解。先自己想一想，再展开下面的答案。

    答为什么密码变更规格必须独立成一个协议？

    核心一句：因为记录协议是靠「内容类型」来决定怎么处理一条记录的，而这条消息恰恰是「处理方式发生改变」的那道分界线——它必须能被记录层在解析内容之前就识别出来。

    拆成三条来说：

    ① 记录层必须一看首部就知道「换挡点到了」

    回到 10.2 的记录格式：SSL 首部第一个字段就是内容类型（8 位），取值有四种——应用数据、告警协议报文、握手协议报文、密码更改规范协议报文。记录层读到类型，就知道该把载荷交给谁、该用哪套参数处理。

    如果 ChangeCipherSpec 只是握手协议里的一条普通报文，那么它的内容类型就是「握手协议报文」，和 ClientHello、Finished 完全一样。记录层要判断「这条记录之后该换参数了」，就必须拆开握手报文的内部结构去看它是第几号消息——这直接破坏了分层：下层不该需要理解上层的语义。

    独立成一个协议 = 拿到一个独立的内容类型，记录层只看首部第一个字节就能完成换挡，不必窥探载荷。

    ② 它必须单独成为一条记录，不能和别的握手消息挤在一起

    SSL 允许多条握手消息合并进同一条记录发送（也允许一条长消息拆到多条记录）。假设 ChangeCipherSpec 是握手消息之一，那就可能出现「ServerHelloDone + ChangeCipherSpec + Finished」被打包进同一条记录的情况。

    可是这条记录该整体用什么参数处理？前两条消息属于旧参数，Finished 已经属于新参数了——一条记录只能整体加密一次、算一个 MAC，无法半条用旧密钥半条用新密钥。这在实现上是死结。

    独立成协议之后，它天然就是单独的一条记录（不同内容类型的载荷不能合并），换挡点干干净净地卡在两条记录之间。

    ③ 它不能被计入 Finished 的散列输入

    回看 7.6 的 Finished 计算式，输入里有 handshake_messages，课本的定义是「从握手消息起到 Sender 码之前的所有数据」——指的是握手协议的消息。

    ChangeCipherSpec 正好夹在「最后一条握手消息」和「Finished」之间。如果它算握手消息，那它自己就得被计入 Finished 的散列；而它又是触发换挡的那条消息，双方对「散列到哪里为止」的理解极易出现一步之差。把它划出握手协议，这个边界问题就自动消失了——课本 p.216 那句括号提醒（「该消息不是握手协议的一部分，而是属于密码变更规格协议」）说的正是这件事。

    📝 考试怎么写（三句话版本）

    ① 记录协议按内容类型分派处理，独立成协议才能让记录层不解析载荷就识别出密码参数的切换点，维持分层清晰；
    ② 独立的内容类型保证它单独成为一条记录，避免同一条记录里出现「一半用旧密钥、一半用新密钥」的无法处理的情况；
    ③ 它不计入握手消息的散列范围，使 Finished 的计算边界明确无歧义。
    （补一句加分：这条消息的本质是状态机的一次转换信号——把「挂起状态」变成「当前状态」，见 6.4。信号和内容分属不同协议，是协议设计上的常规做法。）

    ⚠ 顺手记住一个连带细节

    表 7-2 里序列号那一行写着：「当接收或发送一个密码更改规范协议报文时，序列号被置 0。」
    为什么：MAC 的计算输入里含序列号（见 10.1）。换了新的 MAC 密钥就重新从 0 计数，既简单又不会出问题；如果沿用旧计数，将来分析协议时还要区分「这个序列号是在哪套密钥下用的」，徒增复杂度。

    2报错机制

    3封装

    「同应用数据一样，SSL 告警协议报文同样交由 SSL 记录协议进行压缩和加密处理后发送。」
    课本 p.211 同样强调了这一句——告警不是明文，这是「可认证」的前提。

    追问什么是截断攻击？为什么一条 close_notify 就能防住它？

    截断攻击（truncation attack）：攻击者伪造一个 TCP 层的 FIN 或 RST，把连接提前掐断，让接收方误以为「对方已经说完了」，而实际上后面还有数据没发。

    为什么这很危险——举个例子：服务器要发的是「转账失败，余额不足，请勿重试」，攻击者在「转账」两个字之后把连接掐断，接收方看到的就是半句话。更经典的场景是把「拒绝」截成「同意」的前缀，或者截掉一条安全策略的否定部分。

    问题的根源：TCP 的 FIN/RST 不在 SSL 的保护范围内——它们是传输层的东西，SSL 记录协议管不着，任何人都能伪造（回看 4.4 的 RST 攻击）。SSL 层如果只依赖 TCP 连接的关闭来判断「对方说完了」，就等于把这个判断交给了一个不可信的信号。

    close_notify 的解法：在 SSL 自己的层面上定义一条「我说完了」的消息，而这条消息是走记录协议发出去的——被加密、被算了 MAC。于是：

    • 收到了 close_notify 且 MAC 校验通过 → 确认是对方本人说的「说完了」，数据完整。
    • 没收到 close_notify，连接却断了 → 说明有人在中间掐线，本次数据不完整，不可信。

    这正是表 7-4 里 close_notify 的说明为什么特意加了一句：「各方在关闭连接的写通道时均需发送结束通知。」——不是「可以发」，是「必须发」，否则对端无法区分正常结束和被截断。

    SSL 记录协议

    前面三节协商出来的一切——密码套件、压缩方法、四把密钥、两个 IV、序列号——全部在这一节被用掉。课本给它的定位：「记录协议在 SSL 握手协议完成客户端和服务器之间的握手过程后使用」，PPT 给的定位：「记录协议是 SSL 的数据承载协议，记录是它的数据传输单位」。

    📖 它提供哪两种安全服务课本 p.209
    • 保密性：使用握手协议得到的传统加密共享密钥来加密 SSL 载荷以实现保密性。
    • 完整性：使用握手协议得到的 MAC 共享密钥对 SSL 载荷进行消息完整性检验。

    注意它没有提供认证性——认证是握手协议干的（靠证书）。记录协议只负责「保密 + 完整」这两件事，这是选择题第 2、3 题的分界线。

    10.1 发送方五步流水线PPT p.91、p.93课本 p.209–210 · 图 7-7

    课本 p.209 的原话把整条流水线压成了一句：「记录协议接收到一个要传送的应用消息后，将其分段为块、压缩（可选）、添加 MAC、加密，最后加上 SSL 首部，并将得到的最终数据单元交 TCP 协议发送。」

    1
    分段（Fragmentation）
    「每个上层应用数据被分割成若干个小于或等于 214（16 384）字节的报文段。」PPT 的说法是「将高层协议数据分段，在每个分片添加一个记录头」。
    为什么要有上限：MAC 是对整块算的、加密也是对整块做的——接收方必须收齐一整条记录才能验 MAC 和解密。块太大就意味着延迟高、缓冲区大。16 KB 是延迟与开销的折中。
    顺带回答了简答第 6 题：SSL 收到乱序的记录块不能也不需要自己排序——TCP 已经保证了有序交付，SSL 拿到手时就是有序的（这正是 6.2「传输层提高了可靠性，使得高层服务不必关注可靠性问题」的具体体现）。
    2
    压缩（Compression）可选
    「如果要求压缩，则将每个报文段进行压缩。压缩必须采用无损压缩方法，并且增加长度不能超过 1024 字节。」
    课本还解释了为什么「增加长度」这种怪事会发生：「一般情况下，压缩后的长度要小于压缩前的长度，但对于非常小的数据块，有可能会出现压缩算法的输出比输入长。」
    实际上这一步是空的：「在 SSL 3.0（以及当前的 TLS 中）没有指定压缩算法，所以默认的压缩算法为空，即不压缩。」
    为什么后来干脆不用了：压缩会让密文长度泄露明文内容——这正是 6.1 提到的 CRIME 攻击（属于「协议设计问题」那一类）。PPT 把它列进历史年表里的攻击清单，是有原因的。
    3
    添加 MAC
    对压缩数据计算其消息认证码 MAC，计算方式如下：
    hash( MAC_write_secret ‖ pad_2 ‖
    　　hash( MAC_write_secret ‖ pad_1 ‖ seq_num ‖
    　　　SSLCompressed.type ‖ SSLCompressed.length ‖ SSLCompressed.fragment ) )
    ‖
    为报文连接运算符
    MAC_write_secret
    共享密钥（← 第 8 节导出的 Mcs 或 Msc）
    hash
    散列算法（MD5 或 SHA-1）
    pad_1
    字节 0x36（0011 0110），对 MD5 重复 48 次（384 位），对 SHA-1 重复 40 次（320 位）
    pad_2
    字节 0x5C（0101 1100），重复次数同上
    seq_num
    此消息的序列号
    .type
    处理当前数据块的上层协议
    .length
    压缩后的长度（如果没有压缩，则为明文块的长度）
    .fragment
    压缩后的分块（如果没有压缩，则为明文块）
    三个设计点值得注意：
    ① seq_num 被算进 MAC 里 → 攻击者重放一条旧记录会被发现（序列号对不上），重排记录顺序也会被发现。这是 SSL 抗重放的机制所在。
    ② type 和 length 也被算进去 → 攻击者不能把一条「应用数据」记录改标成「告警」记录，也不能篡改长度。
    ③ 两层散列夹 pad_1 / pad_2 → 这是 HMAC 的雏形。课本 p.219 明确指出差别：SSL 3.0 在填充字节与密钥之间采用的是连接运算（‖），而不是 HMAC 算法的异或运算（⊕）——TLS 改用了标准 HMAC（见 11.1）。
    4
    加密（Encryption）
    「将压缩消息（如果没有压缩，则为明文消息）和 MAC 码用对称加密算法加密。加密所增加的长度不能超过 1024 字节，以使整个报文长度不超过 214 + 2048。」
    流密码
    分组密码

    「压缩消息和 MAC 一起被加密。MAC 在加密之前计算，然后将明文或压缩后的明文与 MAC 一起加密。」

    「填充位（pad_1, pad_2）应在 MAC 之后、加密之前进行。填充的方法是：先填充一定数量的字节后，在最后一个字节中填上填充的总长度。全部填充域的长度应该是使得填充后得到的被加密数据（明文 + MAC + 填充字节）的总长度正好等于分组加密算法中分组长度的最小倍数。」

    ✓ 课本给的填充算例（p.211）

    假定明文（或压缩后的明文）长度 58 字节，MAC 码为 20 字节（使用 SHA-1 算法），加上填充长度（padding_length）占用的 1 字节，一共 79 字节。
    假如分组加密算法的分组长度为 8 字节（使用 DES 算法），则为了达到 8 的最小整数倍（80），需要填充 1 字节。
    口诀：明文 + MAC + 填充 + 1（长度字节） 必须是分组长度的整数倍。

    「先算 MAC 再加密」（MAC-then-Encrypt）是 SSL/TLS 的选择，而课本 p.224 明确说这是一个错误的选择：「事实证明这是一个错误的选择。例如，CBC 加密数据中 MAC 之后的填充字节（Padding）是 SSL 3.0 和一些 TLS 实现中出现的著名的 POODLE 漏洞的成因。」
    为什么错：填充字节在 MAC 之后才加，所以它不受 MAC 保护——攻击者可以篡改填充而完整性检查发现不了。TLS 1.3 的解法是只允许 AEAD（见 11.2）。
    5
    添加 SSL 首部
    加上 4 个字段的记录首部（不加密），交给 TCP 发送。格式见 10.2。

    接收方：完全的逆过程PPT p.91

    解密 → 验证 MAC → 解压 → 分片重组 PPT p.91 原文（课本 p.209 的说法是「解密、完整性验证、解压、报文重组，最后将重组完成后的数据交上层用户」）。
    注意顺序：先解密才能拿到 MAC 去验——因为 MAC 是和明文一起被加密进去的。这也是 MAC-then-Encrypt 的必然结果。

    10.3 链式加密：数字信封PPT p.95

    SSL 采用的是链式加密（数字信封）方法：采用对称加密算法加密消息（SSL 记录协议），用公开密码算法交换对称加密算法的对称密钥（SSL 握手协议） PPT p.95 原文。这一句是整个下半章的收束——它把握手协议和记录协议的分工用一句话说清楚了。

    PPT 第 95 页配的那张图（文字复述）：

    路径发送方 A信道上传的是接收方 B
    E2 · 上路：送钥匙会话密钥 → 加密算法（用 B 的公钥）被 B 公钥加密的会话密钥解密算法（用 B 的私钥） → 会话密钥
    E1 · 下路：送内容明文 → 加密（用会话密钥）密文解密（用会话密钥） → 明文

    图注是「对称和非对称密码算法的应用」。「数字信封」这个名字的由来：把内容装进信封（对称加密），再把信封的钥匙用收件人的锁锁上（非对称加密）——只有收件人能开锁拿钥匙，进而打开信封。

    🔑 为什么不干脆全用公钥加密？

    因为公钥算法太慢。RSA 加密一份 1 MB 的网页要花的时间，比 AES 高好几个数量级。数字信封的做法是各取所长：
    公钥密码解决「怎么在陌生人之间建立共享秘密」——它只需要处理 48 字节的预主密钥，慢一点无所谓；
    对称密码解决「怎么高速保护海量数据」——之后所有应用数据都归它。
    这正好对应第 8 节：握手全程只做了一次公钥运算（加密预主密钥），后面所有的密钥都是用散列函数派生的——散列同样极快。整套设计里，昂贵的操作只出现在必须出现的地方。

    📖 TLS 是怎么来的课本 p.218

    「为了更好地保护 Web 应用的数据传输安全，因特网标准化组织 IETF 在 SSL 3.0 版本的基础上制定了 SSL 的互联网标准版本，称为『传输层安全（Transport Layer Security, TLS）』协议，其主要目标是使 SSL 更安全，并使协议的规范更精确和完善。」

    IETF 在 2011 年发布的 RFC 6167 中建议禁用 SSL 2.0，在 2015 年发布的 RFC 7568 中建议禁用 SSL 3.0。

    11.1 TLS 1.0 与 SSL 3.0 的九点差异课本 7.3.1 p.218–221

    课本原话：「尽管 TLS 1.0 继承了 SSL 3.0 规范的大部分内容，但为了使得协议更规范、安全性更高，TLS 1.0 进行了一些修订。」九点里第 2、3、9 点是重点（都涉及具体的密码学改进），其余偏记忆。

    1
    版本号
    「TLS 记录协议格式与 SSL 记录协议格式完全相同，且各字段意义也完全一致。唯一不同的是版本号。」
    TLS 1.0 → 主版本 3、次版本 1；SSL 3.0 → 主版本 3、次版本 0；TLS 1.1 → 主版本 3、次版本 2。
    为什么 TLS 1.0 的主版本还是 3：因为它就是 SSL 3.1。这个编号方式一直延续到今天——TLS 1.2 在线路上的版本号是 3,3。
    2
    消息认证码 ★
    「TLS 的 MAC 方案与 SSL 3.0 的 MAC 方案有两点不同。」
    2-1　使用的算法：改用标准 HMAC
    TLS 使用的是 RFC 2104 中定义的 HMAC 算法（参见第 3 章）：
    HMACK(M) = H[ (K+ ⊕ opad) ‖ H( (K+ ⊕ ipad) ‖ M ) ]
    M
    HMAC 的消息输入
    H
    散列函数（MD5 或 SHA-1）
    K+
    密钥，长度不规则时左侧用 0 补齐，使其长度等于散列码块长（对 MD5 或 SHA-1 而言，块长等于 512 比特）
    opad
    比特串 01011100（0x5C）重复 64 次（512 比特）
    ipad
    比特串 00110110（0x36）重复 64 次（512 比特）
    2-2　MAC 值的计算范围：多了一个字段
    HMAC_hash( MAC_write_secret, seq_num ‖ TLSCompressed.type ‖
    　TLSCompressed.version ‖ TLSCompressed.length ‖ TLSCompressed.fragment )
    「从上述公式中可以看出，TLS 的 MAC 值计算公式中不仅包括了 SSL 3.0 的所有域，还增加了 TLSCompressed.version 字段（正在使用的协议版本号）。」
    两处改动分别防什么：
    ① 把 ‖ 换成 ⊕：课本 p.219 明确点出 SSL 3.0 的问题——「SSL 3.0 使用了相似的算法，但在填充字节与密钥之间采用的却是连接运算（‖），而不是 HMAC 算法的异或运算（⊕）。」HMAC 是有安全性证明的标准构造，SSL 3.0 那个自创的变体没有。
    ② 把版本号算进 MAC：这样一来中间人改不了版本号字段——直接封死了一类降级攻击。
    3
    伪随机函数 PRF ★
    「TLS 使用一种称为『PRF』的伪随机函数将密钥扩展成密钥生成和验证中的各种密钥数据块。采用伪随机函数的目的是使用相对较小的共享密钥值，通过某种不会受到针对散列函数和 MAC 攻击的方法生成较长的数据块，是更安全的方式。」
    数据扩展函数 P_hash
    P_hash( secret, seed ) = HMAC_hash( secret, A(1) ‖ seed ) ‖
    　HMAC_hash( secret, A(2) ‖ seed ) ‖
    　HMAC_hash( secret, A(3) ‖ seed ) ‖ ⋯

    其中　A(0) = seed　　A(i) = HMAC_hash( secret, A(i − 1) )
    「P_hash 使用 MD5 或 SHA-1 下的 HMAC 算法作为散列函数，并根据迭代的次数来产生所需的数据量。」课本给的两个算例：
    • 用 SHA-1（函数名 P_SHA-1）产生 64 字节：需迭代 4 次，先产生 80 字节，然后将最后的 16 字节丢弃；
    • 用 MD5（函数名 P_MD5）产生 64 字节：同样需迭代 4 次，但此时刚好生成 64 字节。

    「需要注意的是，在上述计算中，每迭代一次要涉及两次 HMAC 计算，每一次计算又涉及两次散列计算。」（所以 1 次迭代 = 4 次散列）

    为什么要用两个散列函数（课本 p.220 原话）：「为了提高 PRF 的安全性，同一种情况下可以使用两个不同的散列函数。如果这两个函数中有一个是安全的，则其安全性就可得到保证。」
    于是 PRF 由两支异或而成，secret 被平分成 S1、S2 两半分别喂给两支：
    PRF( secret, label, seed ) = P_MD5( S1, label ‖ seed ) ⊕ P_SHA-1( S2, label ‖ seed )
    课本 p.220 印出来的式子只有 P_MD5(S1, label‖seed) 这半支（S1 这个记号本身就说明还有个 S2，且上一句刚说了「使用两个不同的散列函数」）。完整式如上。
    PRF 包含三个输入：密钥值、标识符和种子。通过这些参数可以生成一个任意长的输出。
    4
    告警码
    「除 no_certificate 外，TLS 继承了 SSL 3.0 中定义的所有告警码。另外，还定义了一些新的告警码。」（表 7-6，见下方）
    为什么偏偏删掉 no_certificate：在 SSL 3.0 里，客户端没有合适证书时要发一条 no_certificate 告警（见 7.5 阶段 3 第 1 步）。TLS 改成了发一条「空的 Certificate 消息」——用正常流程表达「我没有证书」，比额外定义一个告警码更干净。
    5
    密码套件
    「在可用密码套件上，TLS 和 SSL 3.0 存在细小差别，即 TLS 不支持 Fortezza 密钥交换、加密算法，而 SSL 3.0 是支持的。」（对照 表 7-3 最后一行）

    客户端证书类型
    在 CertificateRequest 消息中：
    TLS 支持：rsa_sign、dss_sign、rsa_fixed_dh、dss_fixed_dh
    TLS 不支持（但 SSL 3.0 支持）：rsa_ephemeral_dh、dss_ephemeral、fortezza_kea
    7
    CertificateVerify 和 Finished 消息
    「TLS 在 CertificateVerify 和 Finished 消息中计算 MD5 和 SHA-1 散列码时，计算的输入与 SSL 3.0 有少许差别，但安全性相当。」

    CertificateVerify：TLS 中仅对 handshake_message 进行 MD5 或 SHA-1 散列值计算；而 SSL 3.0 中散列值计算还包括主密钥和填充，但这些额外信息似乎并没有增加安全性。

    Finished：TLS 中的 Finished 消息基于共享主密钥、以前的握手消息和客户端与服务器的标识标签上的散列值：

    PRF( master_secret, finished_label,
    　MD5( handshake_messages ) ‖ SHA-1( handshake_messages ) )
    其中 finished_label 对于客户端是 "client finished"，对于服务器是 "server finished"。
    对照 7.6 的 SSL 3.0 版本：SSL 3.0 用的是手工拼的两层散列 + Sender 识别码；TLS 直接调用 PRF，用 "client finished"/"server finished" 这两个字符串标签代替 Sender。作用完全一样——让双方算出的 Finished 不同——只是换成了标准构件。
    8
    密码计算
    「TLS 和 SSL 3.0 在计算主密钥值（master secret）时采用的方式不同。」TLS 把第 8 节那两条手工拼的式子全部换成了 PRF 调用：
    master_secret = PRF( pre_master_secret, "master secret",
    　ClientHello.random ‖ ServerHello.random )

    key_block = PRF( master_secret, "key expansion",
    　SecurityParameters.server_random ‖ SecurityParameters.client_random )
    「上述算法被连续执行，直到完全产生 48 字节的伪随机数输出为止。」「上述算法同样被连续执行，直到产生足够的输出为止。」
    「同 SSL 3.0 一样，密钥块 key_block 也是主密钥 master_secret 和客户端与服务器随机数的函数，但实际的计算方法有所不同。」
    注意随机数的顺序变了：算 master_secret 时是 client ‖ server，算 key_block 时是 server ‖ client。这不是笔误，是故意的——两次调用的输入必须不同，否则同一个 PRF 会产生相关的输出。（对比第 8 节 SSL 3.0 用 'A'/'BB'/'CCC' 岔开支路，是同一个思路的不同实现。）
    9
    填充 ★
    「在 SSL 中，填充后的数据长度正好是分组加密算法中分组长度的最小整数倍。而在 TLS 中，填充后的数据长度可以是分组长度的任意整数倍（但填充的最大长度为 255 字节）。」
    课本给的算例（接着 10.1 那个 79 字节的例子）：明文（若使用了压缩算法，则是压缩后的明文）加 MAC 再加上表示填充长度的 1 字节共 79 字节，则填充长度按字节计算时可以是 1、9、17、25 等，直到 249。
    为什么允许填得更长（课本原话）：「这种可变填充长度可以防止基于对报文长度进行分析的攻击。」
    SSL 3.0 填到刚好够，密文长度几乎等于明文长度——攻击者虽然解不开密文，但能从长度推断内容（你输入的密码是 6 位还是 12 位、你点的是哪个链接）。TLS 允许随机多填几个分组，把长度这条侧信道糊住。
    这也正是 6.1 提到的 CRIME 攻击一类问题的对策。

    11.2 TLS 1.3 的六项改变课本 7.3.2 p.222–225

    课本 p.222 · 两个动机

    TLS 1.2 已经在跑了，为什么还要做一次「演进史上最大的改变」，甚至不惜与 1.2 不兼容？

    ① 安全上的考虑。「TLS 广泛的应用使得其成为了攻击者的『众矢之的』」，课本把攻击分成三类：

    • 利用 TLS 设计本身存在的不足——如幸运十三攻击、三次握手攻击、跨协议攻击；
    • 利用 TLS 所用密码原语本身的缺陷——如 RC4 加密、RSA-PKCS#1v1.5 加密；
    • 利用 TLS 实现库中的漏洞——如心脏出血攻击。

    「面对这一系列的攻击，一直以来采取的措施是『打补丁』，即针对新的攻击做新的修补。然而，由于 TLS 的应用规模过于庞大，不断地在如此大规模的实际应用中打补丁并不容易全面实施。因此，需要删除一些不安全的密码套件，改进协议中导致安全问题的过程和方法。」

    ② 性能上的考虑。全网强制 HTTPS 成为趋势，「不足之处在于交互双方必须运行复杂的 TLS 握手协议才能开始传输信息……在加密数据发送之前（或者重新开始之前连接时），握手 TLS 需要两次额外的往返交互。」这在移动网络上「时延可高达 200ms」。

    1禁止使用 RSA 密钥交换算法 ★

    问题：RSA 模式不满足前向保密（forward secret）。「也就是说，如果攻击者记录了加密对话，然后获取服务器的 RSA 私钥，他们可以将对话解密。甚至如果对话先被记录下来，而密钥在未来的某个时候才获得，这种方法仍然有用。」例如先记录所有加密对话，再用心脏出血之类的技术偷取私钥。

    问题二：百万消息攻击。1998 年 Daniel Bleichenbacher 发现在 SSL 中使用 RSA 加密容易受到攻击——攻击者通过发送一百万条左右精心设计的密文，让服务器用私钥执行 RSA 私钥操作，分析服务器返回的响应是正确还是错误来确定修改结果，进而解密信息。「在某些情况下只需请求数千次消息就可以实现这一攻击，这在一台笔记本电脑上都可以做到。」后来出现大量变种，2017 年的 ROBOT 攻击连 facebook.com 这样的大网站也受影响。

    解法：「TLS 1.3 已经删除了 RSA 密钥交换算法，保留了瞬时 Diffie-Hellman 作为唯一的密钥交换机制。」
    ← 对照 8.1：瞬时 D-H 每次用新的私值，天然具备前向保密。

    2减少不安全的 D-H 参数选项

    「选择 Diffie-Hellman 参数时，因为有太多的选项所以会导致选择错误。在 TLS 早期版本中，D-H 参数的选择取决于人。」

    D-H 的安全取决于离散对数问题的难解性，参数越大越难破解；公钥强度小于 1024 bits 就有可能存在问题。2015 年的 LogJam 攻击和 WeakDH 攻击表明，许多 TLS 服务器可以被攻击者诱导选择较小的 D-H 参数。2016 年 Antonio Sanso 在 OpenSSL 中发现某个参数不满足算法要求的数学特性，产生了安全漏洞。

    解法：「TLS 1.3 将 D-H 参数限制在已知安全的参数范围内。」「当然，它仍然有一些选项供选择。如果只允许一个选项，那么在将来某个时候发现这些参数不安全时，就很难更新 TLS。」
    ——最后这半句是很好的设计哲学题材：安全与可演进性之间的取舍。

    3删除不安全的认证加密方法 ★

    「为了防止攻击者篡改数据，加密是不够的，还需要完整性保护。对于 CBC 模式加密，是通过消息验证码（MAC）来完成的。有两种方法可以整合 MAC 和 CBC 模式加密：一是先对明文加密，然后对密文计算 MAC；二是先对明文计算 MAC，然后加密明文和 MAC。」

    「在 SSL/TLS 中，选择的是后者，即先计算 MAC，然后将 MAC 附在明文后面（如果需要，在 MAC 之后还需填充字节以满足 CBC 加密算法要求）再加密，事实证明这是一个错误的选择。例如，CBC 加密数据中 MAC 之后的填充字节（Padding）是 SSL 3.0 和一些 TLS 实现中出现的著名的 POODLE 漏洞（中间人用密文中间的某一个密文块替换密文的最后一个由填充字节构成的密文块，仍然可以通过基于 MAC 的完整性检查）的成因。」

    解法：「TLS 1.3 中允许的唯一认证加密方法是 AEAD（Authenticated Encryption with Associated Data），它将机密性和完整性整合到一个无缝操作中。」
    ← 选择题第 4 题（唯一认证加密方法 = AEAD）和第 5 题（AEAD 提供机密性和完整性）就出自这一段。

    4禁止一些安全性较弱的密码原语

    RC4 是一种经典流密码，自 TLS 早期就得到了广泛支持。2013 年，它被发现具有可度量的偏差，攻击者可利用它来解密消息。「如第 3 章所述，MD5 和 SHA-1 也不再安全。」

    解法：「TLS 1.3 已删除所有可能存在问题的密码套件和密码模式，包括 CBC 模式密码或不安全的流密码如 RC4。建议使用 SHA-2，不建议使用安全性较弱的 MD5 和 SHA-1。」
    ← 与第 3 点是配套的：删掉 CBC 模式，MAC-then-Encrypt 的问题就从根上消失了。

    5对整个握手过程签名 ★

    「在 TLS 1.2 及更早的版本中，服务器的签名仅涵盖部分握手协议报文。握手的其他部分，特别是用于协商使用哪个对称密码的部分，不使用私钥进行签名。相反，使用对称 MAC 来确保握手未被篡改。这种疏忽导致了许多严重的安全漏洞，如 FREAK、LogJam 攻击等。」

    「FREAK 攻击也称为『降级攻击』，它们允许攻击者强制两个参与者使用双方支持的最弱密码，即使支持更安全的密码也是如此。在这种攻击方式中，攻击者处于握手的中间，并将从客户端通告的服务器支持的密码列表更改为仅包含弱密码。然后，服务器选择一个弱密钥，攻击者通过暴力攻击计算出密钥，从而允许攻击者在握手时伪造 MAC。」

    解法：「在 TLS 1.3 中，服务器对整个握手记录进行签名，包括密钥协商，使得 TLS 可以避免三次握手攻击。此外，TLS 1.3 还实现了握手协议和记录协议的密钥分离。」
    ← 对照 7.6：SSL 3.0 的 Finished 靠的是对称 MAC（用主密钥），中间人只要能算出主密钥就能伪造；TLS 1.3 改用服务器私钥签名，中间人没有私钥，无论如何伪造不了。

    6性能上的改进：2-RTT → 1-RTT → 0-RTT

    问题：在图 7-9 的 SSL 握手初始交换过程中，客户端建立与之前没有见过的服务器的新连接时，需要两次往返才能在连接上发送加密的数据，这一交换过程称为「2-RTT（Round Trip Time）」。这在移动网络上「时延可高达 200ms」。

    1-RTT 怎么来的：「TLS 1.3 舍弃了 RSA 的密钥协商过程，然后基于 ECDH 密钥协商算法优化了整个过程。TLS 1.3 具有更简单的密码协商模型和一组瘦身后的密钥协商选项（没有 RSA，没有很多用户定义的 D-H 参数）。这意味着每个连接都将使用基于 D-H 的密钥交换协议，并且服务器所支持的参数很容易被猜到（使用 X25519 或 P-256 的 ECDHE）。」
    于是客户端可以简单地在第一条消息中就发送 D-H 密钥共享信息（key_share），而不是等到服务器确认它希望支持哪种密钥共享。服务器就可以获知已共享密钥并提前一次往返发送加密数据。
    极少数情况下服务器不支持客户端发送的某一密钥共享，可以发送一个新消息 HelloRetryRequest，让客户端知道它支持哪些密钥构件组。「由于密钥构件列表已被缩减太多，所以一般不会发生这种情况。」

    脚注：ECDHE 中 EC = Elliptic Curves（椭圆曲线），DH = Diffie-Hellman，最后一个 E = Extemporaneous（即临时的意思），指的是椭圆曲线密码（ECC）证书中的随机数，也就是 b·G 中的 b，每次都会重新生成。

    🔑 0-RTT：连接恢复的优化课本 p.225

    「TLS 1.3 除了对新建连接过程进行优化，对连接恢复过程也进行了优化，做到了零次往返（0-RTT）。」

    TLS 1.2 的连接恢复
    TLS 1.3 的 PSK 恢复

    ① 客户端发送 ClientHello，并携带会话 ID（session_id），这个 session_id 用于恢复会话，服务器存储 session_id 对应的通信密钥；
    ② 服务器回复 ServerHello、ChangeCipherSpec 和 Finished。
    仍然要一次往返，而且服务器必须存状态。

    采用预共享密钥（Pre-Shared Key, PSK）恢复的新模式。建立会话之后，双方得到称为「恢复主密钥」的共享密钥。可以用 id（类似 session_id）存储在服务器上，也可以通过仅为服务器所知的密钥（类似 session_ticket）进行加密——此会话 ticket 发送到客户端并在恢复连接时查验。
    「对于已恢复的连接，双方共享恢复主密钥，因此除了提供向前保密，不需要交换密钥。下次客户端连接到服务器上时，它可以从上一次会话中获取密钥并使用它来加密应用数据，并将 session_ticket 发送给服务器。」
    关键差别：用 ticket 时服务器不必存状态（状态被加密后寄存在客户端手里）——和 4.3 的 SYN cookies 完全是同一个思路。

    于是 TLS 1.3 的连接过程就简单多了（课本原文）：
    客户发送 ClientHello（携带 key_share 和 early_data）、Finished 以及应用数据；
    服务器回复 ServerHello（携带 early_data 和 key_share）、EncryptedExtensions、ServerConfiguration、Certificate、CertificateVerify 和 Finished。

    ⚠ 课本给的现状判断（p.225 结尾，容易被问）

    「由于这些变动，TLS 1.3 与 TLS 1.2 并不兼容。目前，主流的版本还是 TLS 1.2，TLS 1.3 的大规模应用还需一段时间。」
    （课本第 2 版成书时的判断。要注意「不兼容」不等于「不能共存」——实际部署中服务器同时支持 1.2 和 1.3，靠握手时协商版本；「不兼容」指的是协议流程本身无法互通，不能用 1.2 的实现去解 1.3 的握手。）

    12.1 从 IPsec VPN 的两个不足说起PPT p.97课本 p.225

    PPT 第 97 页 · 问题

    第 6 章已经讲过 IPsec VPN，它在网络层加密，通用性最好。为什么还需要再造一个 SSL VPN？

    因为 IPsec VPN 有两个结构性的不足，而它们恰恰是「远程终端接入内网」这个场景最在意的两件事。

    不足一 · 无法实现基于用户的授权

    「远程接入内部网络的用户类型多种多样，有公司的分支机构、出差在外的企业员工，也有与企业有合作关系的客户等，不同类型的用户应该具有不同的访问内部网络资源的权限，也就是说需要基于用户的授权。但是，IPsec VPN 无法实现基于用户的授权。」
    根本原因：IPsec 工作在网络层，它眼里只有 IP 地址，没有「用户」这个概念。（回看     1.1：网络层安全是点对点的。）

    不足二 · 可能泄露内部网络结构

    「远程终端通过 IPsec VPN 接入内部网络后，可以访问内部网络上的所有主机，从而获得内部网络的拓扑结构等信息，给内部网络带来安全风险。」
    IPsec VPN 的本质是「把你的电脑变成内网的一台机器」——一旦这台机器被攻破，攻击者就站在内网里了，还能顺手把内网扫一遍（回看 3.2 的端口扫视）。

    🔑 SSL VPN 的核心：一个网关做「翻译官」课本 p.225

    「SSL VPN 的核心是 SSL VPN 网关，远程终端通过浏览器和 HTTPS 与 SSL VPN 网关进行通信，由 SSL VPN 网关将远程终端发送的资源访问请求转换成对应的应用层消息，并将内部网络服务器发送的资源访问响应转换成 HTTPS 消息发送给远程终端。」
    两个不足于是同时被解掉了：① 网关能看到「是谁登录的」，所以能按用户授权；② 远程终端从来没有真的进入内网——它只跟网关说话，内网长什么样它一无所知。

    12.2 实现过程的四个阶段PPT p.98课本图 7-12 p.226

    下面的地址沿用 PPT / 课本图 7-12 的示例：SSL VPN 客户端 1.2.3.4；SSL VPN 网关 6.1.4.7 / 10.1.1.2（外网口 / 内网口）；总部网络里有 FTP 服务器 10.2.3.1、DNS 服务器 10.2.3.2、HTTP 服务器 10.2.3.3。

    1
    阶段 1：连接与验证
    ① 建立 HTTPS 会话。远程终端在浏览器地址栏中输入 https:// + SSL VPN 网关的 IP 域名或地址后，浏览器首先发起与网关的 TCP 连接（443 端口）。（图上标注：1.2.3.4, XXX, TCP, 6.1.4.7, 443——正是 1.2 说的那个五元组。）
    TCP 连接建立后，开始 SSL 会话建立过程（← 第 7 节的握手）。SSL 会话建立后，远程终端与网关之间传输的数据都被封装成 TLS 记录协议报文加密传输（← 第 10 节）。
    ② 身份确认。浏览器上出现网关的登录界面，用户输入用户信息：用户名既可以是普通字符串用户名，也可以是数字证书（如 USB Key）；口令可以是静态口令，也可以是动态口令，或者动态和静态口令的组合。
    ③ 应用授权。验证通过后，网关返回该用户的授权服务列表等信息。
    「基于用户的授权」具体怎么落地（课本 p.226）：「SSL VPN 网关为每个注册用户建立授权访问的服务列表。当接收到某个注册用户提供的 URL 后，首先判别授权该用户访问的资源列表是否包含该 URL 指定的资源。只有确定该 URL 指定的资源是授权该用户可访问的资源后，才进行后续的资源访问过程。」
    ——这就是 IPsec VPN 做不到的那件事。网关手里有「用户 → 资源列表」的映射，逐个 URL 检查。
    2
    阶段 2：应用
    即执行访问内部网络资源的操作。用户选择服务种类——三选一，粒度从细到粗：Web 代理 → 端口映射 → IP 连接。详见 12.3。
    PPT 图上在客户端一侧标注了「动态加载 · 免安装客户端」——这是 SSL VPN 最大的卖点之一。
    3
    阶段 3：审计
    「由于 SSL VPN 处在 TCP 之上，所以可以进行丰富的业务控制，可以记录每个用户的所有操作，从而对用户行为进行审计，为更好地管理 VPN 提供有效统计数据。」（图上标为「行为审计（记录用户服务行为）」→ 审计日志）
    「处在 TCP 之上」这五个字是全部理由。IPsec 在网络层，它看到的是 IP 包，只能记录「哪个 IP 跟哪个 IP 通了多少字节」；SSL VPN 在应用层做代理，它看得懂「用户 A 在 15:03 下载了 FTP 服务器上的哪个文件」。
    这同时也是代价：网关必须解密才能审计，所以它是一个天然的解密点——安全性完全押在网关自身上。
    4
    阶段 4：结束
    「当使用者退出 SSL VPN 登录页面时，所有上述安全会话会全部释放。」（图上标为「退出服务」）

    注意 PPT 第 103–104 页举的例子是 DNS（UDP 53），而不是 HTTP 或 FTP。这不是随手挑的：

    • Web 代理转的是 HTTP 请求 → 只能用于 Web；
    • 端口映射映的是 TCP 端口 → 只能用于 TCP 应用；
    • IP 连接封装的是完整的 IP 包 → TCP、UDP 甚至任何 IP 上层协议都能走。

    这正好解释了课本和 PPT 在这一点上的说法差异：
    课本 p.226 说：「SSL/TLS VPN……可以实现所有基于 TCP 协议的应用服务的保护。」
    PPT 第 105 页说：「SSL/TLS VPN 利用 TCP 以及 SSL 对 TCP 会话的保护，可实现对基于 TCP、UDP、IP 的应用的保护。」
    两句都对，只是范围不同：只考虑 Web 代理和端口映射时，确实只能保护 TCP 应用；算上 IP 连接方式，UDP 和任意 IP 应用就都覆盖了。答题时按 PPT 的三种全写，更完整。

    课本 7.6 实验：使用 Wireshark 观察 SSL/TLS 握手过程课本 p.229

    实验目的：通过 Wireshark 软件捕获 TLS 协议握手过程中的所有交互报文，了解 TLS 的握手过程，加深对 TLS 协议的理解。

    实验环境：实验用机的操作系统为 Windows；最新版本的 Wireshark 软件（wireshark.org 官网下载），或由教师提供；访问的目标网站可由教师指定。

    ① ClientHello 里的 Cipher Suites 是一个「列表」，ServerHello 里只剩「一个」——这就是「服务器从客户端列表中选一个」；
    ② 两个 Random 都是明文可读的 32 字节，前 4 字节是 GMT Unix 时间戳（← 7.3 里说的「32 位时间戳 + 28 字节随机数」）；

    ④ ClientKeyExchange 之后紧跟 ChangeCipherSpec，然后 Finished 就变成了「Encrypted Handshake Message」——Wireshark 从这条起就看不懂了，因为已经加密（← 7.6）；

    最容易混的八组概念

    1连接 vs 会话

    会话＝一次握手的成果，装主密钥（48 B），可被多条连接共享；连接＝一条 TCP 通道，点对点、暂时的，装四把工作密钥 + 两个 IV + 序列号。
    口诀：「会话存参数，连接干活。」致命错误杀的是连接，同会话其它连接不受影响。

    2握手协议 vs 记录协议

    握手只产出参数，一个字节的用户数据都不加密；记录协议才真的加密 + 算 MAC。
    选择题第 2、3 题就靠这条分界：「加密传输」→ 记录；「身份鉴别 + 确定算法」→ 握手。

    3全会话拦截 vs 盲拦截

    全会话：要直接的数据链路访问能力（混杂模式），序列号直接看得见，比谁抢答快。
    盲拦截：不在路径上，看不到流量，必须先 DoS 掉被冒充方，再猜 ISN。
    口诀：「看得见的抢答，看不见的猜号。」

    4半连接 vs 全连接

    半连接＝只完成两次握手（收到 SYN、发出 SYN/ACK，等 ACK）→ SYN Flood 打的就是这个队列。
    全连接＝三次握手完成 → TCP 连接耗尽型攻击打这个。
    SYN 网关的做法正是「以客户端名义补发 ACK」，把压力从半连接队列搬到全连接队列。

    5告警 vs 致命错误

    告警（值 1，7 条）：close_notify + no_certificate + 五条证书类（错误/不支持/撤销/过期/未知）——还有回旋余地。
    致命错误（值 2，5 条）：意外消息、MAC 出错、解压失败、握手失败、非法参数——没有任何继续的理由。
    分界线：证书问题可商量，密码学问题不可商量。

    6IDS vs IPS

    分界就在七个字：「部署在数据转发路径上」。
    IDS 在旁路看——只能监控与告警；IPS 站在路中间——能告警 / 丢弃报文 / 切断应用会话 / 切断 TCP 连接。
    PPT：「如果是 IPS，在扫描完成以前能作出反应。」

    7SSL VPN 的三种服务

    粒度由细到粗：Web 代理 → 端口映射 → IP 连接。
    Web 代理：最简单、粒度最细、可精确控制每个链接、不需专门客户端；端口映射：粒度仅次于 Web 代理，类似 NAT 内部服务器；IP 连接：粒度最粗但使用最广，分配一个内网 IP。
    只有 IP 连接封装完整 IP 包，所以只有它能保护 UDP / 任意 IP 应用。

    8IPsec VPN vs SSL VPN

    IPsec 在网络层 → 「网连网」：透明、通用，但无法基于用户授权、可能泄露内网拓扑、要装客户端。
    SSL VPN 在 TCP 之上 → 「人连服务」：可基于用户授权、粒度细、只要浏览器、不泄露拓扑、可审计。
    三道选择题的关键词：「透明」→ IPsec；「用户授权」→ SSL VPN；「浏览器」→ SSL VPN。

    10Finished 里为什么要有 Sender 识别码？ 双方各算一份，必须让两份不同，否则一方能把另一方的 Finished 原样反射回去 课本 p.216 只给了定义
