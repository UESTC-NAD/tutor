Chapter 8 · DNS Security

DNS 安全

你在地址栏敲下 www.example.com 到浏览器真的连上某台服务器之间，有一段几乎没人看见的过程：有人告诉了你的电脑一个 IP 地址，而你的电脑无条件相信了它。这一章讲的就是——凭什么相信、不相信会怎样，以及 DNSSEC 用什么办法让这个「相信」变得可验证。

本页按老师 PPT 的顺序和详略组织：PPT 用 10 页讲 DNS 基础、13 页讲安全威胁、3 页讲 DNSSEC，本页的篇幅也照这个比例分配，但 DNSSEC 一节按课本补足了考试要用的细节（课本 10 道选择题里有 6 道考它）。每一节先给 PPT 抛出的真实问题，再讲机制，最后说明它留下了什么新问题——那正是下一节的由来。

第 0 节 · 总览

这一章在解决什么问题

先别急着背「协议脆弱性、实现脆弱性、操作脆弱性」这三个词。这一章之所以能成为一章，是因为它讲的是同一件事的两半：上半章说明 DNS 为什么必然会被骗，下半章说明 DNSSEC 用什么办法让「骗」变得可以被当场识破。抓住这条因果关系，后面所有细节都有位置可放。

课本开篇 · 问题

你的电脑怎么知道 www.example.com 的 IP 地址是多少？——它问了别人。那它凭什么相信别人给的答案？

这个问题听上去有点抬杠，但它就是整章的题眼。课本第一段把话说得很直白：

课本原文（p.230）

「DNS 通信双方由于缺乏数据来源真实性和完整性的认证机制，系统无法确认数据发送方是否是合法的发送方，也无法验证数据报是否被篡改，攻击者很容易实现源地址和数据内容的欺骗。」

翻译成人话：DNS 协议里根本没有「验明正身」这一步。谁先把一个长得像回答的包送到你面前，你就信谁。所有后面要讲的攻击——事务 ID 欺骗、缓存投毒、解析路径劫持——本质上都是同一句话的不同玩法。

一句话抓住全章

DNS 诞生在一个「上网的人彼此都认识」的年代，所以它的设计基础是 互相信任。当互联网变成一个陌生人的世界，这个假设就成了漏洞本身。这一章的全部内容，就是这个假设崩塌之后发生的事，和补救它的一次尝试。

全章因果链：一根绳从「互相信任」串到「自带签名」

这一章看上去是「一堆攻击 + 一个协议」，实际上是一条链：每一环都在补上一环留下的洞，同时又留下新的洞，逼出下一环。下面这三段链，建议在复习任何一节之前都回来扫一眼。

起点
DNS 要做的事很简单：名字换地址。为了全球规模，它做成了层次结构 + 分布式数据库——根管顶级域，顶级域管二级域，一级只认识下一级。这套设计漂亮地解决了「规模」，但它没解决「真假」：协议里没有任何字段用来证明「这个回答确实来自有权回答的那台服务器」。
于是
为了把「请求」和「回答」配对，DNS 只好用一个 16 比特的事务 ID 当凭据。可 16 比特只有 65 536 种可能，而且报文全程明文——能监听就直接抄到，抄不到就猜。谁抢先把一个 ID 对得上的假回答送到，谁就赢。
留下的坑
骗一次还不算完：DNS 为了省流量会缓存结果，缓存时长由攻击者自己在假回答里填的 TTL 决定。于是「骗一次」变成了「骗很久，还传染给所有用这台解析器的人」→ 缓存投毒。
承上
既然问题出在「ID 太短、包是明文」，那就把猜的空间做大：随机化源端口，把 216 抬到约 232；再加上大小写随机化（0x20 编码）等技巧。
但是
这些全是「让猜变难」，不是「让骗不可能」。对于不需要猜的人——运营商的中间盒子、路由器上的劫持设备、公共 Wi-Fi 的转发器——它们就坐在你的解析路径上，能看到真实的 ID 和端口，随手就能改。清华段海新团队 2018 年的全球测量发现：中国近三成（27.9%）发往谷歌公共 DNS 的 UDP 流量被劫持。
逼出
只要「信任」还建立在「谁送来的」上，就永远防不住路径上的人。唯一的出路是让数据本身自带证据——不管它经过谁的手，我都能验它有没有被改过、是不是那个有权回答的人说的。这就是 DNSSEC。
承上
DNSSEC 的做法你在第 3 章已经学过：权威服务器用私钥给资源记录签名（存进 RRSIG 记录），解析器用它的公钥验签（公钥存在 DNSKEY 记录里）。验过就收，验不过就扔。
新问题
那公钥本身是真的吗？攻击者完全可以把公钥和签名一起伪造——两个都是他造的，自然对得上。所以必须有人来给公钥背书：子区的公钥散列值（DS 记录）交给父区，由父区签名。一层层往上，形成信任链。
还剩什么
① 链条要能一路走到根，中间断一环就成了「安全孤岛」；② 签名只保真不保密——报文照样明文，你查了什么域名，路上的人依旧看得一清二楚 → 这才有了 DoH / DoT；③ 报文变大、验证变慢，反而更容易被拿来做反射放大。

DNS 是什么，凭什么成了头号目标

老师用了整整 4 页讲「DNS 除了查地址还能干什么」，课本里这部分只有半页。这个篇幅差不是随手放的——课本简答题第 9 题「简述 DNS 除提供域名解析功能外还具有哪些功能」，标准答案就是这 4 页 PPT 的三条。

PPT 第 3–6 页 · 问题

DNS 不就是个「电话簿」吗？查一下地址而已，被攻破了顶多打不开网页——值得单开一章讲安全？

值得。因为现代互联网早就越过了「电话簿」这个定位，把一大堆本该由别人负责的判断压在了 DNS 上。老师这 4 页 PPT 就是在铺这件事：你信 DNS 的，远比你以为的多。

PPT 给的三条（p.3–6，逐条配了真实截图）
  • 应用层路由——DNS 决定你连到哪一台服务器（CDN 就近、邮件走 MX）
  • 信任的基础——邮件是不是伪造的、你是不是这个域名的主人，都靠查 DNS 判断
  • 公钥基础设施——哪家 CA 有权给这个域名发证书，写在 DNS 里

把这三条连起来看结论就很刺眼了：只要能改 DNS 的回答，就能同时改掉「你连到哪」「你信谁的邮件」「谁能给你发证书」三件事。这就是它成为头号攻击目标的原因，也是课本开篇说它是「最重要的基础设施」的含义。

1.1 最朴素的作用：把名字换成地址

定义 · 域名系统课本 p.230

域名系统（Domain Name System，DNS）是因特网上最为关键的基础设施，其主要作用是将易于记忆的主机名称映射为枯燥难记的 IP 地址，从而保障其他网络应用（如网页浏览、电子邮件等）顺利执行。

为什么非要有这么一层？课本给的理由很实在：人记不住数字。

  • IPv4 地址是 32 位二进制，写成点分十进制（203.0.113.10）也谈不上好记；
  • IPv6 更长，128 位（2001:db8::f00:baa9），基本没法背。

于是就有了分工：人用域名，机器用 IP，中间由 DNS 做翻译。这个翻译动作叫域名解析。

这里已经埋下了第一颗雷

「翻译」这个动作发生在你看不见的地方。你在地址栏看到的永远是 www.example.com，浏览器实际连的是哪个 IP，界面上不会告诉你。换句话说，DNS 被骗了，你在屏幕上看不出任何异常——这正是后面「恶意网址重定向」为什么如此有效的原因。

1.2 作用一：应用层路由PPT p.3–4

PPT 原文 · p.3

「应用层路由：DNS 把用户的访问指向离用户最近的那个 CDN 服务器节点，负载均衡；Email 服务器利用 DNS 服务器中的 MX 记录作为路由，找到企业内部真正的服务器。」

① CDN：同一个域名，不同的人得到不同的答案

你和地球另一端的人同时访问 www.example.com，拿到的 IP 地址很可能是不一样的。这不是出错，是设计——DNS 服务器会根据请求来源，把你指向物理上离你最近的那个缓存节点。

定义 · CDN 服务器PPT p.3 原文

CDN 服务器（Content Delivery Network Server，内容分发网络服务器）是构成 CDN（内容分发网络）的核心组件。它的主要作用是将网站、应用或流媒体等内容缓存并分发到离用户更近的地理位置，从而提升访问速度、降低延迟、减轻源站压力。

课本把这件事的性质点得很准：这相当于 DNS 实现了「应用层路由」。真正的路由是网络层的事（IP 包该往哪个下一跳走），但这里是在应用层就决定了你去访问哪台机器，顺带还实现了负载均衡——把用户分摊到不同节点上。

为什么这算「安全问题」

因为它意味着「同一个域名解析出不同 IP」是完全正常的现象。正常到什么程度？正常到你根本没法用「这次的 IP 和上次不一样」来判断自己是否被劫持了。攻击者的假回答，混在这种天然的多变性里，毫不显眼。

② MX 记录：邮件该投递到哪台服务器

发邮件到 somebody@example.com 时，发信方并不知道对方公司的邮件服务器是哪台机器。它去查 example.com 的 MX 记录（Mail eXchanger，邮件交换记录）：

PPT p.4 给的 MX 记录示例（原样）
example.com.   MX   10    mail1.example.com.
example.com.   MX   20    mail2.example.com.

中间那个数字（10、20）是优先级，数字越小越优先。所以发信方先试 mail1，连不上再退到 mail2。课本与 PPT 均未解释优先级含义，此处补充

攻击面

能改 MX 记录，就能把整个公司的来信全部收走——发信方会老老实实按你写的地址投递，因为对它来说这就是「查到的正确答案」。收件人甚至不会察觉丢了信。

1.3 作用二：DNS 作为信任的基础PPT p.4–6

PPT 原文 · p.4

「DNS 作为信任的基础：防伪造邮件、域名，作为验证证书申请者身份的信任基础。」

这一条是三条里最需要展开的。它其实包含两件独立的事：判断邮件是不是伪造的，和判断你是不是这个域名的主人。

① SPF：这封信是不是冒名发的

电子邮件协议（SMTP）有个古老的毛病：发件人地址是发信方自己填的，没人核对。你可以随手填 ceo@example.com 把信发出去。钓鱼邮件就是这么来的。

怎么办？让域名的主人自己声明「哪些服务器有权代表我发信」，声明就写在 DNS 里。这就是 SPF。

定义 · SPF 记录PPT p.4 原文

SPF 记录（Sender Policy Framework，发件人策略框架）是 DNS 中的一种 TXT 类型记录，用于声明哪些邮件服务器被授权代表某个域名发送电子邮件。其核心目的是防止垃圾邮件和钓鱼邮件中的「发件人地址伪造」（即邮件欺骗）。

PPT p.4 的流程图说的是什么

图上只有两台服务器和两句话：
① 发送方邮件服务器 →「我要发邮件给你」→ 接收方邮件服务器
② 接收方邮件服务器 → 回头去查 DNS →「查询 SPF 记录：这个地址可以发你这个域的邮件吗？」

关键在于第 ② 步的方向：接收方不是问发送方，而是去问「域名的 DNS 服务器」。因为发送方是可能撒谎的一方，去问它毫无意义。

PPT 第 5 页整页都是 SPF 的真实写法。这段语法课本里没有，逐字段拆一下：语法解释为自编补充

场景 1 · 只允许自己的邮件服务器发信PPT p.5
example.com.   TXT   "v=spf1 mx -all"
场景 2 · 使用第三方邮件服务（如企业邮箱）
example.com.   TXT   "v=spf1 include:spf.qq.com -all"
场景 3 · 混合（自建 + 第三方 + 指定 IP）
example.com.   TXT   "v=spf1 ip4:203.0.113.10 mx include:spf.sendgrid.net ~all"
写法含义
v=spf1版本号，固定开头，表示这是一条 SPF 记录
mx允许本域 MX 记录指向的那些服务器发信——省得再手写一遍 IP
ip4:203.0.113.10允许这个具体 IP 发信（ip6: 同理）
include:spf.qq.com把另一个域的 SPF 规则整段并进来。用第三方邮件服务时，对方 IP 会变，所以只能引用它的记录而不是抄 IP
-all硬失败：以上都不匹配就直接拒收。注意是减号
~all软失败：不匹配则标记为可疑但仍然收下（通常丢进垃圾箱）。刚部署、怕误杀时用它
SPF 语法速查。规则从左往右匹配，第一个命中的生效，所以 all 一定写在最后。

② 域名验证：证明「你是这个域名的主人」

申请一张 HTTPS 证书（第 4 章讲过的那种），CA 凭什么相信你就是 example.com 的主人？最常用的办法就是让你在 DNS 里放一条只有主人才放得进去的记录。

PPT p.6 那张截图展示的事实

截图上是一条真实的 DNS TXT 记录，内容形如：

DNS TXT Record:  _globalsign-domain-verification=WONkt7Og6t_p0WhGT9pHasZU8AN7oS4XvzYqZeBOu-

配图上两个箭头写着「申请证书」和「验证你是否拥有这个域名？」。整个流程是：你向 CA 申请证书 → CA 给你一串随机字符串 → 你把它写进自己域名的 TXT 记录 → CA 去查 DNS，查到了就认为你确实控制着这个域名，于是签发证书。

课本原文课本 p.230

「此外，在证书申请过程中，特别是 Domain Validation 证书，域名也是验证申请者身份的信任基础，例如，DNS 管理员在服务器中配置一个 CA 签发的签名记录来证明它是这个域合法的拥有者。」

推到底：这件事有多危险

如果攻击者能控制某个域名的 DNS 记录，他就能通过 CA 的域名验证，合法地申请到这个域名的真证书。拿到真证书之后再做中间人，浏览器连锁头都不会变色——因为证书是真的，链是通的。DNS 一失守，HTTPS 的整套信任体系跟着塌。这就是为什么下一条要专门讲 CAA。

1.4 作用三：DNS 作为公钥基础设施PPT p.6

PPT 原文 · p.6

「DNS 作为 PKI：防止 CA 在未经网站所有者授权的前提下签发非法的证书。」

第 4 章留下过一个没被彻底解决的问题：全世界有一百多家受浏览器信任的 CA，其中任何一家都能给任何域名签证书。只要有一家被攻破或者作恶，你的域名就可能被签出一张你并不知情的「合法」证书。

DNS 提供的解法很直接：让域名主人自己在 DNS 里写明「只有这几家 CA 有权给我发证」。这条记录叫 CAA。

定义 · CAA 记录PPT p.6 原文

CAA 记录（Certificate Authority Authorization，证书颁发机构授权）是一种特殊的 DNS 记录，它允许网站所有者通过 DNS 声明哪些 CA 有权为其域名签发 SSL/TLS 证书，从而防止未经授权的证书签发。

PPT p.6 给的 CAA 示例（原样）
example.com.  CAA  0 issue "letsencrypt.org"
example.com.  CAA  0 issue "digicert.com"
字段含义
0标志位。0 表示「非关键」——CA 若不认识后面的标签可以忽略；1 表示「关键」，不认识就必须拒绝签发
issue属性标签。issue = 授权签发普通证书；还有 issuewild（通配符证书）、iodef（发现违规时向哪里报告）
"letsencrypt.org"被授权的 CA 标识。上例表示只有 Let's Encrypt 和 DigiCert 两家可以给 example.com 发证，其余 CA 按规范必须拒绝
CAA 字段拆解。字段含义为自编补充，PPT 与课本均只给了示例
课本原文 · 更进一步：TLSA课本 p.230

「本章将要介绍的 DNSSEC 也可以起到公钥基础设施的作用。在 2012 年发布的 TLSA 标准（RFC 6698）之后，DNS 服务器可以作为一个信任的基础，证明网站所使用的 CA 或证书是否合法有效，防止 CA 在未经网站所有者授权的前提下签发非法的证书。」

CAA 和 TLSA 的区别（容易混）

CAA 是给CA 看的——CA 签发前先查一下 CAA，看看自己有没有资格。它靠的是 CA 的自觉。
TLSA（DANE）是给浏览器看的——域名主人直接在 DNS 里公布「我用的就是这张证书 / 这个公钥」，浏览器连上后自己核对。它不依赖任何 CA 的自觉，但前提是 DNS 本身可信，也就是必须先部署 DNSSEC。

这正好说明了一件事：DNS 想当 PKI，前提是 DNS 自己先得可信——第 8 节的 DNSSEC 就是干这个的。

考点 · 这一节直接对应一道简答题

2.1 域名的层次结构PPT p.8课本 p.231

问题

全世界几十亿个域名，凭什么保证不重名？又凭什么能在几十毫秒内查到？

答案是同一个：做成一棵树，并且把管理权按层切开。每一级只负责管好自己的下一级，谁也不需要知道全局。

课本原文课本 p.231

「因特网的域名采用的是层次结构的名字。域名的结构由若干个分量组成，各分量之间用英文小数点隔开：… . 三级域名 . 二级域名 . 顶级域名
各级域名由其上一级的域名管理机构管理，而最高的顶级域名则由因特网的有关机构管理。用这种方法可使每一个名字都是唯一的。」

  • 级别最低的写在最左边，最高的顶级域名写在最右边。所以 mail.tsinghua.edu.cn 里，cn 是顶级、edu 是二级、tsinghua 是三级、mail 是四级。
  • 每一级不超过 63 个字符，不区分大小写；完整域名不超过 255 个字符。
  • 域名系统不规定一个域名要包含多少个下级域名，也不规定每一级代表什么意思——那是各级管理机构自己的事。

上图为课本图 8-1「因特网的名字空间」的重绘简化版（PPT p.8 用的是同一张图的嵌入对象版本）。真实的树宽得多，这里只保留了能说明层级关系的枝条，蓝色高亮的是 mail.tsinghua.edu.cn 这条路径。

顶级域名 TLD 的三类课本 p.231

类别缩写说明
国家顶级域名nTLD采用 ISO 3166 规定，如 cn（中国）、us、uk。我国把二级域名分为「类别域名」（6 个：ac 科研、com 工商金融、edu 教育、gov 政府、net 互联网络中心/运行中心、org 非盈利）和「行政区域名」（34 个，如 bj 北京、sh 上海、js 江苏）

2.2 四类域名服务器PPT p.7

先说一个 PPT 与课本不一致的地方

课本 p.232 只列了三类：本地域名服务器、根域名服务器、权威域名服务器。
PPT p.7 列了四类，多出一个「顶级域名服务器」，并且把顺序改成了根 → 顶级 → 权威 → 本地（按查询经过的顺序，而不是按课本的重要性顺序）。

答题时按 PPT 的四类答更保险——顶级域名服务器在课本正文里其实也出现了（「根域名服务器通常用来管辖顶级域」），只是没单列成一条。

1
根域名服务器（root name server）

PPT p.7 原文：「13 个根域名服务器，上千个根服务器镜像。根 DNS 服务器是最高层级的 DNS 服务器，当客户端发起解析请求，如果本地服务器没有缓存记录，首先会询问根域名服务器，根服务器根据 .com、.org、.net 等，返回下一级顶级域名服务器的地址。」

课本补的关键一句课本 p.232：「根域名服务器并不直接对顶级域下面所属的所有域名进行转换，它主要负责找到下面的所有二级域名的域名服务器。」
——也就是说，根服务器不知道任何具体网站的 IP，它只知道「该去问谁」。

为什么只有 13 个？不是因为只有 13 台机器，而是因为 13 个「标识」（a 到 m，即 a.root-servers.net … m.root-servers.net）。受早期 UDP 报文 512 字节的限制，能塞进一个响应包里的根服务器地址就这么多。真实机器数远不止 13 台——靠 AnyCast 任播技术（RFC 3258，2002 年启用），同一个 IP 地址可以在全球几百个城市同时提供服务。2013 年根镜像达 346 个，到 2019 年 8 月全球已有一千多个镜像，中国大陆至少有 8 个。「为什么是 13」为自编补充
2
顶级域名服务器PPT p.7 独有

PPT 原文：「顶级域名服务器存储了所有顶级域名（如 .com、.org、.net 等）的 DNS 记录。本地域名服务器根据根服务器返回的 IP 地址，对顶级域名服务器发起请求，并获取权威服务器地址。」

PPT 特意加了个括号「（可能分顶级、二级等）」——提醒你现实中层数不固定，可能要多问几级。

3
权威域名服务器（authoritative name server）

PPT 原文：「对于一个特定的域名，必须交由某个 DNS 服务器进行解析，才能将域名与 IP 地址绑定，而这个负责最终解析域名的服务器就是权威解析服务器。当本地域名服务器完成全球迭代查询后，最后由权威域名服务器给出最终的解析结果。」

PPT 括号里那句很重要：「（主辅之分，主服务器能改记录，辅服务器只能从主服务器复制——DNS 区域传送）」。「区域传送」这四个字请记住，第 7 节讲「信息泄漏」时它是主角。

课本补充课本 p.233：一台主机最好至少有两台权威域名服务器（容错）；因特网允许各单位把本单位的域名划分为若干个域名服务器管辖区（zone，区），一般就在各管辖区中设置相应的权威域名服务器。

4
本地域名服务器（local name server）

PPT 原文：「当客户端对某个域名发起访问时，首先会请求到本地域名服务器，然后由本地域名服务器代替客户端从根域名服务器到顶级域名服务器再到权威解析服务器一级级查询，并将从权威解析服务器获取的结果告知客户端。」

课本补的两点课本 p.232：
① 每一个 ISP、一所大学、甚至一个系，都可以拥有一个本地域名服务器，也称默认域名服务器。它离用户较近，一般不超过几个路由器的距离。
② 有时用户直接使用的不是本地域名服务器，而是互联网上的公共域名服务器，如百度 180.76.76.76、腾讯 119.29.29.29、谷歌 8.8.8.8。

安全含义：本地域名服务器是唯一一台你会反复、长期、全部信任的 DNS 服务器。它的缓存被污染一次，所有用它的人一起中招——这就是缓存投毒的价值所在。而「用公共 DNS 更安全」这个直觉，会在第 5.5 节被解析路径劫持打破。
还有一个词：解析器（resolver）课本 p.234

「很多时候将用户直接使用的域名服务器称为域名解析器（domain name resolver）。解析器在用户和域名服务器之间起到桥梁的作用：接受用户的查询请求，向域名服务器查询具体地址，解析来自域名服务器的响应，然后再返回结果给用户。对于用户来说，解析器是服务器端；对于域名服务器而言，解析器又是客户端。」

后面 DNSSEC 一节里反复出现的「验证解析器（validating resolver）」，指的就是这个角色。

2.3 递归查询 vs 迭代查询PPT p.9–11课本 p.234–235

PPT 第 9 页 · 问题

查一个域名要问好几台服务器——那到底是「我一台台去问」，还是「我托一个人帮我全问完」？

两种都存在，而且在同一次查询里同时存在。这正是初学者最容易糊涂的地方：不是二选一，是前半段用一种、后半段用另一种。

PPT 原文 · p.9

递归查询：一般客户机和服务器之间属递归查询，即当客户机向 DNS 服务器发出请求后，若 DNS 服务器本身不能解析，则会向另外的 DNS 服务器发出查询请求，得到结果后转交给客户机。

迭代查询（反复查询）：一般 DNS 服务器之间属迭代查询，如：若 DNS2 不能响应 DNS1 的请求，则它会将 DNS3 的 IP 给 DNS1，以便其再向 DNS3 发出请求。

递归查询（recursive）
迭代查询（iterative）

「你帮我查到底」

我把问题整个交给你，你不查完不许回来。中间你问了谁、问了几次，与我无关。

发生在：客户机 ↔ 本地 DNS 服务器
负担：全压在被问的那一方

「我不知道，但我知道该问谁」

你问我，我答不上来，就给你一个线索（下一级服务器的地址），你自己再去问。

发生在：本地 DNS 服务器 ↔ 各级 DNS 服务器
负担：分摊，根服务器只需回一句「去问 .com」

为什么现实中不用「纯递归」PPT p.10 标题原话

PPT 第 10 页标题写的就是「递归查询（一般不用纯递归查询）」。原因看课本的算法就明白：纯递归时根域名服务器要替你一路问到底再把结果传回来，课本图 8-2 数得清清楚楚，总共要用 8 个 UDP 报文，而且负担全压在根服务器身上——全世界的查询都这么来，13 组根服务器立刻崩溃。

所以现实做法是递归 + 迭代结合：客户机对本地服务器用递归（省事），本地服务器对上面各级用迭代（分摊压力）。课本图 8-3 画的就是这个。

2.5 缓存与 TTL：效率的代价PPT p.14课本 p.235–236

PPT p.14 的标题只有两个字：「DNS 缓存」

配图是一张完整的 DNS 查询过程图，图上标出了三处缓存：DNS 解析器缓存、hosts 文件、DNS 服务器缓存。老师单开一页讲它，是因为缓存是接下来所有「投毒」类攻击的舞台。图为文字复述

课本把缓存的动机说得很清楚：「使用名字的高速缓存可优化查询的开销」。每台域名服务器都维护一个高速缓存，存放最近用过的映射。但这个优化是有代价的——课本用了一个很准的词：

课本原文 · 缓存的代价课本 p.237

「缓存的存在虽然减少了访问时间，却是以牺牲一致性（consistency）为代价的，同时也使得服务器发生缓存中毒的概率增大，极大削弱了 DNS 系统的可用性。」

A
代价一：数据可能是过时的

课本说得很直接：域名服务器向客户报告缓存中的绑定信息时，会标志为「非授权绑定」，并给出这条绑定是从哪台服务器 S 得来的。「因此，客户可很快收到回答，但有可能信息已是过时的了。」如果强调准确性，客户可以自己去联系权威域名服务器核实。

B
代价二：过期时间由「回答的人」说了算

每条记录都带一个 TTL（Time To Live，生存期），说明「这条记录可以缓存多久」。课本举例：「例如，每项目只存放两天」。

这半句就是投毒的杠杆。TTL 是写在应答报文里的，也就是说——谁伪造了应答，谁就顺便决定了这个假记录能在缓存里待多久。课本 p.237 原话：攻击者「伪造一个 DNS 回答，并含有一个长的缓存超时值」。
C
代价三：TTL 设长设短两头不讨好

课本 p.241 在讲「实现脆弱性」时专门列了这条：「如果超时值过大，当主机配置改变时，则不能立即完成更新。如果管理者立即重新定位主机，那么缓存服务器将指向错误的地址。」反过来，「增加此时间值可减少网络开销，而减少此时间值可提高域名转换的准确性」。这是一个纯粹的权衡，没有正确答案。

2.6 DNS 用 TCP 还是 UDPPPT p.12 · 整页只讲这一件事

PPT 第 12 页 · 问题

DNS 使用 TCP 还是 UDP？

老师把这个问题单独放了一整页。它看起来像个八股面试题，实际上是后面两个大攻击的技术前提——反射放大攻击靠的就是 UDP，而 DNSSEC 部署困难也和 512 字节限制直接相关。

普通查询 → UDP
区域传送 → TCP

PPT 原文：「客户端向 DNS 服务器查询域名，一般返回的内容都不超过 512 字节，用 UDP 传输即可。不用经过 TCP 三次握手，这样 DNS 服务器负载更低，响应更快。虽然从理论上说，客户端也可以指定向 DNS 服务器查询的时候使用 TCP，但事实上，很多 DNS 服务器进行配置的时候，仅支持 UDP 查询包，UDP 报文一般不大于 512 字节。」

理由：查一个域名就为了一个 IP，为这点数据握三次手不值。

PPT 原文：「辅域名服务器会定时（一般是 3 小时）向主域名服务器进行查询以便了解数据是否有变动。如有变动，则会执行一次区域传送，进行数据同步。区域传送将使用 TCP 而不是 UDP，因为数据同步传送的数据量比一个请求和应答的数据量要多得多。」

理由：整个区的记录一次性拷过去，量大且必须完整可靠。

这一页埋了三个后面要爆的雷
  1. UDP 无连接、不握手 → 源 IP 可以随便伪造，没人核对 → 反射式 DDoS 的前提（第 5.2 节，选择题第 10 题）
  2. 响应远大于请求 → 反射的同时还放大了流量 → 「四两拨千斤」
  3. 512 字节的天花板 → DNSSEC 的签名记录动辄上千字节，塞不下 → 必须先扩展协议（EDNS），这是 DNSSEC 部署慢的技术原因之一（第 8.10 节）

4.2 缓存投毒PPT p.17课本 p.237

PPT p.17 原文

「已经查询过的 DNS 解析条目会保存在计算机的 DNS 缓存列表中，再次查询时，会根据自己计算机上保存的缓存对应关系来解析，而不会去 DNS 服务器去解析。」

「攻击者观察 DNS 请求，并生成一个伪造的 DNS 回答，并含有一个长的缓存超时值，这样受损的 DNS 缓存可对任何数据请求提供假的数据。」

两句话，两个要害。第一句说明缓存会绕过真服务器，第二句说明缓存待多久由伪造者决定。合起来就是：骗一次，然后让被骗的人替你骗所有人，骗很久。

定义 · 缓存投毒课本 p.237

「缓存投毒是指攻击者将『污染』的缓存记录插入到正常的 DNS 服务器的缓存记录中，所谓『污染』的缓存记录指 DNS 解析服务器中域名所对应的 IP 地址不是真实的地址，而是由攻击者篡改的地址，这些地址通常对应着由攻击者控制的服务器。攻击者利用 DNS 协议中缓存机制中对附加区数据不做任何检查的漏洞，诱骗名字服务器缓存具有较大 TTL 的虚假资源记录从而达到长期欺骗客户端的目的。」

①隐蔽

第 ④ 条就是 DNSSEC 存在的理由

从这个角度看，第 8 节的 DNSSEC 不是凭空冒出来的一个新协议，而是本节这个「缺陷」的直接对偶。

「清华大学的郑晓峰等人在著名的 USENIX Security 2020 会议上发表的论文 Poison Over Troubled Forwarders 中提出了一种新的针对 DNS 转发设备的缓存污染攻击方法，可以对广泛部署的 DNS 转发服务（如家用 Wi-Fi 路由器、公共 Wi-Fi 等场景）实施缓存污染攻击，D-Link、Linksys、微软 DNS、开源软件 Dnsmasq 等多个知名品牌的产品或系统可能受到该攻击的影响。」

值得留意的是攻击目标的下沉：从运营商的大解析器，一路下沉到你家客厅那个路由器。因为那台设备也在做 DNS 转发和缓存，而它的软件通常又旧又不更新。

5.1 ID 盲目攻击PPT p.18

PPT p.18 原文

「攻击者选择一个公用的域名，生成 DNS 回答的泛滥，每个回答包含一个不同的会话标识。」

「盲目」两个字是相对上一节的「监听」说的：攻击者看不到真实的 ID，所以他把所有可能的 ID 全发一遍——反正只要有一个撞对就赢。这是典型的用带宽换概率。

PPT p.18 那张图，五个圈讲完了全过程图为文字复述

图上有四个主体：攻击者询问、DNS 缓存、基本的 DNS（真服务器）、攻击者。五个带圈数字是：

  1. 攻击者询问 → DNS 缓存：「谁是主机？」
    攻击者自己去触发这次查询——不用守株待兔等别人来查
  2. DNS 缓存 → 基本的 DNS：「谁是主机？ID = 768」
    缓存里没有，只好向外问，此时生成了一个真实的 ID（攻击者看不到它）
  3. 攻击者 → DNS 缓存：一大把箭头，「主机是 9.9.9.9，ID = 0…65535」
    这就是「泛滥」：同一个答案配上所有可能的 ID，全部砸过去
  4. DNS 缓存 → 攻击者询问：「主机是 9.9.9.9」
    攻击者再查一次，验收成果——返回了假地址，说明投毒成功
  5. 基本的 DNS → DNS 缓存：「主机是 1.2.3.4，ID = 768」
    真答案最后才到，被当作重复报文丢弃

请注意第 ① 步和第 ④ 步：攻击者既是发起者也是验收者。这说明整场攻击完全由攻击者掌握节奏，不需要等待任何受害者的行为——他想什么时候打就什么时候打。

课本在别处补了它的升级版：生日悖论课本 p.241

「Sacramento 还发现 BIND 4.x 和 8.x 两个系列会允许客户向同一 IP 地址同时发送多个递归查询请求，由此衍生出一种称为生日悖论（Birthday Paradox）的攻击方法，这种攻击方法增加了成功猜测到正确的事务 ID 的可能性，受到广泛的关注。」

道理和「一屋子人里有两个同天生日」一样：解析器同时发出 M 个查询、攻击者发 N 个伪造应答，只要任意一对撞上就成功，命中率远高于 M×N/65536 的直觉估计。→ 上一节的实验台第三档就是算它的

5.2 拿 DNS 当反射放大器PPT p.19课本 p.238

PPT 第 19 页 · 换个思路的问题

前面都是「攻击 DNS」。有没有可能反过来——不打 DNS，而是拿 DNS 当枪去打别人？

有，而且效果好得离谱。课本把针对 DNS 的拒绝服务攻击分成泾渭分明的两类，这个分法必须记住：

课本原文（p.238）

「针对 DNS 的拒绝服务攻击通常有两种方式：一种是攻击 DNS 系统本身（包括对名字服务器和客户端进行攻击），另一种是利用 DNS 系统作为反射点来攻击其他目标。」

第一类：打 DNS 自己

打客户端

课本：「主要通过发送否定回答显示域名不存在，从而制造黑洞效应，对客户端造成事实上的 DoS 攻击。」

不用打垮任何机器——只要一直告诉你「这个网站不存在」，对你来说它就是不存在。

打服务器

课本：「直接以域名服务器为攻击目标。」

课本给了两个真实事件：
· 2009 年 5 月 19 日，江苏、安徽、广西、海南、甘肃、浙江六省区电信互联网络瘫痪——起因是攻击者对智能域名解析服务器 DNSpod 实施 DDoS
· 2016 年 10 月 21 日，攻击者对美国域名解析服务提供商 Dyn 的域名服务器发动 DDoS，导致美国东部大规模互联网瘫痪

一个值得记的数字课本 p.238

据中国互联网应急响应中心 2018 年度报告：2018 年有 77% 的组织至少经历过一次基于 DNS 的网络攻击，23% 的 DNS 网络攻击会对目标组织的声誉产生明显影响。

第二类：拿 DNS 反射，去打别人

PPT p.19 原文 · 把机制说得最清楚的一段

「假设攻击者已知被攻击机器的 IP 地址，然后攻击者使用该地址作为发送解析命令的源地址。这样当使用 DNS 服务器递归查询后，DNS 服务器响应给最初用户，而这个用户正是被攻击者。那么如果攻击者控制了足够多的肉鸡，反复地进行如上操作，那么被攻击者就会受到来自于 DNS 服务器的响应信息 DDoS 攻击。」

1
伪造源地址 —— 这一步之所以可行，全因为用的是 UDP

回看第 2.6 节：UDP 无连接、不握手。攻击者在 IP 头的源地址字段填上受害者的 IP，没有任何人会去核对这个地址是不是真的。
如果 DNS 用的是 TCP，三次握手就会立刻拆穿这个谎——因为握手要求「你得能收到我发回去的包」。

2
反射 —— 服务器老老实实把答案「还」给受害者

DNS 服务器完全无辜：它收到一个查询，按规矩把答案发回源地址。它成了「枪」，而且它自己毫不知情。
好处是：受害者看到的攻击流量来自成千上万台正常的 DNS 服务器，封谁都不对——封了就等于把自己和整个互联网的 DNS 断开。

3
放大 —— 「四两拨千斤」

课本原文：「针对 DNS 的攻击通常利用普通查询过程中 DNS 响应报文尺寸远大于请求报文尺寸，以及区域传送或递归查询过程中 DNS 响应报文数量远大于请求报文数量等特点来放大攻击流量，从而产生『四两拨千斤』的效果。」

课本特别提到 512 字节这个数：「查询报文通常很小，而响应报文在采用 UDP 传输情况下最大可达 512 字节，因而能够产生放大式的攻击效果，并且超过 512 字节的报文又采用 TCP 传输，更增加了 DDoS 攻击成功的概率。」
真实案例：2016 年里约奥运会期间，攻击者利用 DNS 及其他协议，针对巴西政府发动了峰值为 540 Gbps 的 DDoS 攻击。
PPT p.19 那张图的流水号图为文字复述

图上有八个编号的箭头：0 攻击者 → 肉鸡群（下发指令）；1 肉鸡群 → 本地 DNS（一大把红箭头，伪造源地址为被害者）；2、3 本地 DNS ↔ 根服务器；4、5 本地 DNS ↔ 顶级域名服务器；6、7 本地 DNS ↔ 目标域的主 DNS 服务器；8 本地 DNS → 被害者（一大把蓝箭头）。

看编号 1 和 8 的箭头粗细对比就够了：1 是攻击者付出的成本，8 是受害者承受的流量。中间的 2–7 是 DNS 系统自己在忙活——攻击者连查询都不用自己完成，递归查询的活儿有人替他干。

5.3 恶意网址重定向与中间人攻击PPT p.20课本 p.238

课本原文课本 p.238

「在恶意网址重定向和中间人攻击过程中，攻击者通常伪装成客户可信任的实体对通信过程进行分析和篡改，将客户请求重定向到假冒的网站等与请求不符的目的地址，从而窃取客户的账户和密码等机密信息，进行金融欺诈和电子盗窃等网络犯罪活动。」

技术上，它就是前面几种欺骗的「变现环节」：投毒也好、劫持也好，最后总要把用户送到一个攻击者控制的服务器上，才能收割账号密码。

课本点出的一类特殊中间人：中间盒子课本 p.238

「互联网中存在大量称为『中间盒子（Middlebox）』的中间人，这些中间盒子中有些为了各种利益经常会劫持用户的域名解析过程。」

「为了各种利益」这五个字很关键。这类劫持者往往不是黑客，而是网络上的合法设备——运营商的流量管控设备、企业代理、家用路由器、反病毒软件、防火墙。它们坐在路径上是合规的，这就让防御变得非常尴尬。5.5 节会给出这件事的实测数据。

5.4 DNS 域名劫持PPT p.21

PPT p.21 原文

「是指在一定的网络范围内拦截域名解析的请求，返回假的 IP 地址或者什么都不做使请求失去响应，其效果就是对特定的网络不能反应或访问的是假的对攻击者有利的网址。所以域名劫持通常相伴的措施——封锁正常 DNS 的 IP。」

最后那半句是全段的重点

「封锁正常 DNS 的 IP」——为什么劫持还要额外封锁？
因为只要用户还能连上真正的 DNS 服务器，他就有机会拿到正确答案。上一节讲过，DNS 的接收策略是「认第一个」，劫持者不能保证每次都跑赢。与其比谁快，不如让对手根本上不了场。

这和 4.1 节里「对真服务器发 DoS」是同一个思路的两种力度：一个是拖慢，一个是直接掐断。

课本列出的四项安全风险课本 p.240

1道德与隐私风险

「劫持者很可能在未征得用户同意的情况下，篡改用户的 DNS 访问，不仅带来了道德问题，而且给用户的隐私带来了风险。」

2网络故障

「劫持者的行为使得用户的网络链路更加复杂，当出现故障时难以排除。」——你 ping 得通、DNS 也能解析，但就是有些站点不对劲。

3DNS 功能特性缺失

「替代 DNS 服务器可能缺乏 DNS 的某些功能特性，例如，根据终端子网返回最优的 IP 地址的选项（EDNS Client Subnet, ECS）。」——CDN 的就近调度会失效，网速反而变慢。

4服务器本身不安全

「劫持者所使用的替代 DNS 服务器往往不遵守最佳安全实践。」实测：仅 43% 接受 DNSSEC 请求，且所有使用 BIND 的替代服务器版本全部低于 BIND 9.4.0，早在 2009 年就该过期了。

第 4 项才是最该记住的

劫持者把你的流量抢过去，用的却是一台十几年没更新的服务器。也就是说——即使他毫无恶意（只想省钱），他也已经把你的安全水位拉到了他那台老机器的水平。

「43% 才接受 DNSSEC」这个数字还有一层含义：就算你的域名认真部署了 DNSSEC，只要用户被劫持到这类服务器上，验证根本不会发生。第 8 节讲「安全孤岛」时，这个问题会再次出现。

本节结论
只要「信任」建立在「这个包是谁送来的」上，就永远防不住坐在路径上的人——他不用猜，他就是路。
而且
这些劫持者多半不是黑客，是合法运营的网络设备。你没法「封掉」它们，也没法要求它们别这么干。
唯一出路
让数据自己带上证据：不管经过谁的手，我都能验它有没有被改、是不是有权回答的人说的。这就是第 8 节的 DNSSEC。在那之前，先用两节把课本树上剩下的两个抽屉清掉。
第 6 节 · PPT p.24

实现脆弱性：协议没错，是代码写错了

前两节讲的毛病，换谁来实现都躲不掉，因为病在协议设计里。这一节的毛病换个软件就没了——它们是程序员写错的。区分这两者，是这一章分类树的核心。

课本对这一类的定性课本 p.240

「历史上关于计算机或者计算机网络的很多著名安全问题不是由于算法或是协议缺陷造成，而是由编码实现错误引起的，通常是在编码阶段由于安全编码水平不高以及程序测试不全面导致在某种特定条件下程序执行出现异常和错误，从而引发灾难性后果。」

PPT p.24 列的四条

1
BIND 的漏洞

PPT 原文（与课本一致）：「DNS 软件——BIND 的漏洞和缺陷无疑会给 DNS 系统带来严重的威胁，其缓冲区溢出漏洞一度占据 UNIX 及 Linux 操作系统相关安全隐患的首位。」

BIND 是最广泛使用的 DNS 服务器软件。它有多普及，它的漏洞就有多严重——这是「单一实现垄断」的典型代价。

2
破坏 DNS 分组

PPT 原文：「DNS 协议规定了查询和回答的数据大小。但某些 DNS 实施没有适当的检查数据边界。分组可声称包含比实际更多的数据，或者没有包含足够的数据。其结果是缓冲器溢出或不足。」

这句话拆开就是缓冲区溢出的标准剧本：报文头里有个长度字段说「后面有 500 字节」，程序就照 500 字节去读/去拷——但实际只来了 20 字节，或者来了 5000 字节。程序不核对，内存就被写坏了。协议本身规定了大小，是实现没去检查——这就是它被归入「实现脆弱性」的原因。
3
攻击 DNS 服务器

PPT 原文：「被攻击的 DNS 服务器被增加、修改、删除 DNS 记录条目。」

也就是直接攻进服务器改数据。这一条最容易被忽略，但它说明了一件重要的事：DNSSEC 保护的是「数据在传输途中不被改」，保护不了「服务器自己被攻陷、区文件被改」——攻陷之后攻击者拿着私钥，签出来的假记录一样能验证通过。→ 见 8.9

4
更新持续时间（TTL 设置不当）

PPT 原文：「缓存 DNS 服务器同每个 DNS 项的超时相关联，超时防止数据失效。如果超时值过大，当主机配置改变时，则不能立即完成更新。如果管理者立即重新定位主机，那么缓存服务器将指向错误的地址。」

这条和第 2.5 节讲的 TTL 权衡是同一件事，只是站在「运维事故」而不是「攻击」的角度看。

第 7 节 · PPT p.25

操作脆弱性：技术全对，是人错了

这一节里没有一行代码有问题，也没有一个协议字段被误用。攻击者甚至不需要「攻击」——他只是注册了一个长得像的域名，或者等你的域名忘了续费。

课本对这一类的定性课本 p.241PPT p.25 同

「DNS 最初设计时主要考虑的是物理设备故障，并没有考虑由于人为操作或配置错误所带来的安全隐患。由于缺乏有效的配置管理工具，使得 DNS 上存在大量的配置错误（如无用授权、循环依赖和冗余降低等），给整个域名空间带来极大的安全威胁。针对操作脆弱性的安全威胁主要包括域名配置攻击、域名注册攻击和信息泄漏等。」

PPT p.25 列的四种手法

1相似的主机名

PPT 原文：「正常域名为 bankofexample.com.cn，攻击者拥有与之相似的域名 bonkofexample.com.cn，当用户错误地输入了该相似的主机名，就访问了伪装站点。」

看清楚差别了吗？第二个字母 a → o。已改示例域名
PPT 原例用的是某银行的真实域名，本页按隐私惯例换成了示例域名，字母替换的位置一字未改。

2自动名字实现

PPT 原文：「很多浏览器支持自动名字实现，即用户不输入域名服务器的高级域名（.com）而只输入主机名的中间部分，自动名字实现可附加一个后缀，直到找到主机名，通常先试的是 .com，如果 Web 站点不是以 .com 结尾，那么攻击者可以注册 .com 的名字来拦截这个域。」

你的站点是 example.org，用户只敲了 example，浏览器自动补成 example.com——而那个域名是攻击者注册的。

3社会工程

PPT 原文：「说服注册机构，更改域名。」

一句话，但这是最难防的一种——攻击面是「人」，而人没有补丁。课本补充：攻击者「通过冒充原域名所有者以电子邮件等方式向域名注册管理公司提出请求修改注册域名记录，将域名重定向到另一组织或站点」。

4域更新（域名过期）

PPT 原文：「欠费没更新，导致原有域名被他人注册。」

课本说得更细：攻击者「利用域名注册时限，利用原域名所有者忽略域名时限的空隙，购买刚到期的域名占为己有」。这里没有任何技术攻击，只是有人比你更留意日历。

课本的三分法：配置 / 注册 / 泄漏课本 p.241–242

PPT 的四种手法，在课本里被归进三个类别（这三个类别就是图 8-4 树上的三个方框，答题按这个分）：

A
域名配置攻击 —— 分「无意」和「有意」两种

无意攻击（误配置）：课本举的例子非常具体——「将 DNS 空间防火墙等报文过滤软件配置成只允许查询报文发送而不允许应答报文返回。这给 DNS 带来极大问题，因为名字服务器持续发送查询报文而没有意识到这样的配置使其无法接收到任何应答报文。」

有意攻击：「利用 DNS 协议配置的随意性弱点来实施攻击。这种攻击方法的典型代表是对 DNS 通配符（wildcard）的滥用，攻击者通常利用通配符条目来混淆其要真正攻击的目的主机，垃圾邮件也会利用这点向主机名嵌入跟踪信息来验证真实的邮件账号，从而避开反垃圾邮件系统的检测。」

通配符是什么：*.example.com 这样一条记录能把所有没单独配置过的子域名一网打尽——abc.example.com、xyz.example.com 全部解析到同一个地址。方便，但也意味着攻击者可以用无穷多个子域名来发信、来打点，而每一个看起来都是「合法解析出来的」。
顺带一提：通配符和 DNSSEC 的关系很微妙——第 8.3 节会讲 DNSSEC 专门用 NSEC 记录来防止「通配符被错误地扩展」。通配符解释为自编补充
B
域名注册攻击 —— 域名劫持 + 类似域名注册

域名劫持（domain hijacking）：「对域名注册管理公司的注册域名记录非法改变，使之指向其他 Web 站点。」手法就是 PPT 的第 ③ ④ 条：冒充所有者发邮件，或者抢注刚过期的域名。

类似域名注册：「利用用户习惯性错误拼写、字母相似性和替换顶级域名后缀等方式来注册与银行、知名企业的域名相类似的域名，从而达到欺骗客户和窃取机密信息等目的。」

课本对危害的评价很重：「这种攻击属于非法盗取电子财产，造成的损失是巨大而持久的。」
「持久」二字值得琢磨：域名一旦被抢走，你原来印在所有名片、广告、文档上的地址，从此都在替对方引流。
C
信息泄漏 —— 主角是「区域传送」

第 2.2 和 2.6 节埋的伏笔在这里兑现。课本：

「信息泄漏通常发生在区域传送过程中。大多数 DNS 系统的运行至少需要两台 DNS 服务器：一台主服务器和一台用来容错的辅助服务器。DNS 服务器之间通过拷贝数据库文件来进行同步，这一过程称为『区域传送（zone transfer）』。辅名字服务器既可以从主名字服务器装载区数据文件，也可以从其他辅名字服务器装载。」

「在传送过程中，内部网络拓扑、主机名和操作系统等信息有可能会暴露，并从这些信息中判断其功能或发现其他具有漏洞的其他主机，从而使得进一步攻击成为可能。」

为什么这是「一整个区」的问题：区域传送传的不是一条记录，是整个区文件——这个域下面所有主机的名字和地址，一次性打包。如果服务器没有限制「谁可以发起区域传送」，攻击者只要伪装成辅助服务器请求一次，就拿到了这个组织完整的内网地图：哪台是邮件服务器、哪台是数据库、哪台叫 test-old（多半没打补丁）。
这是渗透测试里最经典的第一步侦察动作。攻击价值分析为自编补充
课本在信息泄漏之后还补了三句「可用性」问题课本 p.242
  • 「动态更新不及时或发生中断也会降低 DNS 系统的可用性。」
  • 「主从服务器之间数据更新缺乏连贯性，客户可能从一些服务器得到陈旧数据，从而导致非故意性攻击。」——注意这个词，没有攻击者，效果却和被攻击一样。
  • 「在更新过程中，如果主名字服务器崩溃，一些更新数据就会永久丢失。对 DNS 服务器的错误配置也将大大降低 DNS 的可用性。」
三个抽屉清完了
协议脆弱性（第 4、5 节）：协议设计得就有问题，谁实现都躲不掉。实现脆弱性（第 6 节）：换个软件、打个补丁就好了。操作脆弱性（第 7 节）：技术全对，是人和流程的问题。
关键区分
后两类都有明确的解法——写好代码、定好流程、加强管理。只有第一类没有：只要 DNS 还是那个「没有认证机制的明文协议」，域名欺骗和路径劫持就永远治不好。
于是
要从根上解决，只能改协议——给数据加上密码学证据。这就是第 8 节，DNSSEC。
第 8 节 · PPT p.26–28 + 课本 8.3（p.242–264）· 全章重点

DNSSEC：让数据自己带上证据

PPT 在这里只有 2 页正文，但它是内容提纲的两大块之一，而且课本 10 道选择题里有 6 道考这一节的细节。所以本节按课本补足到考试需要的深度——不过顺序仍然照 PPT 的思路走：先讲它补哪个洞，再讲怎么补。

8.1 它到底在补哪个洞PPT p.27

PPT p.27 原文 · 一句话说清动机

「域名欺骗、恶意网址重定向和中间人攻击之所以能够成功，是因为 DNS 解析的请求者无法验证它所收到的应答信息的真实性和完整性。为应对上述安全威胁，IETF 提出了 DNS 安全扩展协议（DNSSEC）。」

把这句话拆成两半，就是 DNSSEC 全部设计的出发点：

真真实性（来源）

这条记录是不是那个有权回答的人说的？——现在完全没法判断，谁先送到就信谁。

整完整性

这条记录在路上有没有被人改过？——现在完全没法判断，报文里没有任何校验凭据。

DNSSEC 的三项功能（必背）课本 p.243
  1. 提供数据来源验证：DNS 数据来自正确的域名服务器。
  2. 提供数据完整性验证：数据在传输过程中没有任何更改。
  3. 提供否定存在验证：对否定应答报文提供验证信息。

第 3 条最容易被漏掉，却最容易考。它说的是：连「这个域名不存在」这句话也得能验证——否则攻击者只要一直回答「不存在」，就能让你上不了任何网站（第 5.2 节的「黑洞效应」）。这一条正是 NSEC 记录存在的理由。

一段值得读的历史：为什么它拖了这么久课本 p.242–243

「尽管 DNSSEC 的原理比较简单，但其标准的制定和部署面临着巨大的挑战。」课本引了域名软件之父 Paul Vixie 的两段话，很有意思：

1995 年 6 月：「DNSSEC 看似简单，但是对协议和实现影响很大，所以在选择安全模型和设计方案上用了一年时间。我们估计还要一年时间 DNSSEC 才能用在前沿领域。之后，至少再用一年时间才能用在一般的地方。」

2002 年 11 月（七年后）：「我们现在还在做基础的研究工作：究竟哪种数据模型对 DNS 安全可以工作……我们终于搞定了，这次是真的！我已经这么说三四次了……RFC 2535 标准已死，我们从头开始！」

时间线：1997 年 RFC 2065（第一个标准）→ 1999 年 RFC 2535（修订，「很快被证明这次修订是失败的」）→ 2005 年 RFC 4033-4035（终于可用，目前主流软件如 BIND 实现的就是这一版）→ 2008 年 RFC 5155（NSEC3）→ 2012 年 RFC 6698（DANE/TLSA）。
从提出到可用，走了整整十年。

8.2 基本思想：签名与验签PPT p.28

PPT p.28 原文 · 全章最该背下来的一段

「DNSSEC 基本思想：依赖于数字签名和公钥系统去保护 DNS 数据的可信性和完整性：权威域名服务器用自身的私钥来签名资源记录，然后解析服务器用权威域名服务器的公钥来认证来自权威域名服务器的数据，如果认证成功，则表明接收到的数据确实来自权威域名服务器，则解析服务器接收数据；如果认证失败，则表明接收到的数据很可能是伪造的，则解析服务器抛弃数据。」

1
「用自身的私钥来签名资源记录」

这就是第 3 章的数字签名，一字不差地搬过来用。签名的对象是资源记录集合（RRset），签出来的东西另外存成一条新记录，叫 RRSIG。

关键：签名是离线预先做好的，不是每次查询临时算——课本原话「这一过程是离线进行的」。为什么？因为私钥要保护好，不能天天挂在网上；而且签名是慢操作，每次查询都签会拖垮服务器。

2
「解析服务器用权威域名服务器的公钥来认证」

课本 p.243 把这一步写得更细：「收到应答报文的客户端或解析器可以利用服务器的公钥和加密算法对收到的 RR 进行加密运算，得到一个计算出来的 RRSIG，并将其与所收到报文中的 RRSIG 进行比对，如果二者相同，则通过了对签名者的认证并验证了数据的完整性，即应答报文中 RR 是真的，否则就说明收到的 RR 是假的。」

公钥怎么给？存成另一条新记录，叫 DNSKEY，跟着应答一起发过来。
但这里立刻冒出一个致命问题——课本自己马上就问了：「上述过程中，解析服务器如何保证它所获得的公开密钥（DNSKEY 记录）是真实的而不是假冒的呢？尽管 DNS 服务器在返回 DNSKEY 记录的同时，也返回对这个公钥的数字签名（与 RR 同名的 RRSIG 记录）。但是，攻击者同样可以同时伪造公开密钥和数字签名两个记录而不被解析者发现。」
这个问题的答案就是 8.5 节的信任链。
3
「如果认证失败……则解析服务器抛弃数据」

请注意这个选择：不是「标记为可疑」，不是「警告后仍然放行」，而是直接扔掉，让解析失败。

用户体验上这很糟糕——网页打不开，而且看不出为什么。但从安全角度这是唯一正确的选择：宁可给你「打不开」，也不给你一个假地址。

对比一下浏览器遇到证书错误时的做法（弹个警告，让你点「继续访问」），你会发现 DNSSEC 的立场硬得多——因为它下面根本没有「用户」可以问，解析器是在后台默默工作的。

8.3 四种新的资源记录课本 p.243–252PPT 只点名 DNSSEC，未讲字段

DNSSEC 没有改动 DNS 的报文格式（那样会破坏兼容），而是新增了四种资源记录类型。这四种记录属于 DNSSEC，不属于原始 DNS——这就是选择题第 1 题的考点。

记录全称装什么一句话作用
DNSKEYDNS Public Key服务器的公开密钥「这是我的公钥」——验签要用它
RRSIGResource Record Signature对资源记录集合的数字签名「这段数据是我签的」——证据本体
NSECNext Secure排序后的下一个记录名 + 本名下所有 RR 类型「这中间真的什么都没有」——证明不存在
DSDelegation Signer子区 DNSKEY 的散列值「我儿子的公钥应该长这样」——存在父区，接起信任链
四种记录的详细说明可参考 RFC 4034（课本写作 RFC 3034，系笔误；DNSSEC 现行记录定义在 RFC 4034）。

① DNSKEY —— 公钥放在哪课本 p.244

标志 Flags（16 bit）
第 7 位（左起第 0 位）是区密钥标志 ZK（Zone Key）。ZK 置 1 表明它是一个区密钥，可用于签名数据的验证，而且资源记录的所有者必须是区的名字。

课本特别说明：这个标志「仅仅给区签名或调试软件一个提示，即使 SEP 位置 1，验证者在签名验证过程中也不必变更它们的行为」。并且「一条 DNSKEY RR 中如果 SEP 位置 1，则 ZK 位也应置 1，以便能够合法地产生签名」。
比特 0~6 和 8~14 是保留比特，创建时必须置 0，处理时必须忽略。
协议 Protocol（8 bit）
值必须是 3。「这是为了与以前版本 DNSSEC 兼容而保留下来的。该字段其他的值不能用于 DNSSEC 签名的验证。」

③ NSEC —— 怎么证明「不存在」课本 p.248–249

问题

「www.test.net 不存在」——这句话怎么签名？总不能把全世界不存在的域名都提前签一遍吧。

这正是课本提出的难题，而且它把两条死路都堵死了：

课本原文（p.248）

「为了保证私有密钥的安全性和服务器的性能，所有的签名记录都是事先（甚至离线）生成的。
服务器显然不能为所有不存在的记录事先生成一个公共的『不存在』的签名记录，因为这一记录可以被重放（replay）；
更不可能为每一个不存在的记录生成独立的签名，因为它不知道用户将会请求怎样的记录。」

两条路的问题各不相同：通用回答会被录下来到处重放（拿去否认任何一个真实存在的域名）；逐个签名则要求预知未来。DNSSEC 的解法很妙：不签「X 不存在」，而是签「排序后，A 和 B 之间什么都没有」。

NSEC 记录装的两样东西课本 p.249

「NSEC 记录包括两项内容：排序后的下一个资源记录的名称（xyz.test.net.）以及它的所有者所拥有的资源记录类型（A、RRSIG、NSEC）。这个特殊的资源记录类型会和它自身的签名一起被发送到查询的发起者。」

课本 p.249 的例子（原样）· 区数据签名时 NSEC 记录会自动生成
vpn.test.net.  10800 IN A  192.168.1.100
    172800 NSEC  xyz.test.net.  A RRSIG NSEC
    172800 RRSIG NSEC 5 5 172800 20110611031416 (
      20110512031416 5271 test.net. Ujw/aq….15dV5tF7XgWSR78= )
xyz.test.net.  10800 IN A  192.168.1.200
怎么用：课本原话——「当用户请求的某个域名在 vpn 和 xyz 之间时，如 www.test.net，服务器会返回域名不存在，并同时包括 vpn.test.net. 的 NSEC 记录。」

这条 NSEC 说的是：「排序后，vpn 的下一个是 xyz。」而 www 排在 vpn 和 xyz 之间——既然 vpn 的下一个直接就是 xyz，中间就不可能有 www。而且这句话是签过名的（后面那条 RRSIG NSEC），改不了、伪造不了。
为什么这个设计能防重放

因为每条 NSEC 只否定一个特定的区间。攻击者录下「vpn → xyz 之间为空」这条记录，拿它去否认 abc.test.net 是没用的——abc 不在这个区间里，验证方一眼看穿。

这就是「签一个通用的『不存在』会被重放」那句话的对照面：把否定说得越具体，可被滥用的范围就越小。此对照为自编补充

顺带解决了通配符的一个隐患课本 p.249

「为了保护资源记录中的通配符不被错误地扩展，DNSSEC 会对比已验证的通配符记录和 NSEC 记录，从而来验证域名服务器在生成应答时的通配符扩展是正确的。」

——回看第 7 节「域名配置攻击」里讲的通配符滥用：NSEC 加上 RRSIG 的 Labels 字段，正是用来判断「这个应答是不是通配符合成出来的」。

8.4 为什么要两对密钥：ZSK 与 KSK课本 p.245–246

问题

一对公私钥不就够签名了吗？为什么课本说「权威域的管理员通常用两对密钥配合完成对区数据的签名」？

ZSK · 区签名密钥（Zone Signing Key）
KSK · 密钥签名密钥（Key Signing Key）

签什么：「对区内的 DNS 资源记录进行签名。」——A、MX、NS、NSEC……除 DNSKEY 之外的所有记录。

怎么用：「权威认证服务器在每次 DNS 查询的时候，都会使用 ZSK 对查询结果（资源记录）进行数字签名，并将数字签名放在 RRSIG 记录中。」

公钥在哪：「ZSK 可以通过 DNSKEY 记录获取。」标志字段 256。

签什么：「用来对包含密钥（如 ZSK）的资源记录（DNSKEY）进行签名，并将签名结果放在 DNSKEY 的 RRSIG 记录中。」

为什么要它：课本一句话点题——「为了防止 ZSK 被修改」。

公钥在哪：也在 DNSKEY 记录里（标志 257），而它的散列值要交给父区，存成 DS 记录。

一句话记住分工课本 p.245

「在 DNSKEY 记录中，会同时包含 ZSK 和 KSK。所以，在一个区（zone）中，除 DNSKEY 记录外，其他的记录均由 ZSK 签名。」

换句话说：KSK 只干一件事——签 DNSKEY 记录本身。别的什么都不签。

使用两对密钥的好处课本 p.246 · 原文两条

1KSK：签得少，可以长期用

「用 KSK 密钥签名的数据量很少，被破解（即找出对应的私钥）概率很小，因此可以设置很长的生存期。这个密钥的散列值作为 DS 记录存储在上一级域名服务器中，并且需要上级域名服务器的数字签名。较长的生命周期可以减少密钥更新的工作量。」

2ZSK：签得多，换起来方便

「ZSK 签名的数据量比较大，因而被破解的概率较大，生存期应该小一些。因为有了 KSK 的存在，ZSK 可以不必放到上一级的域名服务中，更新 ZSK 不会带来太大的管理开销（无须和上级域名服务器进行交互）。」

这个设计的本质：把「常换的」和「难换的」分开

换 ZSK：自己在本区里换掉，重新签一遍，完事。
换 KSK：得通知父区更新 DS 记录——要走管理流程、要等对方生效，慢且容易出错。

所以：让「需要经常换的那把」不牵扯外部（ZSK），让「牵扯外部的那把」尽量不用换（KSK）。

课本 p.263 提到，2018 年 2 月 ICANN 发布了根 KSK 轮转计划，同年 10 月 15 日宣布首轮根区 KSK 轮转圆满完成——换一次根 KSK 是全球性的工程，前后筹备了好几年，正是「牵扯外部就难换」的极端例子。

8.5 信任链与信任锚课本 p.243、245–246

课本自己提出的问题 · p.243

「解析服务器如何保证它所获得的公开密钥（DNSKEY 记录）是真实的而不是假冒的呢？」

课本紧接着自问自答，把最容易犯的错误先堵掉：

课本原文

「尽管 DNS 服务器在返回 DNSKEY 记录的同时，也返回对这个公钥的数字签名（与 RR 同名的 RRSIG 记录）。但是，攻击者同样可以同时伪造公开密钥和数字签名两个记录而不被解析者发现。」

这就是「自证」的死穴：证明和被证明的东西都由同一个人提供，怎么核都是自洽的。要打破它，就必须让「证明」来自一个攻击者控制不了的地方。

课本给的答案课本 p.243

「与第 4 章介绍的基于 X.509 的 PKI 体系一样，DNSSEC 也需要一个信任链，必须有一个或多个开始就信任的公钥（或公钥的散列值）。RFC 4033 称这些初始信任的公开密钥或散列值为『信任锚（trust anchor）』。信任链中的上一个节点为下一个节点的公钥散列值进行数字签名，从而保证信任链中的每一个公钥都是真实的。在理想情况下，即所有 DNS 服务器均支持 DNSSEC，每个解析服务器只需要保留根域名服务器的 DNSKEY 就可以了。」

安全授权：链条是怎么一节一节接起来的课本 p.245

「解析器首先用 KSK 公钥验证 DNSKEY，然后用 ZSK 公钥来验证数据。因此，KSK 公钥成为 DNSSEC 的关键入口。如果解析器信任它所使用的 KSK 公钥，则这个 KSK 公钥就是该解析器的信任锚。

启用 DNSSEC 的区（或称签名区）将自己的 KSK 公钥交给父区，由父区用自己的 ZSK 私钥对其进行签名；同样，父区也可以将自己的 KSK 公钥交由自己的父区，由其用 ZSK 私钥进行签名。这样的过程称为安全授权，当这个过程向上到达信任锚的时候，就形成了一条信任链（trust chain）。

由于 DNS 所具有的层级结构，根区位于最顶端，且具有唯一性，因此根区的 KSK 公钥就自然而然地成为所有区的信任锚，称为 DNSSEC 信任根（DNSSEC root）。」

8.7 三个标志位：DO / AD / CD课本 p.255–256

课本原话：「DNSSEC 在协议报文头中增加了下列三个标志位。」这三个位直接对应选择题第 4、5 两题，必须分清。

标志全称谁置位课本原文含义
DODNSSEC OK
RFC 3225		发查询的一方「支持 DNSSEC 标志位。支持 DNSSEC 的解析服务器在它的 DNS 查询报文中，必须把 DO 标志位置 1，否则权威域服务器认为解析器不支持 DNSSEC，因而不返回 RRSIG 等记录。」
→ 「我要签名，请给我」
ADAuthentic Data回答的服务器「认证数据标志。如果服务器验证了 DNSSEC 相关的数字签名，则置 AD 位为 1，否则为 0。这一标志位一般用于自己不做验证的解析器和它所信任的递归解析服务器之间。」

CDChecking Disabled发查询的一方「关闭检查标志位。用于支持 DNSSEC 验证功能的解析器和递归域名服务器之间的交互。解析器在发送请求时把 CD 位置 1，服务器就不再进行数字签名的验证而把递归查询得到的结果直接交给解析器，由解析器自己验证签名的合法性。」
→ 「你别验，我自己来」
考点 · 选择题第 4、5 题（相邻两题，专治混淆）

第 4 题：在 DNSSEC 协议中，用于指示域名服务器或解析器支持 DNSSEC 的标志是（　）　A. DO　B. AD　C. CD　D. 以上都不是 → 答案 A

第 5 题：在 DNSSEC 协议中，用于关闭签名检查的标志是（　）　A. DO　B. AD　C. CD　D. 以上都不是 → 答案 C

助记：DO = DNSSEC OK（我行，我支持）；CD = Checking Disabled（别查了）；AD = Authentic Data（数据是真的）。三个词的英文全称就是答案本身。

CD 位的名字最容易理解反

「关闭检查」听起来像是放弃安全，实际恰恰相反：置 CD = 1 的一方，是那个要亲自验证的人。它对递归服务器说：「你别越俎代庖，把原始数据和签名原样给我。」

为什么要亲自验？因为「别人验过了」这句话（也就是 AD 位）本身没有签名保护，是可以伪造的。真正较真的解析器，只信自己算出来的结果。

这三个位为什么必须先有 EDNS课本 p.254–255PPT 未讲

原始 DNS 报文头里的标志位早就用光了——课本说「DNS 协议头部的第 2 个 16 比特字段定义的相关类型和标记都已经被用得差不多了」。所以 DO 位实际上是塞在 EDNS 的 OPT 伪资源记录里的（把 Z 字段的最高位定义为 DO，见 RFC 3225）。

而 EDNS 之所以必须先有，还有个更硬的理由：DNSSEC 的记录长度远超原始协议规定的 512 字节——课本：「这些记录的长度远远超过了最初的 DNS 协议标准规定的 512 字节，而要求 DNS 报文大小必须达到 1220 字节，甚至是 4096 字节。」→ EDNS 细节见 8.10

8.8 验证的四种结局课本 p.256

课本原话：「支持验证的 DNSSEC 解析器对它所收到的资源记录的签名（RRSIG）进行验证，结果可能是以下四种情况之一。」这四个词的英文要能对上中文。

①
安全的（secure）

「解析器能够建立到达资源记录签名者的信任链，并且可以验证数字签名的结果是正确的。」
→ 唯一的「一切正常」。链通了，签名也对。

②
不安全的（insecure）

「解析器收到了一个资源记录和它的签名，但是它没有到达签名者的信任链，因而无法验证。一个验证解析器可以有自己的本地策略来将某个域空间标识为不安全的。」
→ 有签名但链断了，验不了。这就是「安全孤岛」的典型状态。注意：这不是失败，是「无法判断」，通常仍然放行。

③
伪造的（bogus）

「解析器有一个到资源记录签名者的信任链和一个表示附属信息已经签名的安全代理，但是签名验证失败：丢失签名、过期的签名、不支持算法的签名、NSEC 记录表示应该存在的数据却丢失等。失败的原因可能是因为受到攻击了，也可能是管理员配置错误。」
→ 链是通的，但签名对不上——这才是真正的报警状态，数据被丢弃。

④
不确定（indeterminate）

「解析器无法获得信任锚来指出树的某个部分是安全的，这是默认的操作模式。」
→ 连信任锚都没有，压根没法开始验。「这是默认的操作模式」这半句很重要：在 DNSSEC 尚未全面部署的今天，绝大多数查询落在这一档。

最容易混的是 ② 和 ③

两者都「没验成功」，但性质截然不同：
insecure = 我没法验（链断了，或者对方根本没签）→ 不是攻击信号，通常放行
bogus = 我验了，但它是错的（链是通的，签名对不上）→ 这是危险信号，数据丢弃

用日常类比：insecure 是「这封信没有签名，我不知道谁写的」；bogus 是「这封信有签名，但签名是假的」。后者才说明有人在动手脚。

8.9 DNSSEC 挡不住什么课本 p.262 · 简答题第 5 题原文

这一小节的内容就是课本简答题第 5 题「分析 DNSSEC 的优缺点」的标准答案，几乎可以直接背。

课本原文 · 官方答案的出处课本 p.262

「DNSSEC 通过数字签名保证域名信息的真实性和完整性，防止对域名服务信息的伪造、篡改。但是：
① DNSSEC 并不保证机密性，因为它不对 DNS 记录进行加密；
② 同时它也解决不了 DNS 服务器本身的安全问题，如被入侵、存储的 Zone 数据被篡改、拒绝服务攻击、DNS 软件的实现问题等；
③ 另外，由于 DNSSEC 的报文长度增加和解析过程繁复，在面临 DDoS 攻击时，DNS 服务器承受的负担更为严重，抵抗攻击所需的资源要成倍增加。」

✓ 它解决的
  • 域名欺骗（事务 ID 欺骗、缓存投毒）——伪造的记录没有有效签名，当场被识破
  • 恶意网址重定向与中间人篡改——路径上的人改一个比特，签名就对不上
  • 否定应答的伪造——NSEC 让「不存在」也变得可验证
✗ 它挡不住
  • 窃听与隐私——签名≠加密，你查了什么路上的人照样看得一清二楚
  • 服务器被攻陷——攻击者拿到私钥，签出来的假记录一样验证通过（第 6 节 PPT 那条「攻击 DNS 服务器」）
  • 拒绝服务——不但挡不住，反而更脆弱（报文更大、验证更慢）
  • 被拿来当反射源——见下面的简答题第 6 题
考点 · 简答题第 6 题：部署 DNSSEC 后还能防反射式 DDoS 吗？

官方答案：不能。「因为 DNSSEC 虽然通过数字签名保证域名信息的真实性和完整性，防止对域名服务信息的伪造、篡改，但它并不对请求者进行身份认证。2017 年 Akamai 检测到超过 400 起利用 DNSSEC 协议的反射 DDoS 攻击。」

而且情况比「不能防」更糟——DNSSEC 让反射攻击更有效了。因为带 RRSIG、DNSKEY 的应答报文比普通应答大好几倍，放大倍数直接翻番。→ 回到 5.2 的实验台，把模式切到「带 DNSSEC 签名」看看差多少

一句话概括这道题：签名解决的是「这个回答是不是真的」，反射攻击利用的是「这个提问是不是真的」——DNSSEC 从来没管过后者。

安全性取决于什么课本 p.262 表 8-4

「DNSSEC 的安全性取决于 PKI 所用密钥的安全性……取决于密钥的位数，位数越长，意味着破解所花费的时间或者消耗的计算资源越多，因而安全强度越大。」DNSSEC 选择了 RSA/SHA-n：先用 SHA-n 做安全散列变换，再用 RSA 私钥进行数字签名。

① EDNS 扩展机制与 OPT 伪资源记录（课本 8.3.1.2，p.254–255）

为什么需要 EDNS——课本列了三条 RFC 1035 老格式的不足：

  1. 「DNS 协议头部的第 2 个 16 比特字段定义的相关类型（RCODE）和标记（flags）都已经被用得差不多了，需要添加新的返回类型和标志来支持新的需求。」
  2. 「只给标示 domain 类型的标签分配了两位，现在已经用掉了两位（00 标示字符串类型，11 标示压缩类型），后面如果有更多的标签类型则无法实现。」
  3. 「当初 DNS 协议设计时，用 UDP 协议来传输 DNS 协议数据包，且将包大小限制为 512 字节，现在很多主机已经具备重组大数据包的能力，所以需要一种机制来允许 DNS 请求方通知 DNS 服务器让其返回大的数据包。」

做法：「为了保持向后兼容性，更改已有的 DNS 协议格式是不可能的，所以只能对 DNS 协议的数据部分进行扩展。EDNS 中引入了一种新的伪资源记录 OPT RR（Pseudo-RR）。之所以称之为伪资源记录，是因为它不包含任何 DNS 数据，并且不能被缓存、不能被转发、不能被存储在区（zone）文件中。OPT 被放在 DNS 通信双方 DNS 消息的 Additional data 区域中。」

字段名数据类型描述课本表 8-2

TYPEu_int16_tOPT RR 的类型编号，IANA 为其分配的是 41（0x29）

TTL 字段被重新利用了：「高位 8 比特是扩展 RCODE（返回状态码），这 8 比特加上 DNS 头部的 4 比特总共有 12 比特……接着是 8 比特的 VERSION 字段，表示 EDNS 的版本（初始版本是 0，称为 EDNS0）；最后是 16 比特的 Z 字段。在 RFC 2671 中，Z 字段为 0，即没有定义……在 RFC 3225 中，将 Z 字段的最高位定义为 DO 标志位，用来指示是否支持 DNSSEC。」

相关标准：最早 RFC 2671 → RFC 2673 → 最新是 2013 年推出的 RFC 6891。课本还提到：「Google、Cisco、CloudFlare 等域名服务提供商自 2019 年 2 月 1 日后，对 EDNS 实现不标准的权威服务器，Google 等公共 DNS 将不再尝试访问，从而可能导致域名解析失败。」

② NSEC 的区数据枚举问题与 NSEC3（课本 p.252）

问题出在哪：NSEC 记录会老实告诉你「我的下一个是谁」。攻击者只要顺着链一路问下去（问 a → 得知下一个是 c → 问 c → 得知下一个是 f …），就能把整个区里所有子域名全部列举出来。课本称之为「区数据枚举」。

「NSEC 存在区数据枚举问题，即可以方便地枚举一个区中所有的子域名及对应的资源记录类型，此问题也是 2008 年前很多厂商不愿意部署实施 DNSSEC 的一个主要原因。2008 年之后，RFC 5155 提出替代方法 NSEC3（新增了 NSEC3 资源记录以及 NSEC3 参数记录 NSEC3PARAM），基于一定的计算复杂度这一前提，避免了区数据枚举问题。」

业界并没有共识（这就是简答题第 7 题的题眼）：「有人认为 DNS 数据本就应该是公开的，因此也就不存在所谓的区数据枚举问题；但有人认为这会让恶意攻击者获取互联网域名数据及域名注册人信息的困难度大大降低，是个潜在风险。」

现状：「如美国国家顶级域名和巴西国家顶级域名仍然使用 NSEC 方式，其他顶级域名大多已采用 NSEC3 方式。但是在一个区内，NSEC 和 NSEC3 只能选其一。NSEC 和 NSEC3 是 DNSSEC 协议中较复杂的问题，详细情况读者可参考 RFC 7129。」

③ BIND 9 的 DNSSEC 配置（课本 8.3.2，p.258–262）

课本原话：「配置或部署 DNSSEC 有两种场景：（1）配置安全的域名解析服务器（resolver），该服务器可以保护使用它的用户，防止被 DNS 欺骗攻击。这里只涉及数字签名的验证工作。（2）配置安全的权威域名服务器（name server），对权威域的资源记录进行签名，保护服务器不被域名欺骗攻击。」

配置安全解析服务器（三步）
  1. 激活 DNSSEC：在 /etc/named.conf 中打开 dnssec-validation yes;
  2. 配置信任锚：也就是你所信任的权威域的 DNSKEY。「在理想情况下，我们配置一个根的密钥就够了，但是在目前 DNSSEC 还没有完全部署的情况下，我们需要配置很多安全岛（secure island）的密钥。」课本给了三个可下载信任域 DNSKEY 的公开站点：Root Zone DNSSEC Trust Anchors（iana.org/dnssec，「如果 DNSSEC 全部部署成功，用这一个公开密钥就足够了」）、UCLA secspider、IKS Jena TAR。文件写成 trusted-keys { … }; 的形式，再 include 进 named.conf
  3. 验证：重启 named 后用 dig 测试
    #dig @127.0.0.1 +dnssec test.net. SOA
    「如果配置正确，应该返回 test.net 的 SOA 记录和相应的 RRSIG 记录，另外返回的报文头部中应该包含 AD 标志位」，形如 ;; flags: qr rd ra ad; QUERY: 1, ANSWER: 2, …
配置权威服务器（三步）
  1. 生成签名密钥对，用 BIND 自带的 dnssec-keygen：
    dnssec-keygen -a alg -b bits [-n type] [options] name
    -a 算法（RSA｜RSAMD5｜DH｜DSA｜RSASHA1｜NSEC3DSA｜…｜HMAC-SHA512）；-b 密钥长度（512｜1024｜2048｜4096）；-n 密钥类型（DNSSEC 密钥应指定 ZONE 类型）；-f KSK 表示生成密钥签名密钥。
    先生成 KSK：# dnssec-keygen -f KSK -a RSASHA1 -b 512 -n ZONE test.net.
    再生成 ZSK：# dnssec-keygen -a RSASHA1 -b 512 -n ZONE test.net.
    共产生两对密钥（四个文件），分别以 .key（公钥）和 .private（私钥）结尾。
  2. 签名：先把两个 DNSKEY 用 cat "$INCLUDE …key" >> db.test.net 写入区文件，然后
    dnssec-signzone -o zonename -f result.file [-N INCREMENT] [-k KSKfile] [-t] zonefile [ZSKfile]
    生成的 db.test.net.signed 就是签名文件，再在 named.conf 里把 zone 的 file 指向它，并打开 dnssec-enable yes;
    课本特别强调：「每次修改区中的数据时，都要重新签名」，然后 rndc reload test.net
  3. 发布公钥：「要让其他人验证你的数字签名，其他人必须有一个可靠的途径获得你的公开密钥。DNSSEC 通过上一级域名服务器数字签名的方式签发你的公钥。」用 dnssec-signzone 时会自动生成 keyset- 和 dsset- 开头的两个文件，分别存储 KSK 的 DNSKEY 记录和 DS 记录，要发送给上级（.net）的管理员，由对方加进 .net 区并用 .net 的密钥重新签名。
    如果上级还没配 DNSSEC：「那就只能另找其他方式了。例如，把上述两个文件提交到一些公开的信任锚数据库中发布（如 secspider），或者直接交给愿意相信你的解析服务器的管理员，配置到他们的 trust anchor 文件中。」

课本还给了 logging { channel dnssec_log { … }; }; category dnssec { dnssec_log; }; 的日志配置段，用于排查验证失败。

④ DNSSEC 的部署困境与「安全孤岛」（课本 8.3.4，p.262–263）

历史进程：「1999 年 RFC 2535 发布后的近 10 年间，DNSSEC 受限于技术、成本、网络性能等多方面因素的影响，一直未得到各方面的充分重视，部署进展缓慢。BIND 9 的开发主要用于支持 DNSSEC 协议。2000 年，瑞典在其国家顶级域中首次尝试部署 DNSSEC 协议，但发现存在隐私和扩展方面的问题。」

转折点是 Kaminsky：「2008 年安全研究人员发现 DNS 缓存攻击漏洞（Kaminsky 漏洞），此漏洞利用方法简单有效，影响巨大，而利用这一漏洞所发起的 DNS 缓存投毒攻击数量及其造成的损失也在大幅度上升。DNSSEC 作为解决这一漏洞的主要办法受到了业界的重视，2010 年开始进入大规模部署阶段，且呈现加速之势。」

根区签名：「根域名服务器实施 DNSSEC 是 ICANN 联合美国威瑞森公司（VeriSign），并在美国商务部支持下历时 8 个月时间，于 2011 年 7 月 15 日正式公布 DNSSEC 信任锚点，完成部署工作。」

安全孤岛：「DNSSEC 协议设计时并没有考虑增量式部署的情况，其安全功能是基于所有 DNS 服务器全部采用 DNSSEC 协议这一假设的。如果某个域名从自身向上一直到根区的链条中有某一个区域没有部署 DNSSEC 协议，则 DNSSEC 协议的认证链条无法通达，从而也就不具备其所提供的安全认证功能。因此在 DNSSEC 完全部署到位之前，会造成『安全孤岛』现象。」

「那些先部署了 DNSSEC 的区则形成一个个『孤岛』。这会造成两种情况：第一，不安全的未签名域与签名域进行通信时会将大量错误信息混入其中；第二，严格执行 DNSSEC 的域会在阻止错误信息的同时将大量未应用 DNSSEC 的域名解析信息拒之门外。」

⑤ DoH / DoT：DNSSEC 之后还缺的那一块（课本 p.264）

课本在全章最后给出了完整结论，这段话把 DNSSEC 和加密方案的分工讲得最清楚：

「总的来说，解决 DNS 解析路径劫持的最佳方案是在部署 DNSSEC 的基础上，推进 DNS 加密方案的部署。DNSSEC 能够解决 DNS 响应记录内容被中间盒子篡改的问题，部署 DNSSEC 可以保证终端用户拿到正确的响应结果。然而，此时 DNS 流量仍然通过明文传输，存在隐私隐患。DNS 加密方案，包括 DoT、DoH 等，不仅解决明文传输时的隐私威胁，而且可以对用户所使用的 DNS 服务器进行认证，进而最终解决劫持者伪装公共 DNS 服务器的问题。」

「但是，DNS 加密方案的部署比 DNSSEC 更难，争议更大。同时，相关研究（如安全会议 NDSS 2020 上发表的论文 Encrypted DNS ⇒ Privacy? A Traffic Analysis Perspective）表明 DNS 加密方案仍然存在安全问题。」

两者的分工一句话：DNSSEC 管「内容有没有被改」，DoH/DoT 管「过程有没有被看见、对面是不是本人」。缺一不可。

现状：「目前，Firefox 浏览器从第 62 版本开始支持 DNS-over-HTTPS，Google Chrome 是继 Firefox 之后添加 DoH 支持的第二款浏览器。此外，越来越多的公共 DNS 服务器和知名 DNS 软件开始逐步支持不同的 DNS 加密方案，其中公共 DNS 服务器包括 Google、Cloudflare、Quad9 等，知名的 DNS 软件包括 BIND、Unbound、Knot、CoreDNS 等。」

课本还提到 DNS OARC 的加固提议（2018 年两次会议）：除 DoH/DoT 外，还包括「DNS 服务器隐私保护、国际化域名（IDNs）滥用监测以及加强 DNSSEC 验证效率」等多方面改善域名安全的提案。

⑥ 怎么判断一个域名服务器是否支持 DNSSEC（课本 p.264）

本节结论
DNSSEC 用数字签名把「这条记录是谁说的、有没有被改」变成了可以当场计算的事实，而不是只能选择相信的传闻。
代价
记录翻倍、报文变大、解析变慢、密钥要管、签名会过期、链断一节就全白搭。二级以下的部署率至今只有 0.03%。
还没解决
隐私——签名不加密，你查了什么全世界都看得见。这才有了 DoH / DoT。整章到此闭环：从「无法验证」到「可以验证」，再到「不想被看见」。

最容易混的八组概念

这一组左边右边
1　递归 vs 迭代 递归：「你帮我查到底」。发生在客户机 ↔ 本地 DNS。负担全压在被问的一方 迭代：「我不知道，但我知道该问谁」。发生在本地 DNS ↔ 各级 DNS。负担分摊
现实中两者同时存在于一次查询里，不是二选一
2　权威 vs 本地 权威域名服务器：这条记录的真正持有者，给出的答案带 AA 位。有主辅之分，主能改记录，辅只能复制（区域传送） 本地域名服务器：你配置的那台，替你跑腿去迭代查询，并把结果缓存下来。
缓存投毒打的就是它
3　ID 欺骗 vs 缓存投毒 事务 ID 欺骗：骗一个客户端的一次查询。攻击者每次都要抢，必须在线 缓存投毒：骗一台解析器的持久记忆，TTL 由攻击者自己填，波及所有用户，还会扩散。种下之后攻击者可以下线
4　打 DNS vs 用 DNS 打人 攻击 DNS 系统本身：打客户端（一直回答「不存在」造成黑洞效应）或打服务器（DNSpod 2009、Dyn 2016） 拿 DNS 当反射点：伪造源 IP 为受害者，让服务器把应答「还」给他。靠 UDP 不握手 + 响应远大于请求（2016 里约 540 Gbps）
5　DNSKEY vs DS DNSKEY：装公钥本身，存在本区的区文件里 DS：装公钥的散列值，存在父区里。放在父区才能打破「自己证明自己」
6　ZSK vs KSK ZSK（标志 256）：签区内其他所有记录。数据量大 → 易被破解 → 生存期短 → 换起来不用惊动父区 KSK（标志 257）：只签 DNSKEY 记录。数据量小 → 难破解 → 生存期长 → 换它必须通知父区改 DS（ICANN 换一次根 KSK 是全球工程）
7　DO / AD / CD DO（查询方置位）＝ DNSSEC OK ＝「我支持，请把签名给我」
CD（查询方置位）＝ Checking Disabled ＝「你别替我验，我自己来」		 AD（回答方置位）＝ Authentic Data ＝「我替你验过了，通过」
AD 位本身没有签名保护，可以被伪造——这就是较真的解析器要置 CD=1 自己验的原因
8　insecure vs bogus insecure ＝ 我没法验（链断了，或对方根本没签）→ 不是攻击信号，通常放行 bogus ＝ 我验了，但它是错的（链是通的，签名对不上）→ 危险信号，数据丢弃
「没有签名」和「签名是假的」，性质完全不同
